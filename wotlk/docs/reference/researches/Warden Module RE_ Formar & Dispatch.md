# Comprehensive Analysis of the Warden Security Module and Check Dispatcher in World of Warcraft Build 12340

The architecture of the Warden security system in the World of Warcraft 3.3.5a client (specifically build 12340) represents a seminal implementation of client-side integrity monitoring within the massive multiplayer online (MMO) genre.
This system is designed as a dynamic, server-controlled execution environment that minimizes the local footprint while maintaining a high degree of adaptability against evolving third-party modifications and cheat software.
The fundamental design philosophy centers on a challenge-response mechanism where the server transmits a proprietary, encrypted module that the client must execute and utilize to perform environmental and memory-based audits.

---

## Cryptographic Lifecycle and Session Establishment

The security of the communication between the client and the server is predicated on a multi-stage cryptographic process that begins during the authentication phase.
The client utilizes the Secure Remote Password (SRP6) protocol to establish a shared secret without exposing the password in plain text or a simple hashed format.
The SRP6 protocol is particularly effective in preventing passive eavesdropping and man-in-the-middle attacks, which are critical for protecting the initial exchange of session keys.

### Secure Remote Password (SRP6) Mechanics

The SRP6 implementation in the 12340 client involves a series of complex modular exponentiations.
The process begins with the client sending its identity and an ephemeral public key $A$.
The server responds with a salt and its own public key $B$.
The derivation of the shared secret $S$ and the subsequent session key follows a precise mathematical framework:

\[
u = H(A, B)
\]
\[
x = H(s, H(I, ":", P))
\]
\[
S = (B - k \cdot g^x)^{(a + u \cdot x)} \mod N
\]

In these equations, $H$ is the SHA1 hash function, $P$ is the user's password, and $a$, $b$ are the private ephemeral keys generated by the client and server respectively.  
The shared secret $S$ serves as the entropy source for the RC4 stream cipher keys used for all subsequent game traffic, including the transmission of the Warden module itself.

---

### RC4 Stream Encryption and Packet Obfuscation

Once the session key is established, the client and server initialize two separate RC4 states—one for incoming traffic (SMSG) and one for outgoing traffic (CMSG).
RC4 is a symmetric stream cipher that utilizes a 256-byte state vector (S-box) to generate a pseudo-random key stream.
The implementation in the 12340 client is highly optimized, ensuring that the overhead of encryption does not negatively impact game performance while providing a necessary layer of obfuscation for the Warden protocol packets.

#### Cryptographic Component Implementation Detail

| Component                  | Implementation Detail         |
|----------------------------|------------------------------|
| Key Exchange               | SRP6 (RFC 2945 variant)      |
| Hash Algorithm             | SHA1                         |
| Stream Cipher              | RC4 (256-bit state)          |
| Message Authentication     | SHA1-based HMAC/Checksums    |

## The Warden Module Binary Format

The Warden module is not a permanent fixture of the game's file system but is instead a dynamic library (DLL) transmitted from the server upon successful login or at periodic intervals during gameplay.
This module is delivered via the `WARDEN_SMSG_MODULE_INITIALIZE` packet and exists only in the client's memory, making it more difficult for static analysis tools to locate and inspect.

### Container Structure and Obfuscation Layers

The binary blob received from the server is not a raw executable.
It is encased in a proprietary container that employs three distinct layers of protection: compression, RSA signing, and RC4 encryption.

1. **Compression:**  
   The raw module code, which is approximately 6.6 MB in its uncompressed state and contains over 5,200 functions, is compressed to reduce transmission time. The compression typically utilizes the Storm library's Zlib or PKWare implementation.

2. **RSA Digital Signature:**  
   To ensure that only authorized modules are executed, the server signs the compressed blob using a private RSA key. The client maintains a hardcoded 2048-bit RSA public key used to verify this signature before the module is decrypted.  
   This step is critical; if an attacker attempted to inject a malicious module, it would fail the signature check and the client would terminate the connection.

3. **Warden-Specific RC4 Layer:**  
   In addition to the session-wide RC4 encryption, the module itself is often encrypted with a one-time key unique to the Warden initialization packet. This prevents the module from being extracted from a raw packet capture without first reconstructing the entire session's crypto state.

---

### Module Initialization and Hooking

Upon successful decryption and decompression, the Warden module must be integrated into the game's execution flow.
The `WARDEN_SMSG_MODULE_INITIALIZE` packet provides the necessary entry point and a table of function pointers that the module requires to interact with the system.

#### Initialization Packet Structure

| Packet Field      | Data Type | Description                                               |
|-------------------|-----------|----------------------------------------------------------|
| Command           | uint8     | 0x00 (WARDEN_SMSG_MODULE_INITIALIZE)                     |
| Size              | uint16    | Total size of the initialization payload                 |
| Type              | uint8     | Architecture identifier (typically 0x01 for x86)         |
| SFileOpenFile     | uint32    | RVA for the Storm.dll file opening routine               |
| SFileGetFileSize  | uint32    | RVA for the Storm.dll file size routine                  |
| SFileReadFile     | uint32    | RVA for the Storm.dll file reading routine               |
| SFileCloseFile    | uint32    | RVA for the Storm.dll file closing routine               |
| SHA1 Checksum     | byte      | Verification hash of the function pointers               |

The provision of the SFile family of functions is particularly significant.
These functions are part of Blizzard's Storm library and are used to access the game's MPQ archives.
By providing these pointers to the Warden module, the server enables the module to perform deep integrity checks on the game's static assets, such as models, maps, and LUA scripts, directly from the disk-based archives.

## The Check Dispatcher Logic

The core of Warden's defensive capability is the check dispatcher, which resides within the loaded module.
The dispatcher is responsible for parsing requests from the server, executing the requested checks, and aggregating the results for transmission back to the server.
This process is initiated by the `WARDEN_SMSG_CHEAT_CHECKS_REQUEST` packet.

### XOR-Based Opcode Obfuscation

The dispatcher does not use transparent command identifiers.  
Instead, each check type is obfuscated using an XOR byte provided in the packet header.  
Analysis of captured check packets indicates that this XOR key is frequently set to 0x7F in many build 12340 implementations, though it can vary based on server configuration.

For example:

| Encoded Byte | XOR Key | Decoded Type | Internal Identifier |
|--------------|---------|--------------|---------------------|
| 0x28         | 0x7F    | 0x57         | TIMING_CHECK        |
| 0xC0         | 0x7F    | 0xBF         | PAGE_CHECK_B        |
| ...          | ...     | ...          | MEM_CHECK           |
| ...          | ...     | ...          | DRIVER_CHECK        |
| ...          | ...     | ...          | MODULE_CHECK        |

The decoding process: the client iterates through the check data block, applying the XOR key to each command byte.
For instance, a byte of 0x28 XORed with 0x7F results in 0x57, which corresponds to a TIMING_CHECK.  
A byte of 0xC0 XORed with 0x7F yields 0xBF, identifying a PAGE_CHECK_B.

---

### String Table and Indexing Mechanism

The `WARDEN_SMSG_CHEAT_CHECKS_REQUEST` packet utilizes a string table to store filenames, driver names, or LUA scripts that are referenced by multiple checks.
This design reduces packet size by avoiding redundant data transmission.

However, reverse engineering of the 12340 dispatcher has identified a significant implementation discrepancy:  
in the case of the MODULE_CHECK, the dispatcher in build 12340 reportedly fails to increment the string index pointer correctly, even if the module name is present in the table.
This suggests that the MODULE_CHECK might be hardcoded to look for specific identifiers or that the server-side implementation must compensate for this client-side behavior to avoid desynchronization.

## Detailed Analysis of Check Types

The Warden module implements a wide array of checks designed to detect various categories of exploitation.
These range from simple memory comparisons to sophisticated timing-based detection of virtualized environments.
