# From ClickToMove to MSG_MOVE_STOP: A Reverse-Engineering Guide to Client-Side Character Termination in World of Warcraft 3.3.5a

## Analysis of Movement Control Failure Modes

The core challenge lies in the discrepancy between user intent—to halt an ongoing character movement initiated by the `CGPlayer_C::ClickToMove` function—and the actual client-side behavior observed in World of Warcraft 3.3.5a (build 12340). The attempts made to achieve this goal have consistently failed, resulting in the character ignoring the stop command and continuing its forward motion indefinitely, evidenced by the persistent transmission of `MSG_MOVE_HEARTBEAT` (0x00EE) packets without ever generating the required `MSG_MOVE_STOP` (0x00CF) signal. This failure indicates that the mechanisms attempted are not designed to preemptively cancel an active movement order but rather to add a new command to a processing queue. Understanding why these methods fail is fundamental to devising a correct solution.

The primary method attempted was re-invoking the `ClickToMove` function with different action parameters. Specifically, calling `ClickToMove(0x0D, ...)` was used, where `0x0D` represents an "Idle" state . The expectation was that this would act as a global interrupt, cancelling any preceding move orders. However, the result was that while the character's internal state might have been updated to "idle," the physical movement persisted. This strongly suggests that the `ClickToMove` function does not operate as a high-priority interrupt handler but rather as a command enqueuer. Each call, including `action=0x0D`, is treated as a distinct instruction added to a sequence that is processed in a non-preemptive manner. An "Idle" command issued after a "Move" command simply means the character will eventually enter an idle state *after* the current move is completed, which in this case never happens because the movement logic remains engaged. The fact that a similar attempt with `action=0x03` yielded the same result further reinforces this hypothesis; any command sent through the `ClickToMove` interface appears to be subject to the same queuing mechanism and fails to override an already executing pathfinding or locomotion routine.

A second category of failed attempts involved leveraging the game's Lua scripting interface. The command `MoveForwardStop()` is a standard player action in World of Warcraft, typically bound to a key like 'S' . The expectation was that injecting this command via the `FrameScript_Execute` function at address `0x00819210` would trigger the same engine-level stop logic as a manual keypress. The complete ineffectiveness of this method on CTM-initiated movement is a critical diagnostic clue. It implies a significant architectural separation between the CTM movement system and the standard player input handling layer. The `ClickToMove` function appears to initiate a low-level, self-sustaining movement process that bypasses or operates independently from the higher-level state machines managed by the UI and Lua scripting environment. When a player manually stops, the game's input system signals the main character controller to cease locomotion and sends the `MSG_MOVE_STOP` packet. The CTM-initiated movement, however, seems to be governed by a different set of rules or a separate state machine within the `CGPlayer_C` class itself, one that is not directly influenced by these standard input commands. This explains why even native game functions, when called programmatically, have no effect on the CTM-driven locomotion.

The final unsuccessful approach involved combining multiple commands within a single frame. This tactic, while logical in trying to force a state change, also proved futile. The observation that only the last `CTM` call matters highlights the atomic nature of each function invocation. There is no inter-frame logic that compares the previous and current `CTM` actions to perform a cancellation. The system simply processes the latest instruction provided. Attempting to issue a move command followed immediately by an idle command results in the idle command being queued, but as established, it cannot preempt the ongoing move. The persistence of `MSG_MOVE_HEARTBEAT` packets confirms that the character's position is still being updated by some internal loop, and the absence of `MSG_MOVE_STOP` indicates that no formal termination protocol has been executed. The character is effectively in a limbo state: the "stop" command has been received but not acted upon, leaving the underlying movement engine in an uncoordinated state. These collective failures underscore the necessity of moving beyond the `ClickToMove` interface and seeking a lower-level, more direct method of control, either by finding a dedicated stop function or by manipulating the raw state data that governs the character's movement.

## Primary Strategy: Identifying the Internal Stop Function

The existence of such a function is highly probable within the `CGPlayer_C` class or its parent classes, as managing movement state is a core responsibility of the player-controlled character object. The task is therefore to reverse-engineer the `Wow.exe` binary (build 12340) to pinpoint this function's address and understand its signature.

A plausible candidate for this functionality would be a method within the `CGPlayer_C` class. Based on its responsibilities, a function named something like `StopMoving(void)` or `InterruptCurrentAction(void)` would be a strong contender. The hypothetical signature `void __thiscall CGPlayer_C::StopMoving(void);` suggests a simple, direct call that performs several crucial actions internally. First, it would reset the character's action state, likely writing a value corresponding to "stopped" or "idle" into the relevant member variable, thereby clearing the action flag that `ClickToMove` sets. Second, and most critically, it would construct and dispatch the `MSG_MOVE_STOP` packet. This internal generation ensures that all necessary data, such as the precise timestamp, the character's exact stopping coordinates, and the final snapshot of movement flags, are synchronized correctly, avoiding the inconsistencies that plague manual packet crafting. Third, it would likely clear or invalidate the destination coordinates and GUID stored for the pending CTM movement, preventing any resumption of the route. Finally, it would update the character's animation state to reflect a stopped posture, ensuring visual feedback matches the locomotion state.

The discovery of this function can be systematically approached through a combination of static and dynamic analysis techniques. Static analysis involves examining the disassembled code of the `Wow.exe` executable. Using a tool like IDA Pro or Ghidra, one would navigate to the cross-references of the `CGPlayer_C` class definition and search for functions whose names or behavior suggest a role in movement termination. Keywords like "stop," "interrupt," "cancel," or "locomotion" in function names or strings within the function bodies are valuable leads. Disassembling known movement-related functions, such as those handling player input or AI paths, could reveal calls to this unknown stop function.

However, dynamic analysis—observing the program's behavior at runtime—is a more powerful and targeted method. The user's existing hook on the `SendPacket` function at `0x00632B50` provides an ideal entry point for this investigation. The procedure is as follows:
1.  **Establish a Baseline:** In-game, perform a legitimate, non-cheating "stop" action. For example, pressing the 'S' key to stop walking should generate a valid `MSG_MOVE_STOP` packet.

This method is superior because it leverages the game's own, intended logic for stopping movement, ensuring compatibility and correctness.

This dynamic approach circumvents the ambiguity of static analysis and directly traces the execution path from the network event back to its source. It guarantees the identification of the function the developers themselves use, which is inherently the most reliable method. The success of this strategy hinges on capturing the correct context during a genuine stop event, making the `SendPacket` hook an indispensable tool for this research. By following this methodology, the user can transition from ineffective workarounds to a proper, function-call-based solution.

## Tertiary Strategy: Packet Injection as a Last Resort

While the preferred methods of invoking an internal stop function or performing direct memory writes are far superior due to their integration with the game's internal logic, the capability to intercept and inject network packets at the `SendPacket` hook (`0x00632B50`) provides a final, albeit challenging, avenue for achieving the objective. This strategy involves crafting a valid `MSG_MOVE_STOP` (0x00CF) packet payload and forcing the client to send it, effectively simulating a legitimate stop command from the server's perspective. This approach is considered a last resort primarily because it requires a deep understanding of the packet's binary format, which is proprietary to Blizzard, and introduces significant complexity in payload construction and synchronization.

The primary difficulty with packet injection lies in the construction of a valid payload. Unlike simpler packets, a `MSG_MOVE_STOP` packet is not merely a command with an opcode. It must contain a rich set of data points that accurately represent the character's state at the precise instant of stopping. The exact composition of this payload is unknown without reverse-engineering the client code that generates it. Based on standard MMO packet conventions and the information available, a complete payload would almost certainly include the following components:

*   **Timestamp:** A 32-bit or 64-bit integer representing the server time at which the stop occurred. Sending an incorrect or unsynchronized timestamp is a common reason for packet rejection by the server.
*   **Position (X, Y, Z):** The three-dimensional coordinates of the character at the moment it came to a halt. These must be the *exact* values, down to the floating-point precision used by the game engine.
*   **Orientation/Rotation:** The character's facing direction at the time of stopping.
*   **Movement Flags:** A bitwise representation of the character's locomotion state, including status flags like running, swimming, jumping, etc. This is a critical piece of data that must match the character's state perfectly.

The user correctly identified that crafting this payload is complex. Without knowing the precise order and encoding of these fields, creating a functional packet is largely guesswork. Any deviation—a slightly off timestamp, a rounded coordinate, or an incorrect flag combination—could lead to the server rejecting the packet, causing the character to remain in motion, or worse, triggering anti-cheat measures. The process would require a meticulous reverse-engineering effort, likely involving setting breakpoints on the function that builds the `MSG_MOVE_STOP` packet (as described in the primary strategy section) to capture a valid example of its contents. The captured bytes would then need to be analyzed to determine the layout of the structure defining the payload.

Furthermore, even if a valid packet can be constructed, the act of injecting it does not guarantee the client-side visual and logical state will be consistent with the server. The client might continue playing the "running" animation for a short period after receiving the stop packet, or it might experience a brief desynchronization before correcting its position. This can lead to a jarring player experience and potential instability. Therefore, this method is best reserved for scenarios where the other two strategies are definitively ruled out. Its most useful application in this research context would be for verification. Once a reliable stop mechanism is implemented via a function call or memory write, the DLL could capture the `MSG_MOVE_STOP` packet that the game generates internally. It could then compare this packet's content against the one it crafts and injects. If both packets are identical byte-for-byte, it serves as a definitive proof that the custom injection method is technically sound and mirrors the official client behavior. This validation step ensures that if packet injection were ever needed in another context, the implementation is flawless.
