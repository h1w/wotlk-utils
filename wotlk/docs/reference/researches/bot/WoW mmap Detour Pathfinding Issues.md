## Executive Summary

The integration of autonomous navigation capabilities into legacy game client
environments—specifically the World of Warcraft (WoW) 3.3.5a (Build 12340)
architecture—presents a complex convergence of coordinate space mathematics, binary file
structure alignment, and compile-time configuration mismatches. This report addresses the
critical failure mode observed where the findNearestPoly function of the Recast Detour library
consistently returns a null result (0) when operating on .mmap and .mmtile data generated by
the TrinityCore/MaNGOS ecosystem.

The investigation has identified that the failure is not a singular runtime error but the result of a
tripartite systemic incompatibility between the injected Dynamic Link Library (DLL) and the
static navigation data. First, the presence of the header value maxPolys=2^31 (2,147,483,648) in
the generated map files confirms that the data was constructed using a 64-bit Polygon
Reference (DT_POLYREF64) schema. The utilizing library, however, is a standard 32-bit build (via
vcpkg), which triggers an integer overflow during the bit-mask initialization in dtNavMesh::init.
This overflow forces the allocation of zero bits for the salt and tile masks, rendering the mesh
mathematically invalid and untraversable.

Second, the coordinate system transformation between the WoW client’s proprietary Z-up
world space and Recast’s Y-up navigation space requires a specific permutation matrix (

) that is not natively handled by stock Detour queries. Failure to apply this
swizzling transform places the query coordinates outside the bounding volume of the loaded
mesh.

Third, the binary file headers generated by TrinityCore contain proprietary metadata wrappers
("MMAP" magic bytes and version identifiers) that precede the standard dtNavMeshParams
structure. A direct binary read using standard Recast loaders results in memory misalignment,
causing the parsing of garbage data as mesh parameters.

This report provides an exhaustive technical deconstruction of these failure vectors, supported
by code analysis of the DetourNavMesh source, TrinityCore generation logic, and binary format
specifications. It concludes with a comprehensive remediation strategy involving the custom
compilation of the Recast library to match the 64-bit reference width, the implementation of a


custom binary loader to strip proprietary headers, and the precise application of coordinate
transformation matrices.

## 1. Technological Framework and Architecture

To understand the specific failure mechanism of findNearestPoly, one must first establish the
architectural context of the operating environment. The problem exists at the intersection of
three distinct software lineages: the legacy World of Warcraft client (2010 era), the modern
TrinityCore emulation codebase, and the Recast & Detour navigation middleware.

### 1.1 The Host Environment: World of Warcraft 3.3.5a (Build 12340)

The target application is a 32-bit x86 executable compiled for Windows. This architecture
imposes strict memory addressing limits (typically 2GB or 4GB with Large Address Awareness).
When a DLL is injected into this process, it shares the same linear address space as the game
client. This provides the distinct advantage of low-latency access to player coordinates and
object states but requires the injected code to adhere strictly to the host’s memory alignment
and calling conventions.

Crucially, the WoW client itself does not natively use Recast/Detour for its internal movement
logic in the 3.3.5a era; it relies on a proprietary mesh and heightfield system (Collision Height
Field or "CHF" and M2 collision geometry). The .mmap files in question are external artifacts,
reverse-engineered and generated by the emulation community to replicate server-side
pathfinding logic. This creates a fundamental "data provenance" disconnect: the client (WoW)
renders the world using one set of data (ADTs/WMOs), while the injected DLL attempts to
navigate using a derivative dataset (MMAPs) generated by a third-party tool (TrinityCore
mmaps_generator). Any discrepancy between the visual world and the navigation mesh results
in the agent attempting to traverse geometry that does not exist in the mesh, or vice versa.

### 1.2 The Navigation Middleware: Recast & Detour

Recast & Detour is the industry-standard open-source solution for navigation mesh generation
and pathfinding. It operates in two distinct phases:

1. **Recast (Generation):** A compile-time or offline process that voxelizes raw geometry,
    filters walkable surfaces, and generates a polygonal mesh.
2. **Detour (Runtime):** A runtime library that loads the generated mesh data and performs
    spatial queries (pathfinding, raycasting, nearest-point lookups).

The user is employing the "Stock" version of Detour (via vcpkg), which implies a standard
configuration intended for general-purpose development. However, the data (.mmap) was
generated by TrinityCore’s highly customized fork of Recast. These customizations are not


merely superficial; they alter the fundamental binary layout of the data structures.

### 1.3 The Data Pipeline: TrinityCore Mmap Generator

TrinityCore acts as the "author" of the binary data. The generation pipeline involves:

1. **Extraction:** mapextractor pulls raw geometry from the WoW client’s MPQ archives.
2. **Assembly:** vmap4assembler constructs Line-of-Sight (LoS) models.
3. **Mesh Generation:** mmaps_generator (using TerrainBuilder.cpp 1 ) consumes the map data
    and rasterizes it into Recast tiles.

The configuration settings used during step 3 are baked into the binary files. If the generator
was compiled with specific preprocessor definitions—such as DT_POLYREF64—the output files
carry that structural DNA. A consumer (the injected DLL) that does not share this DNA will
inevitably fail to interpret the data correctly.

## 3. The DT_POLYREF64 Incompatibility: The Core

## Schism

The most definitive evidence of incompatibility provided in the query is the header value

maxPolys = 2^31 ( ). This value is physically impossible for a standard 32-bit
Recast build to handle and is the primary reason for the "silent failure" of the navigation mesh


initialization.

### 3.1 The Theory of Polygon References (dtPolyRef)

In Detour, a dtPolyRef is not a pointer. It is a packed integer handle that uniquely identifies a
polygon across the entire mesh. It allows the system to validate references even if tiles are
unloaded or reloaded. The handle packs three distinct pieces of information into a single
integer:

1. **Salt ( ):** A counter incremented every time a tile is reloaded. This invalidates old
    references held by agents (e.g., if a door opens/closes and the tile rebuilds).
2. **Tile Index ( ):** The index of the tile in the mesh array.
3. **Poly Index ( ):** The index of the polygon within that specific tile.

The allocation of bits for , , and is determined dynamically at runtime during
dtNavMesh::init, based on the maxPolys and maxTiles parameters passed in the
dtNavMeshParams structure.

### 3.2 32-bit Reference Architecture (Stock Recast)

In the default vcpkg distribution, DT_POLYREF64 is undefined. The dtPolyRef type is unsigned
int (32 bits).

The logic in DetourNavMesh.cpp calculates the bit widths as follows:

This requires that at least 10 bits be reserved for the salt, leaving only 22 bits for Tiles + Polys
combined.

**Impact of DT_POLYREF64 on Alignment:**

The field userId is of type dtPolyRef.

```
● Stock Recast: dtPolyRef is 4 bytes (uint32).
● TrinityCore: dtPolyRef is 8 bytes (uint64_t).
```
When TrinityCore writes the tile, it writes 8 bytes for userId.

When the Stock DLL reads the tile, it reads 4 bytes for userId.

**Consequence:** Every field after userId is shifted by 4 bytes.

```
● polyCount reads the lower half of the 64-bit userId (or the upper half depending on
endianness).
● vertCount reads the old polyCount.
● The bvTree pointer offsets are read as garbage.
```
When findNearestPoly attempts to traverse the BVTree using these corrupted offsets, it
accesses invalid memory. In a robust system, this crashes. In a release build with relaxed
checks, it simply fails to find a leaf node and returns 0.

## 5. Algorithmic Breakdown of findNearestPoly Failure

To understand exactly _where_ the function returns 0, we trace the execution path of
dtNavMeshQuery::findNearestPoly given the identified incompatibilities.

### 5.1 The Algorithm Steps

1. **Coordinate Quantization:** The query center is verified against the mesh bounds. (Fails if
    coordinates are not swizzled).


2. **Tile Lookup:** m_nav->getTileAt(x, y, layer) is called to find the tile at the query location.
    ○ This relies on m_posLookup bucket array.
    ○ If init failed (due to the bit-width issue), the lookup table may be empty or uninitialized.
3. **Broadphase Search (BVTree):** If a tile is found, the algorithm traverses the tile’s Bounding
    Volume Tree (bvTree) to find polygons that overlap the query extents.
       ○ The BVTree node indices are stored relative to the tile data.
       ○ Due to the **4-byte alignment shift** in dtMeshHeader caused by the dtPolyRef size
          mismatch, the values in header->bvNodeCount and the root node index are corrupt.
       ○ The traversal loop while (node < end) will likely terminate immediately (if nodeCount
          reads as 0) or fail intersect tests (if nodes read as garbage floats).
4. **Polygon Refinement:** The algorithm checks the distance to polygons found.
    ○ If the BVTree returns no candidates (due to corruption), the function returns 0.

### 5.2 The "Silent" Failure

The function findNearestPoly is designed to be robust; if it finds no polygons, it returns a status
of DT_SUCCESS but sets the output nearestRef to 0. This explains why the user sees a
"success" return code (or lack of crash) but gets no result. The function is working correctly;
the data it is processing describes an empty or invalid void.

## 6. Implementation of the Solution

The incompatibility is structural and cannot be resolved by changing runtime parameters alone.
The injected DLL **must** be recompiled to match the binary footprint of the TrinityCore
generator.

### 6.1 Step 1: Forking and Compiling Recast

The user must uninstall the vcpkg version of Recast. It is unsuitable for this task because vcpkg
aims for standard ABI compatibility, whereas TrinityCore breaks standard ABI.

**Action:**

1. Clone the specific version of Recast used by the TrinityCore build (usually found in
    dep/recastnavigation of the TC source tree). This ensures protocol version matches.
2. Configure the build system (CMake) to enable 64-bit polygon references.

be implemented to strip the TC metadata.

## 7. Broader Implications for Emulation Development

This failure case highlights a significant systemic risk in game emulation development: the
**Implicit Interface Dependency**. While the .mmap file extension suggests a standard format,
the file is actually a versioned, compiler-dependent binary snapshot of a C++ object.

### 7.1 The Fragility of ABI

The fact that dtPolyRef size changes the offset of fields in dtMeshHeader is a violation of
robust binary file design, yet it is common in high-performance middleware where serialization
speed is prioritized over compatibility. By dumping structs directly to disk, TrinityCore creates a
hard dependency on the exact compiler flags (padding, packing, type sizes) used at generation
time.

### 7.2 Versioning "Hell"

TrinityCore updates its map format frequently (v4, v5, v6, etc.). The user is on Build 12340
(3.3.5a), which corresponds to a specific era of TrinityCore (circa 2010-2012, or modern "3.3.
branch"). Using a modern Recast library (vcpkg typically pulls the latest HEAD) against 2010-era
data structures invites subtle version mismatches beyond just the 64-bit reference issue. It is
strongly recommended to check the MMAP version in the file header and cross-reference it
with the TrinityCore source code history to ensure the dtNavMeshParams struct definition
hasn't changed in other ways (e.g., addition of new fields like maxVertsPerPoly).

## 8. Conclusion

The inability of the user's DLL to find polygons using findNearestPoly is a deterministic
consequence of loading 64-bit, coordinate-swizzled, proprietary-header-wrapped data into a
stock 32-bit library. The data is effectively "invisible" to the library because:


1. **Bit-width mismatch** prevents the mesh from indexing tiles (Salt/Tile bits = 0).
2. **Alignment mismatch** corrupts the geometric data in the tiles (User ID shift).
3. **Coordinate mismatch** places the query in the wrong spatial octant.

The remediation requires a full recompilation of the navigation stack with DT_POLYREF
enabled and the implementation of a proprietary loading layer to handle the TrinityCore file
wrappers. Without these binary-level adjustments, the navigation mesh will remain opaque to
the injected logic.
