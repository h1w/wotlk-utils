# Архитектура и внутренняя структура клиента World of Warcraft 3.3.5a (Build 12340): Исчерпывающий технический отчет

## 1. Введение и архитектурный обзор

Настоящий отчет представляет собой углубленное исследование внутренней архитектуры клиента World of Warcraft версии 3.3.5a (сборка 12340), выпущенной Blizzard Entertainment в 2010 году. Целью данного документа является предоставление исчерпывающей технической базы для разработки разделяемой библиотеки на языке C++, способной взаимодействовать с адресным пространством процесса, управлять состоянием игрового персонажа, перехватывать события движка и интегрировать пользовательский интерфейс на базе фреймворка ImGui.

Исследование базируется на анализе статических смещений памяти (offsets), структур данных, таблиц виртуальных функций (VTables) и механизмов взаимодействия подсистем, характерных для архитектуры x86 (32-бит). Клиент версии 3.3.5a, являясь кульминацией дополнения Wrath of the Lich King, обладает устоявшейся и хорошо документированной структурой, однако для создания высокоуровневого программного обеспечения требуется детальное понимание не только адресов, но и логики работы ключевых компонентов: Object Manager (менеджер объектов), Lua Engine (скриптовый движок), Render Pipeline (конвейер рендеринга DirectX 9) и Network Layer (сетевой слой).

Разработка библиотеки предполагает внедрение (инъекцию) кода в адресное пространство процесса Wow.exe. Это накладывает строгие требования к управлению памятью и потокобезопасности, так как клиент WoW 3.3.5a не является потокобезопасным в контексте вызова большинства своих внутренних функций. Взаимодействие должно происходить либо через перехват основного потока исполнения (Main Thread Hooking), либо через тщательную синхронизацию. В отчете детально рассматриваются методы перехвата функции EndScene интерфейса IDirect3DDevice9 для синхронизации с кадровым циклом игры, что является стандартом де-факто для реализации графических оверлеев ImGui и безопасного исполнения Lua-скриптов.

## 2. Организация памяти и Object Manager

Центральным элементом архитектуры клиента, отвечающим за хранение и управление состоянием всех игровых сущностей (игроков, NPC, динамических объектов, предметов), является Object Manager. Понимание его структуры — это фундаментальный шаг для любой разработки, связанной с чтением состояния мира.

### 2.1. Структура менеджера объектов в памяти

В сборке 12340 Object Manager не представлен простым массивом. Это сложная структура, базирующаяся на связных списках (Linked Lists), управление которыми осуществляется через статический указатель на соединение клиента. Доступ к списку объектов требует выполнения цепочки разыменований указателей (pointer dereferencing).

#### Ключевые статические адреса и смещения

| Идентификатор         | Адрес / Смещение | Тип данных | Описание                                                         |
|-----------------------|------------------|------------|-------------------------------------------------------------------|
| StaticClientConnection| 0x00C79CE0       | uintptr_t  | Глобальный указатель на структуру подключения клиента.            |
| ObjectManagerOffset   | 0x2ED0           | offset     | Смещение от ClientConnection до указателя на ObjectManager.       |
| FirstObjectOffset     | 0xAC             | offset     | Смещение от ObjectManager до первого объекта в связном списке.    |
| NextObjectOffset      | 0x3C             | offset     | Смещение внутри структуры объекта, указывающее на следующий объект|
| LocalPlayerGUIDOffset | 0xC0             | offset     | Смещение от ObjectManager до GUID локального игрока.              |

#### Алгоритм итерации по объектам

1. Получение базового адреса: Считывается значение по адресу 0x00C79CE0. Если значение равно 0, клиент не находится в игровом мире.
2. Переход к менеджеру: К полученному адресу добавляется смещение 0x2ED0. По этому адресу располагается указатель на ObjectManager.
3. Захват головы списка: По смещению 0xAC из ObjectManager считывается адрес первого объекта (FirstObject).
4. Циклический обход:  
   - Проверка валидности указателя (не Null и кратен 4).
   - Работа с объектом (чтение типа, координат, дескрипторов).
   - Переход к следующему объекту по смещению 0x3C.
   - Повторение цикла, пока указатель не станет равным 0.

**Внимание:** Объекты могут создаваться и уничтожаться в каждом кадре! Рекомендуется выполнять обход внутри перехваченной функции EndScene.

### 2.2. Типология объектов и наследование

Каждый объект в памяти наследуется от базового класса CGObject. По смещению 0x14 внутри структуры объекта находится идентификатор типа (TypeID).

| ID  | Тип (Enum)     | C++ Класс   | Описание                                      |
|-----|---------------|-------------|-----------------------------------------------|
| 1   | Item          | CGItem      | Предметы в инвентаре или экипировке           |
| 2   | Container     | CGContainer | Сумки, рюкзаки (наследуется от Item)          |
| 3   | Unit          | CGUnit      | NPC, монстры, питомцы                         |
| 4   | Player        | CGPlayer    | Игровые персонажи (наследуется от Unit)        |
| 5   | GameObject    | CGGameObject| Интерактивные объекты мира                     |
| 6   | DynamicObject | CGDynamicObject| Визуальные эффекты заклинаний, тотемы      |
| 7   | Corpse        | CGCorpse    | Тела умерших игроков и NPC                     |

### 2.3. Система дескрипторов (UnitFields)

Вся игровая статистика сущности хранится не в полях класса C++, а в специальном динамическом массиве, называемом "Дескрипторами" или UnitFields. Указатель на этот массив всегда находится по смещению `0x8` от начала объекта.

Доступ к конкретному параметру осуществляется по индексу в этом массиве. Массив хранит 32-битные значения (`uint32` или `float`), физическое смещение вычисляется как `Index * 4`.

#### Карта дескрипторов для Unit и Player:

| Параметр              | Индекс (Hex) | Смещение (Байты) | Тип данных | Примечание                                                            |
|-----------------------|--------------|------------------|------------|-----------------------------------------------------------------------|
| OBJECT_FIELD_GUID     | 0x0          | 0x00             | uint64     | Полный 64-битный GUID объекта (занимает 2 слота: 0x0 и 0x1)          |
| OBJECT_FIELD_TYPE     | 0x2          | 0x08             | uint32     | Битовая маска типа объекта                                            |
| OBJECT_FIELD_ENTRY    | 0x3          | 0x0C             | uint32     | ID записи в базе данных (NPC ID)                                      |
| UNIT_FIELD_HEALTH     | 0x18         | 0x60             | uint32     | Текущее здоровье                                                      |
| UNIT_FIELD_MAXHEALTH  | 0x20         | 0x80             | uint32     | Максимальное здоровье                                                 |
| UNIT_FIELD_POWER1     | 0x19         | 0x64             | uint32     | Текущая мана/ярость/энергия                                          |
| UNIT_FIELD_MAXPOWER1  | 0x21         | 0x84             | uint32     | Максимум маны/ярости/энергии                                         |
| UNIT_FIELD_LEVEL      | 0x36         | 0xD8             | uint32     | Уровень персонажа/NPC                                                 |
| UNIT_FIELD_FACTIONTEMPLATE | 0x37    | 0xDC             | uint32     | ID фракции (для определения враждебности)                             |
| UNIT_FIELD_FLAGS      | 0x39         | 0xE4             | uint32     | Флаги состояния (бой, оглушение, полет)                               |
| UNIT_FIELD_SUMMONEDBY | 0xE          | 0x38             | uint64     | GUID владельца (для питомцев/тотемов)                                 |

Для объектов типа Player массив дескрипторов продолжается после полей Unit. Точные индексы для специфичных полей игрока (например, XP) начинаются после последнего индекса Unit.

#### Позиционирование в пространстве

В отличие от дескрипторов, координаты объекта хранятся непосредственно в структуре класса CGObject (или его наследников), а не в массиве UnitFields. Это сделано для оптимизации рендеринга и физических расчетов.

**Смещения координат:**

- Pos X: `0x79C` (float)
- Pos Y: `0x798` (float)
- Pos Z: `0x7A0` (float)
- Rotation (Facing): `0x7A8` (float, в радианах)

> Эти значения доступны для записи, но их прямая модификация ("телепортация") часто отслеживается античит-системами на серверной стороне. Для легитимного перемещения используется подсистема Click-To-Move.

## 3. Подсистема навигации и управления (Click-To-Move)

Для программного управления персонажем наиболее эффективным методом является использование механизма Click-To-Move (CTM). Эта функция позволяет задавать точные 3D-координаты назначения и тип действия.

### 3.1. Структура CTM и адресация

CTM-структура располагается по фиксированным смещениям относительно базового класса игрока или как глобальная структура.

- Адрес функции ClickToMove: `0x00611130`
- Адрес структуры CTM (ориентировочно): `0x00CA11D0`

#### Поля структуры ClickToMove:

| Смещение | Тип     | Имя поля     | Описание                                                       |
|----------|---------|--------------|----------------------------------------------------------------|
| 0x04     | float   | TurnScale    | Скорость/масштаб поворота                                      |
| 0x0C     | float   | Distance     | Дистанция взаимодействия (насколько близко подойти)            |
| 0x1C     | int     | Action       | Тип выполняемого действия (Enum)                               |
| 0x20     | uint64  | InteractGUID | GUID цели для взаимодействия (атака, лут, разговор)            |
| 0x74     | float   | DestX        | Целевая координата X                                           |
| 0x78     | float   | DestY        | Целевая координата Y                                           |
| 0x7C     | float   | DestZ        | Целевая координата Z                                           |

### 3.2. Типы действий (Action IDs)

- **FaceTarget (0x1):** Поворачивает персонажа к координате или GUID (без движения).
- **Stop (0x3):** Немедленно останавливает движение.
- **Move (0x4):** Перемещение к заданной точке.
- **NpcInteract (0x5):** Подойти к NPC и взаимодействовать.
- **Loot (0x6):** Лут трупов мобов.
- **ObjInteract (0x7):** Взаимодействие с игровыми объектами (руда, трава и т.п.).
- **AttackGuid (0xA):** Атака по цели.
- **AttackPos (0xB / 0xD):** Атака в точку (реже используется).

### 3.3. Математика навигации и поворота

Даже при использовании CTM часто требуется самостоятельно рассчитывать углы поворота к цели.

- Угол хранения (Rotation) в WoW — радианы (от 0 до 2π).
- Для расчета угла между двумя точками используется функция арктангенса:

```math
\theta = \text{atan2}(Ty - Py, Tx - Px)
```

Полученное значение **необходимо нормализовать** в диапазон `[0, 2π]`, если результат отрицательный (добавить `2π`).

## 4. Интеграция с графическим конвейером (DirectX 9 и ImGui)

Реализация внутригрового UI с использованием ImGui требует внедрения в процесс рендеринга (hooking). WoW 3.3.5a использует API DirectX 9.

### 4.1. Механизм перехвата (Hooking) EndScene

Для отображения оверлея нужно выполнить код в момент, когда игра закончила построение 3D-сцены, но не вывела кадр на экран — для этого перехватывается функция EndScene у IDirect3DDevice9.  
**Индекс в VTable:** 42

Процесс:

1. **Поиск VTable:** создается dummy-объект IDirect3D9/IDirect3DDevice9 для получения реального указателя на VTable.
2. **Hook:** по индексу 42 заменяется функция на наш обработчик (`Hooked_EndScene`), оригинальный адрес сохраняется для trampoline-вызыва.

### 4.2. Реализация ImGui и обработка ввода (WndProc)

Внутри `Hooked_EndScene` происходит инициализация и рендеринг ImGui.

```cpp
// Псевдокод логики EndScene
HRESULT __stdcall Hooked_EndScene(LPDIRECT3DDEVICE9 pDevice) {
    if (!g_Initialized) {
        ImGui::CreateContext();
        ImGui_ImplDX9_Init(pDevice);
        g_Initialized = true;
    }
    ImGui_ImplDX9_NewFrame();
    // Отрисовка окон ImGui
    ImGui::Render();
    ImGui_ImplDX9_RenderDrawData(ImGui::GetDrawData());
    return oEndScene(pDevice); // Вызов оригинальной функции
}
```

Для передачи ввода ImGui требуется перехват оконной процедуры (`WndProc`). Через `SetWindowLongPtr` подменяется обработчик оконных сообщений на свой, который передаёт input в `ImGui_ImplWin32_WndProcHandler`. Когда ImGui "захватывает" ввод, события не передаются игре.

### 4.3. Проекция World-To-Screen (W2S)

Для реализации функционала ESP (Box ESP, линии до целей) необходимо проецировать 3D-координаты объектов мира на 2D-плоскость экрана монитора. Для этого используются матрицы камеры.

Согласно исследованиям, данные камеры находятся в динамической памяти, но доступ к ним осуществляется через указатель, возвращаемый функцией `CGWorldFrame__GetActiveCamera` (окрестности адреса `0x007A07E4`).

#### Математика проекции

Координата в пространстве экрана получается путем умножения координаты мира на видовую проекционную матрицу (ViewProjection Matrix):

```
V_clip = V_world × M_view_proj
```

После умножения производится перспективное деление (Perspective Divide):

```
V_ndc.x = V_clip.x / V_clip.w
V_ndc.y = V_clip.y / V_clip.w
```

Если `V_clip.w < 0` (или малое значение ε), точка находится позади камеры и не должна отрисовываться.

#### Смещения данных камеры

- **Camera X/Y/Z:** Смещения `0x8`, `0xC`, `0x10`
- **Матрица вида (View Matrix):** Обычно массив из 16 float значений (`Matrix4x4`), расположенный в памяти камеры. В некоторых случаях потребуется перемножить матрицу вида и матрицу проекции вручную, если игра не хранит готовую ViewProj-матрицу. Смещения матрицы часто начинаются с `0x14` или вычисляются динамически.

## 5. Интеграция с Lua Engine

World of Warcraft 3.3.5a использует модифицированную версию Lua 5.1. Интеграция с Lua позволяет вызывать внутриигровые API (например, `CastSpellByName`) и получать данные, недоступные через Object Manager (например, содержимое чата).

### 5.1. Исполнение скриптов (`FrameScript_Execute`)

Для выполнения произвольного Lua-кода из C++ используется функция, известная как `FrameScript::Execute` или `Lua_DoString`.

- **Адрес функции:** `0x00819210`

Эта функция принимает строку с кодом Lua, имя файла (контекст, обычно "GlueXML" или "RunScript") и указатель на дополнительное состояние.

Вызов этой функции позволяет библиотеке делать всё, что доступно макросам `/script`.

#### Проблема Protected Lua

Многие мощные функции (каст заклинаний, движение) защищены ("Protected") и могут вызываться только в ответ на аппаратное событие (клик мыши). Обход этой защиты в 3.3.5a возможен путем патчинга функции проверки безопасности (`IsSecure`), заставляя ее всегда возвращать `true`. Это открывает доступ к полному API (Lua Unlock).

### 5.2. Получение данных (`FrameScript_GetText`)

Для чтения значений глобальных переменных Lua (например, текста в окне) используется функция `FrameScript_GetText` (или `Lua_GetLocalizedText`).

- **Адрес функции:** `0x007225E0`

Также критически важен доступ к самому состоянию Lua (`lua_State`). Глобальный указатель на `lua_State` находится по адресу `0x00D3F78C`.

Имея этот указатель, можно использовать стандартные функции C API Lua (`lua_gettop`, `lua_tostring`, `lua_pushstring`) для прямого манипулирования стеком Lua, что быстрее и надежнее парсинга строк.

### 5.3. Перехват событий (Events)

События игры (например, `COMBAT_LOG_EVENT_UNFILTERED`) обрабатываются через систему сигналов. Перехват функции `FrameScript_SignalEvent` позволяет C++-библиотеке реагировать на события быстрее, чем это делает UI игры. Это позволяет, например, мгновенно использовать прерывание заклинания (Kick), как только сервер присылает пакет о начале каста противником, не дожидаясь отрисовки каст-бара.

## 6. Сетевой уровень и Opcodes

Наиболее продвинутый уровень взаимодействия — работа с сетевыми пакетами. Это позволяет отправлять команды серверу напрямую, минуя ограничения интерфейса Lua и проверки клиента.

### 6.1. Структура пакетов и Opcodes

Коммуникация строится на обмене пакетами, идентифицируемыми кодами операций (Opcodes). Список опкодов для 3.3.5a (12340) огромен.

#### Критически важные Opcodes

- **CMSG_CAST_SPELL**
- **CMSG_USE_ITEM** (`0x00AB`): Использование предмета
- **CMSG_GOSSIP_HELLO** (`0x017B`): Разговор с NPC
- **SMSG_UPDATE_OBJECT** (`0x00A9`): Основной пакет от сервера, содержащий информацию о появлении новых объектов или изменении их полей

Разбор этого пакета позволяет обновлять данные в Object Manager.

### 6.2. Отправка пакетов (`NetClient::SendPacket`)

Для отправки пакета необходимо сформировать объект класса `CDataStore` (буфер данных) и вызвать функцию отправки.

- **Адрес функции SendPacket:** `0x005379A0`

При отправке пакетов типа CMSG (Client Message) клиент 3.3.5a автоматически шифрует заголовок пакета (но не тело) потоком RC4 и сессионным ключом, согласованным при логине. Вызов внутренней функции SendPacket предпочтительнее самостоятельной реализации, так как она уже использует правильное состояние RC4.

## 8. Заключение

Разработка библиотеки для World of Warcraft 3.3.5a (12340) требует системного подхода к управлению памятью и понимания взаимосвязей между подсистемами клиента.

Представленные данные обеспечивают полный набор инструментов для создания функционала: от пассивного чтения состояния мира через Object Manager и дескрипторы до активного управления через Click-To-Move и инъекцию Lua-кода.

Особое внимание при реализации следует уделить безопасности:

- минимизации записи в память (использовать только CTM и Lua, избегать патчинга кода `.text`-секции во избежание детекта Warden),
- а также корректной синхронизации с основным потоком игры через хук EndScene для обеспечения стабильности работы графического интерфейса ImGui.

Комбинирование этих методов позволяет создать мощный инструмент автоматизации и расширения функционала клиента, сохраняя при этом высокую производительность и стабильность приложения.
