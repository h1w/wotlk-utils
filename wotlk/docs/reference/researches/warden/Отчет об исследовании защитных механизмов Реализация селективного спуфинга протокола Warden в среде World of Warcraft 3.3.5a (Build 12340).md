# Отчет об исследовании защитных механизмов: Реализация селективного спуфинга протокола Warden в среде World of Warcraft 3.3.5a (Build 12340)

## 1. Введение и архитектурный контекст

В сфере исследований безопасности игровых протоколов и защитных механизмов, система Warden, разработанная компанией Blizzard Entertainment, представляет собой один из наиболее долгоживущих и архитектурно сложных примеров динамической защиты клиента. Данный отчет посвящен детальному техническому анализу и реализации механизмов обхода (спуфинга) специфических проверок целостности — DRIVER_CHECK, MPQ_CHECK и PROC_CHECK — в контексте клиента World of Warcraft версии 3.3.5a (Build 12340). Исследование проводится с позиции defensive security research, с целью изучения уязвимостей в логике валидации данных на стороне клиента и сервера, особенно в условиях модифицированных серверных ядер, используемых на проектах типа Warmane.

### 1.1. Эволюция и назначение модуля Warden

Модуль Warden не является статической частью исполняемого файла WoW.exe. Вместо этого он представляет собой динамически загружаемую библиотеку (в формате PE-файла, но загружаемую вручную в память без регистрации в LDR-списках Windows), которая передается сервером клиенту во время сессии.
Эта архитектура позволяет разработчикам (или администраторам приватных серверов) обновлять сигнатуры угроз, алгоритмы сканирования и смещения памяти в реальном времени, не требуя обновления самого игрового клиента. В версии 3.3.5a используется вторая или ранняя третья итерация протокола, характеризующаяся использованием потокового шифрования RC4 для защиты канала связи между модулем и сервером, а также использованием алгоритма SHA-1 для хеширования проверяемых сегментов памяти и файлов.

Основная цель Warden — обеспечение целостности игровой среды путем обнаружения стороннего ПО, модификаций памяти (инъекций, хуков) и драйверов уровня ядра, которые могут использоваться для автоматизации игрового процесса или получения нечестного преимущества. Однако, архитектура, полагающаяся на доверие к клиентской стороне для выполнения проверок и отправки результатов, содержит фундаментальный недостаток: если клиент скомпрометирован (например, через инъекцию DLL), результаты проверок могут быть перехвачены и фальсифицированы до момента их шифрования и отправки на сервер.

## 1.2. Техническая постановка задачи

В рамках данного исследования мы оперируем в контексте уже внедренной динамической библиотеки (x86 DLL) в адресное пространство процесса WoW.exe. Существующая инфраструктура уже обеспечивает успешный перехват входящих пакетов `SMSG_WARDEN_DATA` (Opcode 0x02E6) и исходящих `CMSG_WARDEN_DATA` (Opcode 0x02E7) через установку хука на функцию шифрования RC4.
Текущее состояние системы характеризуется режимом "pass-through": запросы парсятся для анализа, но ответы отправляются оригинальные, что приводит к обнаружению любых модификаций клиента.

**Задача:** перейти от пассивного мониторинга к активному вмешательству (MITM — Man-In-The-Middle) внутри процесса. Необходимо реализовать логику селективной подмены данных для трех критических типов проверок, которые часто используются для детекции продвинутых инструментов (PQR, WPE Pro, EWT, драйверные обходы):

1. **DRIVER_CHECK** (Opcode 0x71): Проверка наличия драйверов устройств по их именам в пространстве имен объектов Windows.
2. **MPQ_CHECK** (Opcode 0x98): Верификация целостности архивов MPQ (MoPaQ) для предотвращения модификаций моделей или текстур.
3. **PROC_CHECK** (Opcode 0x7E): Проверка целостности кода внешних или внутренних процедур для обнаружения сплайсинга (инлайн-хуков).

Сложность реализации обусловлена не только необходимостью корректного формирования бинарной структуры ответа, но и особенностями парсера строк в версии 3.3.5a, который содержит ошибки индексации, требующие точного воспроизведения ("bug-compatibility") для валидации на сервере.

## 2. Архитектура протокола и криптографический слой

### 2.1. Инкапсуляция и шифрование RC4

Все коммуникации Warden защищены симметричным потоковым шифром RC4. Ключ сессии генерируется при handhshake на основе сессионного ключа, используя SHA-1 для генерации 16-байтового ключа RC4.
**Процесс:**
1. Клиент формирует буфер с результатами проверок.
2. Вызывается функция RC4_Encrypt (или её аналог), выполняющая XOR данных буфера и псевдослучайной гаммы.
3. Зашифрованные данные упаковываются в пакет `CMSG_WARDEN_DATA` и отправляются на сервер.

> Для спуфинга критически важно модифицировать данные до вызова функции шифрования.

---

### 2.2. Структура запроса WARDEN_SMSG_CHEAT_CHECKS_REQUEST

Сервер инициирует проверки, отправляя пакет с опкодом `WARDEN_SMSG_CHEAT_CHECKS_REQUEST` (обычно 0x02). Структура:

| Смещение | Тип данных | Описание                         |
|----------|------------|-----------------------------------|
| 0x00     | uint8      | Опкод Warden (0x02 - Request Checks) |
| 0x01     | uint16     | Размер строкового пула           |
| 0x03     | byte[]     | Строковый пул (null-terminated)  |
| 0x03+N   | byte[]     | Тело проверок                    |
| End      | uint8      | XOR-ключ для расшифровки типов   |

Строковый пул содержит имена модулей/драйверов/и т.д., используемые в проверках.

---

### 2.3. Цикл обработки проверок и уязвимость индексации

- Каждая проверка начинается с 1-байтового типа (Opcode), зашифрованного XOR-ключом из конца пакета.

#### Критическая ошибка индексации (Index Desynchronization Bug)
DRIVER_CHECK, MPQ_CHECK и LUA_EVAL_CHECK читают индекс строки из потока, а MODULE_CHECK — нет. Это вызывает рассинхронизацию индексов строк при разборах.
**ВАЖНО:** При реализации спуфера, эмулировать эту ошибку — иначе ответы будут не для тех проверок, и возникнет детект.

## 3. Детальный анализ реализации DRIVER_CHECK (0x71)

### 3.1. Структура запроса

| Поле        | Размер   | Описание                          |
|-------------|----------|-----------------------------------|
| Seed        | 4 байта  | Salt для хеширования              |
| SHA1        | 20 байт  | Ожидаемый хеш драйвера            |
| String Index| 1 байт   | Индекс имени драйвера в пуле      |

Механизм: через QueryDosDeviceA; 0 — нет драйвера, иначе — есть драйвер.

### 3.2. Стратегия спуфинга и формат ответа

В случае отсутствия драйвера (легитимно), клиент пишет в выходной буфер байт `0xE9`.

#### C++ пример:
```cpp
case DRIVER_CHECK:
{
  const uint8 byte = 0xE9;
  if (memcmp(buff.contents() + buff.rpos(), &byte, sizeof(uint8))!= 0) {
    // FAIL
  }
  // PASS
}
```

Реализация подмены: 
1.  Перехватить обработку типа 0x71. 
2.  Прочитать и проигнорировать 4 байта Seed и 20 байт SHA1. 
3.  Прочитать 1 байт String Index. 
4.  Важно: Не выполнять реальный вызов QueryDosDeviceA. Это избыточно и может быть 
небезопасно, если анти-чит использует ловушки (honeypots). 
5.  Вместо результата проверки записать в выходной буфер один байт: 0xE9. 
Использование байта 0xE9 может показаться странным (это опкод инструкции JMP в x86), 
но в контексте протокола Warden это магическая константа, сигнализирующая об 
отсутствии искомого объекта (драйвера, страницы памяти и т.д.). Любое другое значение 
будет интерпретировано сервером как аномалия или признак наличия драйвера, что 
повлечет за собой дальнейшие проверки или немедленную блокировку.

## 4. Детальный анализ реализации MPQ_CHECK (0x98)

### 4.1. Структура запроса и алгоритм хеширования

| Поле        | Размер   | Описание                        |
|-------------|----------|---------------------------------|
| String Index| 1 байт   | Индекс имени файла MPQ в пуле   |

**Принцип работы:**  
Сервер указывает, например, `Data\common.mpq`, а клиент должен вернуть статус и SHA-1 хеш нужного файла. Часто хешируется только часть файла (напр. заголовок или таблица файлов), иногда — полный файл.

### 4.2. Стратегия спуфинга

1. **Оффлайн-подготовка:**  
  Вычислить SHA-1 хеши для всех стандартных MPQ-файлов клиентской версии и заранее хранить их в DLL или конфиге.
2. **Перехват:**  
  При запросе 0x98 извлечь имя в строковом пуле.
3. **Поиск:**  
  Найти "чистый" хеш в своей базе.
4. **Ответ:**  
  - Записать байт `0x00`.
  - Добавить 20 байт SHA-1 хеша.

> **Важно:** Если клиент Warmane модифицирован, берите хеши с его MPQ, иначе бан.

## 5. Детальный анализ реализации PROC_CHECK (0x7E)

### 5.1. Структура запроса и целевые объекты

| Поле         | Размер    | Описание                          |
|--------------|-----------|-----------------------------------|
| Seed         | 4 байта   | Инициализация хеширования         |
| SHA1         | 20 байт   | Ожидаемый хеш для сверки          |
| Module Index | 1 байт    | Индекс имени модуля (WoW.exe и др.)|
| Proc Index   | 1 байт    | Индекс имени процедуры (функции)  |
| Offset       | 4 байта   | Смещение относительно функции     |
| Length       | 1 байт    | Сколько байт читать               |

### 5.2. Угроза хуков и стратегия "Shadow Copy"

Warden может запросить, например, пролог функции Lua_DoString. Если на нее стоит JMP-хук, сервер увидит неоригинальные байты ("JMP xx xx...") — это 100% бан.

**Метод обхода – Shadow Copy:**
1. **При ините DLL (до хуков!)** создать копию начала всех нужных функций (например, WoW.exe, lua51.dll), либо пробросить файл с диска в память через MapViewOfFile.
2. **При поступлении PROC_CHECK:**  
   - Рассчитать смещение относительно начала функции.
   - Прочитать нужный диапазон байт из shadow-копии вместо реальной памяти.
3. **Сформировать ответ:**  
   - Записать 0x00, далее оригинальные байты.

> **Примечание:** Для JMP/CALL внутри функций могут быть relocs, но прологи обычно position independent, и этого метода достаточно.

## 6. Синтез и интеграция в цикл обработки

### 6.1. Псевдокод обработчика

```cpp
void InterceptAndSpoofWarden(ByteBuffer& packet) {
    // 1. Читаем строки (string pool)
    uint16 strLen = packet.readUInt16();
    std::vector<std::string> strings = ParseStrings(packet, strLen);
    ByteBuffer resultBuff;

    // 2. Цикл по проверкам
    while (packet.readPos < packet.size() - 1) { // За минусом XOR-ключа
        uint8 type = packet.readUInt8();
        uint8 xorKey = packet.peekLastUInt8();
        uint8 realType = type ^ xorKey;
        switch (realType) {
            case 0x71: // DRIVER_CHECK
                packet.readUInt32();  // Seed
                packet.readBytes(20); // SHA1
                packet.readUInt8();   // Index
                resultBuff.writeUInt8(0xE9);
                break;
            case 0x98: // MPQ_CHECK
                uint8 strIdx = packet.readUInt8();
                std::string filename = strings[strIdx];
                uint8* cleanHash = GetCleanMpqHash(filename);
                resultBuff.writeUInt8(0x00);
                resultBuff.append(cleanHash, 20);
                break;
            case 0x7E: // PROC_CHECK
                packet.readUInt32();    // Seed
                packet.readBytes(20);   // SHA1
                uint8 modIdx = packet.readUInt8();
                uint8 procIdx = packet.readUInt8();
                uint32 offset = packet.readUInt32();
                uint8 len = packet.readUInt8();
                std::vector<uint8> cleanBytes = ReadFromShadowCopy(strings[modIdx], strings[procIdx], offset, len);
                resultBuff.writeUInt8(0x00);
                resultBuff.append(cleanBytes);
                break;
            case 0xD9: // MODULE_CHECK
                // Эмуляция бага: не читаем индекс строки!
                packet.readUInt32();
                packet.readBytes(20);
                resultBuff.writeUInt8(0xE9);
                break;
            default:
                RunOriginalCheck(realType, packet, resultBuff);
                break;
        }
    }
    SendSpoofedResponse(resultBuff);
}
```

### 6.2. Производительность

- Хеши MPQ читаем из памяти, не с диска!
- Shadow copy загружается при старте, не в момент проверки.
- Обработка занимает микросекунды — не вызывает лагов или бан через TIMING_CHECK.

## 7. Контрмеры Warmane и эвристический анализ

### 7.1. Проверки согласованности

Сервер может сравнить результат PROC_CHECK (на начало функции) с PAGE_CHECK (на 4Кб страницу памяти с этой функцией). Если подменить только PROC_CHECK, будет mismatch и бан.

> **Вывод:** Подменять и PAGE_CHECK, MEM_CHECK и PROC_CHECK всегда из одного shadow copy.

### 7.2. Серверные проверки поведения

Даже если Warden обманут, сервер банит за неестественное поведение (бот-скрипты, Unlocker, ультра-быстрые реакции). Спуф Warden скрывает ПО, но не ваши действия!

---

## 8. Заключение

Реализация спуфинга Warden для WoW 3.3.5a — это сложная инженерная задача, требующая глубокого знания криптографии, структуры пакетов и багов клиента. Ключ успеха:  
- Эмуляция use-after-free багов (магический байт 0xE9),
- Строгая имитация индексов строк,
- "Shadow Copy" стратегия для PROC_CHECK и всех memory-related проверок,
- Использование эталонных хешей MPQ строго своей сборки (оригинал/патч от Warmane).
