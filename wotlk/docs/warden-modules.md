# Warden Modules: Полное руководство по бинарному формату и извлечению типов проверок

## 1. Что такое Warden модуль

Warden модуль — это бинарный блоб размером около 18 KB в зашифрованном виде, который сервер отправляет клиенту World of Warcraft для проверки на читы.

### Ключевые особенности:
- **НЕ является PE файлом** — нет стандартных MZ/PE сигнатур Windows
- **Собственный формат Blizzard**: состоит из 40-байтного заголовка, RLE-упакованных секций и дельта-encoded релокаций
- **Pipeline обработки**:
  1. RC4 расшифровка (приходит зашифрованным с сервера)
  2. zlib декомпрессия
  3. Результат: ~29 KB распакованного кода
- **В памяти клиента**: размещается через `VirtualAlloc` с флагами `PAGE_EXECUTE_READWRITE` и `MEM_PRIVATE`

Модуль — это фактически исполняемый код, который клиент загружает в свою память и запускает. Он содержит логику для проверки памяти игры на наличие читов.

## 2. Формат заголовка (40 байт)

Первые 40 байт модуля — это заголовок, который описывает структуру модуля:

| Offset | Size | Field | Описание |
|--------|------|-------|----------|
| 0x00 | 4 | moduleSize | Итоговый размер после распаковки секций |
| 0x04 | 4 | reserved | Зарезервировано, не используется |
| 0x08 | 4 | relocOff | Смещение до таблицы релокаций |
| 0x0C | 4 | relocCount | Количество релокаций |
| 0x10 | 4 | exportTableOff | Смещение до таблицы экспортов |
| 0x14 | 4 | exportCount | Количество экспортируемых функций |
| 0x18 | 4 | baseIndex | Индекс для вычисления entry point |
| 0x1C | 4 | importTableOff | Смещение до таблицы импортов |
| 0x20 | 4 | importLibCount | Количество импортируемых библиотек |
| 0x24 | 4 | sectionDescCount | Количество дескрипторов секций |

### Структура после заголовка:
- **С offset 0x28**: дескрипторы секций (по 12 байт на каждую)
- **Далее**: упакованные данные секций начинаются с offset `0x28 + sectionDescCount * 12`

**Для новичков**: Представьте заголовок как оглавление книги — он говорит, где в модуле находятся различные части (код, данные, таблицы импортов).

### RLE упаковка секций:

Данные секций упакованы с использованием простого RLE (Run-Length Encoding) формата:

**Формат потока**:
- Чередующиеся пары `uint16_t LE`: COPY / SKIP
- Первая пара всегда начинается с COPY
- **COPY**: длина (2 байта) + literal байты (копируются как есть)
- **SKIP**: только длина (2 байта), заполняется нулями в выходном буфере

**Расположение**:
- Поток начинается с адреса `sections[0].virtualAddr`
- Заканчивается на `moduleSize`
- Заголовок (0x00-0x27) копируется в выходной буфер verbatim
- RLE данные находятся по смещению `0x28 + sectionDescCount * 12`

**Флаги секций**:
- `0x20` = CODE (исполняемый код)
- `0x02` = IDATA (инициализированные данные)
- `0x04` = BSS (неинициализированные данные)

**Распаковка**: см. Python-скрипт `wotlk/docs/scripts/module_format/unpack_rle.py`

## 3. Зачем извлекать типы проверок

### Проблема:
Каждый Warden модуль использует **свои собственные ID типов проверок**. Например:
- В модуле **7C4ABC97**: проверка TIMING имеет ID `0x1F`
- В модуле **DA3BF29E**: проверка TIMING имеет ID `0x74`
- В модуле **9A95D199**: ID типов опять другие

### Почему это важно:
1. **TrinityCore** (эмулятор сервера) захардкодил типы одного конкретного модуля в исходниках
2. Эти типы **НЕ работают** с другими модулями
3. Без знания реальных типов модуля **невозможно** правильно распарсить пакет `CHEAT_CHECKS_REQUEST`
4. Неправильный парсинг = неправильные ответы = бан

### Решение:
DLL автоматически извлекает типы проверок при загрузке каждого нового модуля, анализируя его бинарный код.

**Простая аналогия**: Это как если бы каждый учитель использовал свою систему оценок (A/B/C в одной школе, 5/4/3 в другой). Чтобы правильно понять оценку, нужно сначала узнать систему конкретного учителя.

## 4. Два паттерна диспатчера

В каждом Warden модуле есть код-диспатчер, который обрабатывает проверки. Мы нашли два паттерна:

### 4.1. Dispatch Chain (Request Parser)

**Назначение**: Используется модулем для разбора входящего пакета `SMSG_WARDEN_DATA` от сервера.

**Как это работает**:
1. **XOR-декодирование**: `xor r8, [reg+4]` — снимает XOR-шифрование с байта типа
2. **Расширение**: `movzx eax, al` — расширяет байт до 32-битного значения
3. **Дерево сравнений**: серия инструкций `cmp/sub/dec` + условные прыжки `je/jne/jg/ja`
4. **Обработчики**: каждый лист дерева ведёт к обработчику конкретного типа

**Пример дерева решений**:
```
CMP al, 0x8E
JG  label_high      ; если тип > 0x8E, идём в верхнюю ветку
JE  handler_0x8E    ; если тип = 0x8E, это MEM проверка
CMP al, 0x69
JE  handler_0x69    ; если тип = 0x69, это PROC проверка
...
```

**Извлечение типов**: Используем BFS (breadth-first search) с очередью и visited set. Обходим все ветки дерева, собираем типы из каждой ветки в локальный аккумулятор, затем объединяем результаты всех веток. CMP-значения в greater/less-семействе прыжков (jg/ja) ВСЕГДА вставляются как реальные type IDs (это pivot-значения бинарного дерева поиска).

### 4.2. Remap Table (Response Builder)

**Назначение**: Используется модулем для формирования исходящего пакета `CMSG_WARDEN_DATA` клиенту.

**Как это работает**:
1. **XOR-декодирование**: `xor r8, [reg+4]` — снимает XOR
2. **Расширение**: `movzx eax, al` — расширяет байт
3. **Сдвиг**: `add/sub` — применяет смещение
4. **Проверка**: `cmp` — проверяет, не выходит ли за пределы таблицы
5. **Ремаппинг**: `movzx byte [reg+large_disp]` — читает из таблицы на 200+ элементов
6. **Прыжок**: `jmp [reg*4+disp]` — прыгает на обработчик

**Проблема**: Таблица содержит 200+ записей, большинство из которых указывают на default handler (обработчик ошибок). Это создаёт огромное количество шума.

**Вывод**: Remap Table **бесполезна** для прямого извлечения типов, но можно использовать как fallback метод через cross-reference.

## 5. Алгоритм извлечения типов

### Стратегия 1: Dispatch Chain (работает для 11 из 15 модулей + 1 partial)

#### Шаг 1: Поиск XOR-anchored паттерна
Сканируем бинарь модуля на последовательность байт:
```
32 [40-7F, rm≠4] 04
```
Это инструкция `xor r8, [reg+4]` в различных вариациях.

#### Шаг 2: Поиск movzx
В пределах 30 байт после XOR ищем:
```
0F B6 C0+
```
Это `movzx r32, r8` — расширение байта до 32 бит.

#### Шаг 3: Определение типа диспатчера
Анализируем следующие инструкции после movzx:
- Если видим `CMP al, imm8` + условные прыжки → **Dispatch Chain**
- Если видим `ADD/SUB` → `CMP` → `MOVZX byte [reg+large_disp]` → **Remap Table**

#### Шаг 4: BFS обход дерева (для Dispatch Chain)
Запускаем BFS walker с очередью веток (максимум 16 веток, 400 байт на ветку):

| Инструкция | Действие |
|------------|----------|
| `MOV r32, imm32` | Запоминаем значение регистра для будущего использования |
| `CMP r32, imm8` + `je` | **Тип найден!** (значение из CMP). Продолжаем обход |
| `CMP r32, imm8` + `jne` | **Тип найден!** Переходим по jne, останавливаем текущую ветку |
| `CMP r32, imm8` + `jg/ja` | **CMP-значение ВСЕГДА вставляется!** (pivot BST). Переходим по jump И проверяем `je` после jg |
| `CMP r32, r32` | Берём значение из ранее запомненного регистра |
| `SUB/DEC` + `je` | `acc += delta`, тип = acc |
| `SUB/DEC` + `jne` | `acc += delta`, тип = acc, переходим по jne |
| `TEST eax, eax` + `je` | **Тип = текущий acc** (аккумулятор) |
| `JMP` | Безусловный переход, следуем за ним |
| `PUSH/CALL/RET/LEAVE` | **Стоп** — конец функции |

**Важно**: Объединяем результаты ВСЕХ веток (не выбираем лучшую).

#### Пример обхода:
```assembly
movzx eax, al          ; Расширяем тип проверки
cmp   al, 0x8E         ; Сравниваем с 0x8E
jg    upper_branch     ; Если больше, идём наверх
je    handler_MEM      ; Если равно, это MEM (0x8E) ✓

; Тип 0x8E найден! Продолжаем...
cmp   al, 0x69         ; Сравниваем с 0x69
je    handler_PROC     ; Если равно, это PROC (0x69) ✓

; Тип 0x69 найден!
```

### Стратегия 2: Remap Cross-Reference (для 3 из 15 модулей)

Для модулей, где **все** XOR-сайты являются Remap Tables (нет Dispatch Chain):

#### Шаг 1: Чтение таблиц
Для каждой найденной Remap Table читаем 256 байт.

#### Шаг 2: Группировка
Группируем элементы таблицы по их значениям (INDEX VALUE).

#### Шаг 3: Поиск default
Находим default index — самое частое значение в таблице (обычно это обработчик ошибок).

#### Шаг 4: Извлечение кандидатов
- **Singletons**: уникальные значения (встречаются 1 раз)
- **Pairs**: значения, встречающиеся 2 раза
- **Triplets**: значения, встречающиеся 3 раза
- Берём только группы размером ≤3 элементов

#### Шаг 5: ExtractFromSingleRemap (для одиночных таблиц)
Если найдена только одна remap таблица:
- Находим default handler (наиболее частое значение в таблице)
- Извлекаем все non-default записи как кандидаты в type IDs
- Не требует пересечения с другими таблицами

#### Шаг 6: Последняя попытка (last-resort)
Если основная стратегия не дала результата:
- Повторяем chain extraction на remap-классифицированных XOR-сайтах
- Часто ремап-классификация была ложной, и там на самом деле dispatch chain

#### Шаг 7: Применение shift
Вычисляем реальный тип:
```
realType = (rawOffset + shift) & 0xFF
```
где shift — смещение, применяемое модулем перед обращением к таблице.

#### Шаг 8: Пересечение
Пересекаем результаты всех Remap Tables модуля. Оставшиеся элементы = типы проверок.

**Для новичков**: Представьте, что у вас 3 списка подозреваемых. Настоящие преступники — те, кто есть во **всех трёх** списках одновременно.

## 7. Верифицированные типы (модуль 7C4ABC97)

Модуль **7C4ABC97** был вручную проанализирован и служит эталоном.

### Размеры данных проверок (из AzerothCore source):

| Type ID | Имя | Размер данных | Формат данных |
|---|---|---|---|
| 0x1F | TIMING | 0 | (нет данных) |
| 0x22 | PAGE_A | 29 | seed(4)+SHA1(20)+addr(4)+readLen(1) |
| 0x47 | PAGE_B | 29 | seed(4)+SHA1(20)+addr(4)+readLen(1) |
| 0x69 | PROC | 31 | seed(4)+SHA1(20)+modIdx(1)+procIdx(1)+addr(4)+readLen(1) |
| 0x8E | MEM | 6 | unk(1)+addr(4)+readLen(1) |
| 0x91 | MPQ | 1 | strIdx(1) |
| 0xB3 | MODULE | 24 | seed(4)+SHA1(20) |
| 0xD8 | DRIVER | 25 | seed(4)+SHA1(20)+strIdx(1) |
| 0xDB | LUA | 1 | strIdx(1) |

### Важные замечания:
1. **Размеры фиксированы** — это константы из исходников AzerothCore, идентичны для всех модулей
2. **TIMING** = 0 байт (проверка не требует дополнительных параметров)
3. **MPQ и LUA** = 1 байт (индекс строки из string section)
4. **MEM** = 6 байт (НЕ 25, как в старых документах!)
5. **MODULE** = 24 байта (seed + SHA1 хеш)
6. **DRIVER** = 25 байт (seed + SHA1 + string index)
7. **PAGE_A и PAGE_B** = идентичный формат (оба 29 байт)
8. **PROC** = 31 байт (самая сложная: seed + SHA1 + 2 индекса + адрес + длина)

### Использование в парсинге:
- Детерминированный парсер назначает размеры через структурную валидацию
- Размеры используются для вычисления границ проверок в пакете
- Типы проверок должны быть извлечены из модуля до парсинга пакета

## 8. Сигнатура модуля в памяти

### Стабильная сигнатура (найдена во всех 10 модулях):
```
56 57 FC 8B 54 24 14 8B 74 24 10 8B 44 24 0C 8B CA 8B F8 C1 E9 02 74 02 F3 A5
```

### Что это:
Это **memcpy-подобная функция** — универсальная утилита для копирования памяти, которую Blizzard включает в каждый модуль.

### Дизассемблированный код:
```assembly
push esi                  ; 56
push edi                  ; 57
cld                       ; FC (clear direction flag)
mov  edx, [esp+0x14]      ; 8B 54 24 14
mov  esi, [esp+0x10]      ; 8B 74 24 10
mov  eax, [esp+0x0C]      ; 8B 44 24 0C
mov  ecx, edx             ; 8B CA
mov  edi, eax             ; 8B F8
shr  ecx, 2               ; C1 E9 02 (копируем по 4 байта)
je   short skip           ; 74 02
rep  movsd                ; F3 A5 (fast copy)
```

### Использование:
Функция `FindModuleInMemory()` сканирует память процесса на эту сигнатуру:
1. Перебирает все регионы памяти (`VirtualQuery`)
2. Фильтрует только `MEM_PRIVATE` + `PAGE_EXECUTE_READWRITE`
3. Ищет байтовый паттерн
4. Находит → получаем базовый адрес модуля

**Зачем это нужно**: Чтобы найти загруженный модуль в памяти клиента для анализа его dispatcher'ов.

## 10. Как это используется в DLL

### Pipeline обработки нового модуля:

1. **Перехват SMSG_WARDEN_DATA** (opcode 0x2E6):
   - Hook на 0x007DA850 (WardenPreHandler)
   - Клонируем RC4 S-boxes для расшифровки

2. **MODULE_CACHE пакет**:
   - Извлекаем зашифрованный модуль из CDataStore
   - RC4 decrypt → zlib decompress
   - Сохраняем на диск: `warden_dumps/<hash>.bin`

3. **Извлечение типов** (приоритеты):
   - **PRIMARY**: In-memory scan (`ScanModuleInMemory`) — сканирование загруженного модуля в памяти процесса через `FindModuleInMemory` (поиск по сигнатуре), затем XOR-anchored dispatch chain + remap table supplement
   - **SECONDARY**: RLE-unpacked binary scan (`ScanModuleBinary` с `UnpackRLE`) — распаковка декомпрессированного бинарника через RLE алгоритм, затем сканирование реального x86 кода
   - **FALLBACK**: Raw packed binary scan (legacy, может давать false positives из-за RLE control words)
   - **LAST RESORT**: Blind memory scan всех MEM_PRIVATE регионов (`ScanAndExtractTypeIDs`)

4. **Особенности in-memory сканирования**:
   - Для сканирования используется `FindModuleInMemory()` → получаем базовый адрес модуля
   - `ScanForDispatchers()` находит XOR-anchored сайты в релоцированном коде
   - **Важно**: remap таблицы содержат абсолютные адреса (после релокации), необходимо вычесть `g_scanBaseAddr` (базу модуля) для получения buffer-relative offsets
   - `ClassifyDispatcher()` определяет Dispatch Chain vs Remap Table
   - `WalkDispatchChain()` — BFS обход дерева для dispatch chains
   - Результат: `std::set<uint8_t>` с типами проверок

5. **Парсинг CHEAT_CHECKS_REQUEST**:
   - Используем извлечённые типы для правильного парсинга
   - Формируем корректный CHEAT_CHECKS_RESULT
   - Отправляем серверу

- **`warden/warden_module.cpp`** — загрузка и кеширование модулей
- **`warden/warden_scan.cpp`** — поиск модуля в памяти
