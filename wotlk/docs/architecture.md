## 1. Общая картина

### Что такое этот проект?

Представьте, что у нас есть игра World of Warcraft (версия 3.3.5a, она же WotLK). Это обычная программа Windows, которая называется `Wow.exe`. Наша задача — "заглянуть внутрь" этой программы, чтобы понять, как она общается с сервером, особенно в части системы защиты от читов под названием **Warden**.

Для этого мы создали **две программы**:

1. **injector.exe** — консольное приложение (обычная .exe программа)
2. **wotlk.dll** — динамическая библиотека (файл с расширением .dll)

### Как они работают вместе?

```
Пользователь
   |
   | запускает
   v
injector.exe
   |
   | ищет процесс Wow.exe
   | инжектирует DLL
   v
Wow.exe ← внутри загружается wotlk.dll
   |
   | теперь DLL работает "внутри" процесса игры
   | и может перехватывать функции, читать память и т.д.
```

**Важный технический момент**: Wow.exe — это **32-битная программа** (x86). Windows не позволяет загружать 64-битную DLL в 32-битный процесс. Поэтому и `injector.exe`, и `wotlk.dll` должны быть скомпилированы как 32-битные программы (x86).

### Зачем две программы, а не одна?

- **injector.exe** — это "внешняя" программа. Она запускается отдельно, находит процесс игры и "вкалывает" в него нашу DLL. После инжекции она завершается (или остается работать, если запущена в режиме ожидания выгрузки).
- **wotlk.dll** — это "агент", который живет внутри процесса игры. Именно DLL делает всю основную работу: перехватывает функции, логирует пакеты, анализирует Warden-модули.

## 2. Последовательность событий при запуске

### Шаг за шагом: что происходит, когда вы запускаете injector.exe

#### 1. Пользователь запускает `injector.exe`

Вы просто открываете консоль (cmd.exe) и пишете:
```
injector.exe
```

#### 2. Injector ищет процесс `Wow.exe`

Программа `injector.exe` начинает сканировать список всех запущенных процессов Windows. Она ищет процесс с именем `Wow.exe`.

- Если `Wow.exe` не запущен, injector **ждет** (периодически проверяет снова каждые несколько секунд).
- Если `Wow.exe` найден, переходим к следующему шагу.

#### 3. Injector инжектирует `wotlk.dll` в процесс

Injector использует Windows API для "вкалывания" DLL в чужой процесс. Упрощенно:

1. Открывает процесс `Wow.exe` (получает handle через `OpenProcess`)
2. Выделяет память внутри процесса `Wow.exe` (через `VirtualAllocEx`)
3. Записывает путь к DLL в эту память (через `WriteProcessMemory`)
4. Создает удаленный поток внутри процесса (через `CreateRemoteThread`), который вызовет `LoadLibraryExA` с путем к нашей DLL

**Важный нюанс**: используется флаг `LOAD_WITH_ALTERED_SEARCH_PATH`. Дело в том, что `Wow.exe` по умолчанию не ищет зависимости DLL в папке самой DLL. Без этого флага мы получим ошибку 126 (модуль не найден), если у DLL есть зависимости (например, другие библиотеки).

#### 4. Windows вызывает `DllMain` при загрузке DLL

Когда `LoadLibraryExA` загружает нашу DLL, Windows автоматически вызывает функцию `DllMain` (это точка входа для любой DLL).

**Проблема**: `DllMain` вызывается под так называемым **loader lock** — глобальной блокировкой, которая не позволяет другим потокам загружать/выгружать DLL в этот момент. Если мы будем долго выполнять код в `DllMain`, можем заблокировать весь процесс или вызвать deadlock.

**Решение**: в `DllMain` мы делаем только одну вещь — создаем новый поток (`CreateThread`) и сразу возвращаем управление.

#### 5. `DllMain` создает отдельный поток `MainThread`

```cpp
BOOL APIENTRY DllMain(HMODULE hModule, DWORD ul_reason_for_call, LPVOID lpReserved) {
    if (ul_reason_for_call == DLL_PROCESS_ATTACH) {
        CreateThread(NULL, 0, MainThread, hModule, 0, NULL);
    }
    return TRUE;
}
```

Теперь вся логика переносится в `MainThread`, который работает в отдельном потоке и не блокирует loader lock.

#### 6. `MainThread` выполняет инициализацию

Этот поток делает следующее (по порядку):

##### a) Открывает консольное окно

```cpp
AllocConsole();
```

Появляется окно консоли, в котором будут выводиться логи. После `AllocConsole()` нужно перенаправить стандартные потоки `stdin`, `stdout`, `stderr` в эту консоль (через `freopen_s`).

**Важный нюанс**: чтобы ANSI color codes работали (цветные логи), нужно включить флаг `ENABLE_VIRTUAL_TERMINAL_PROCESSING` для stdout.

##### b) Настраивает логирование (glog)

Мы используем библиотеку **glog** (Google Logging Library) для структурированных логов. Настраиваем:
- Уровни логирования (INFO, WARNING, ERROR)
- Куда писать логи (консоль + файлы)
- Формат логов (с временными метками, уровнями и т.д.)

##### c) Инициализирует Shadow Copy

**Shadow Copy** — это "чистая копия" секции `.text` файла `Wow.exe` с диска. Секция `.text` содержит исполняемый код программы.

Зачем это нужно? Когда Warden проверяет память, он сравнивает текущий код в памяти с оригинальным кодом на диске. Если мы хотим понять, какие адреса проверяются, нам нужна эта чистая копия для сравнения.

##### d) Устанавливает 4 хука (функциональных перехвата)

Мы используем библиотеку **MinHook** для перехвата (hooking) четырех функций WoW:

1. **FrameScript_Execute** (адрес 0x00819210) — функция, которая выполняет Lua-скрипты в игре
2. **SMSG_WARDEN_DATA** (адрес 0x007DA850) — обработчик входящих пакетов от сервера с Warden-данными
3. **SendPacket** (адрес 0x00632B50) — функция, которая отправляет пакеты на сервер
4. **ARC4::Process** (адрес 0x00774EA0) — функция шифрования/дешифрования RC4 (используется для заголовков пакетов)

**Что такое хук?** Это техника, когда мы "подменяем" начало оригинальной функции прыжком на нашу функцию. Наша функция выполняет какую-то логику (например, логирование), а потом может вызвать оригинальную функцию.

##### e) Ожидает сигнала на выгрузку

Создается **именованное событие Windows** (named event) с именем `wotlk_unload_event`. Поток блокируется на `WaitForSingleObject` — спит, пока кто-то не сигнализирует это событие.

Когда пользователь запустит `injector.exe --eject`, injector сигнализирует это событие, и `MainThread` проснется, чтобы начать процесс выгрузки.

## 3. Последовательность событий при подключении к серверу

Теперь представим, что игрок запустил WoW, наша DLL уже загружена и работает. Игрок вводит логин/пароль и подключается к серверу. Что происходит с точки зрения Warden?

### Жизненный цикл Warden (Warden lifecycle)

#### 1. Игрок успешно логинится на сервер

Сервер принимает логин, игрок попадает в список персонажей или в мир.

#### 2. Сервер отправляет пакет `MODULE_USE` (opcode 0x00)

Это первый Warden-пакет. Сервер говорит: "Я хочу использовать Warden-модуль с таким-то хешем (MD5)".

Пример:
```
Opcode: 0x00 (MODULE_USE)
Payload: 7C 4A BC 97 ... (16 байт MD5 хеша модуля)
```

#### 3. DLL: сбрасывает состояние

Наша DLL понимает, что начинается новая Warden-сессия. Мы сбрасываем (reset) состояние всех компонентов:

- `warden_scan::Reset()` — забываем все извлеченные типы проверок из предыдущего модуля
- `warden_rc4::Reset()` — очищаем клонированные RC4 S-box'ы
- `module_dump::Reset()` — очищаем буфер для нового модуля

#### 4. DLL: пытается загрузить модуль из кеша на диске

Функция `module_dump::TryLoadFromCache(hash)` проверяет, есть ли уже сохраненный модуль с таким хешем в папке `wotlk/docs/warden_dumps/`.

Если файлы `<hash>.bin`, `<hash>.decomp`, `<hash>.rc4` уже существуют:
- Загружаем их с диска
- Пропускаем этапы 5-7
- Переходим сразу к этапу 8

Если файлов нет — продолжаем.

#### 5. Сервер отправляет пакеты `MODULE_CACHE` (opcode 0x01)

Сервер начинает передавать Warden-модуль по частям (chunks). Каждый пакет содержит ~500 байт зашифрованных данных.

Пример:
```
Opcode: 0x01 (MODULE_CACHE)
Chunk data: [~500 байт зашифрованного модуля]
```

Наша DLL собирает все чанки в буфер.

**Важно**: некоторые сервера используют кеширование. Если модуль уже был отправлен клиенту ранее, сервер может не отправлять `MODULE_CACHE` пакеты снова. Поэтому у нас есть кеш на диске.

#### 6. Сервер отправляет пакет `MODULE_INITIALIZE` (opcode 0x03)

Этот пакет означает: "Всё, модуль полностью передан, инициализируй его".

#### 7. DLL: расшифровывает, распаковывает и сохраняет модуль

Три шага:

1. **RC4 дешифрование**: модуль зашифрован RC4. Ключ — это хеш модуля. Мы расшифровываем буфер.
2. **zlib распаковка**: расшифрованные данные сжаты zlib. Распаковываем их.
3. **Сохранение на диск**: сохраняем три файла:
   - `<hash>.bin` — оригинальный зашифрованный дамп
   - `<hash>.rc4` — после RC4 дешифрования
   - `<hash>.decomp` — после zlib распаковки (это и есть бинарный Warden-модуль)

#### 8. DLL: сканирует распакованный модуль для извлечения типов проверок

Warden-модуль — это не обычная PE-библиотека (.dll), а специальный бинарный формат. Внутри есть исполняемый код, который парсит запросы от сервера и строит ответы.

**Проблема**: типы проверок (MEM_CHECK, LUA_CHECK, PAGE_CHECK и т.д.) имеют **разные ID в разных модулях**. Например, в модуле `7C4ABC97` LUA_CHECK имеет ID 0xDB, а в модуле `DA3BF29E` — ID 0x70.

**Решение**: мы сканируем бинарный код модуля, ищем **dispatch chain** — цепочку инструкций вида:
```asm
xor r8, [reg+4]       ; декодируем тип
movzx eax, al         ; расширяем до 32-бит
sub al, 0x1F          ; вычитаем базовое значение
cmp al, 0x0           ; сравниваем с 0
je handler_timing     ; если равно, это TIMING_CHECK
sub al, 0x3
cmp al, 0x0
je handler_page_a     ; если равно, это PAGE_CHECK_A
...
```

Из этой цепочки мы извлекаем реальные ID типов проверок для данного модуля.

Функция: `warden_scan::ScanModule()`

#### 9. DLL: находит модуль в памяти по сигнатуре

Warden-модуль загружается в память процесса `Wow.exe` (через `VirtualAlloc`, регион с типом `MEM_PRIVATE`).

Мы ищем его по **стабильной сигнатуре** — последовательности байт, которая встречается во всех модулях:
```
56 57 FC 8B 54 24 14 8B 74 24 10 8B 44 24 0C 8B CA 8B F8 C1 E9 02 74 02 F3 A5
```

Это начало функции типа `memcpy` (копирование памяти), которая есть в каждом модуле.

Функция: `warden_scan::FindModuleInMemory()`

#### 9a. DLL: устанавливает внутренние RC4 хуки в модуле

После нахождения модуля в памяти, `warden_rc4_hook::Install()` сканирует runtime-код модуля для поиска **ВСЕХ** RC4 PRGA функций. Использует кластерный анализ инструкций с displacement 0x100/0x101, группирует в кластеры, отбирает кластеры с обеими ссылками (i+j). Устанавливает до 4 одновременных MinHook хуков (каждый со своим naked stub и trampoline). Все последующие RC4 вызовы внутри модуля проходят через наш detour, позволяя захватить plaintext CMSG. Это решает проблему модулей, где main thread и module thread используют разные RC4 функции.

#### 10. DLL: сканирует память процесса для поиска RC4 S-box'ов

RC4 — это алгоритм шифрования. Его состояние (state) — это массив из 256 байт (называется S-box) + два индекса `i` и `j`.

Warden использует RC4 для шифрования пакетов `CMSG_WARDEN_DATA` (ответы клиента серверу). Но этот RC4 **не тот же**, что шифрует заголовки пакетов (ARC4::Process).

Мы сканируем всю память процесса (регионы `MEM_PRIVATE` и `MEM_IMAGE`) в поисках массивов, похожих на RC4 S-box:
- Проверяем, что все 256 значений уникальны (это перестановка чисел 0..255)
- Пробуем два формата: `uint8_t S[256]` (256 байт) и `uint32_t S[256]` (1024 байта)
- Пробуем два layout: `[i][j][S]` и `[S][i][j]`

Обычно находим ~40 кандидатов (20 уникальных адресов × 2 layout).

Функция: `warden_rc4::ScanMemoryForSBoxes()`

#### 11. Сервер отправляет пакет `HASH_REQUEST` (opcode 0x05)

Это НЕ проверка памяти (несмотря на название в некоторых источниках "MEM_CHECKS_REQUEST"). Это запрос на SHA1-хеш.

Сервер отправляет 16-байтовый seed (случайное число). Клиент должен вычислить SHA1-хеш и вернуть результат (20 байт).

#### 12. Сервер отправляет пакет `CHEAT_CHECKS_REQUEST` (opcode 0x02)

Это основной тип пакета — запросы на проверки.

Структура пакета:
```
[1 byte: opcode 0x02]
[N bytes: string section] — список строк, завершается 0x00
[M bytes: checks section] — последовательность проверок
[1 byte: xorByte]
```

**String section**: список строк для LUA_CHECK, MODULE_CHECK и т.д. Каждая строка — null-terminated. После последней строки идет дополнительный байт 0x00 (терминатор секции).

**Checks section**: последовательность проверок. Каждая проверка начинается с **type byte** (XOR'ованного с `xorByte`), затем идут данные.

Пример (для модуля 7C4ABC97):
```
0x8E ^ xorByte = тип MEM_CHECK
[4 байта: адрес] [1 байт: длина]

0xDB ^ xorByte = тип LUA_CHECK
[1 байт: индекс строки в string section]

0x22 ^ xorByte = тип PAGE_CHECK_A
[4 байта: seed] [4 байта: адрес] [1 байт: длина]
```

#### 13. DLL: парсит проверки, извлекает типы, адреса, строки

Наш хук `WardenPostHandler` перехватывает пакет ПОСЛЕ того, как оригинальный обработчик WoW его расшифровал RC4.

Мы парсим пакет:
- Читаем string section, строим вектор строк
- Читаем checks section, для каждого типа извлекаем байты
- Логируем все найденные проверки

Функция: `ParseChecksRequest()`

#### 14. DLL: учит размеры данных через DFS solver

**Проблема**: мы не знаем точный размер данных для каждого типа проверки (например, сколько байт после type byte для PAGE_CHECK_B?).

**Решение**: мы используем **DFS (Depth-First Search)** — алгоритм перебора с возвратом. Мы пробуем разные комбинации размеров, проверяем, парсится ли пакет полностью (доходим ли до последнего байта = xorByte). Если да — запоминаем размеры.

После нескольких пакетов мы "обучаемся" и знаем размеры всех типов для данного модуля.

Функция: `warden_scan::LearnSizesDFS()`

#### 15. Warden модуль шифрует и отправляет `CMSG_WARDEN_DATA` (opcode 0x02E7)

Оригинальный обработчик WoW строит ответ (результаты проверок), шифрует его RC4 и отправляет на сервер через `SendPacket`.

#### 16. DLL: перехватывает отправку

Наш хук `SendPacketHook` перехватывает отправку. Используется двухуровневая расшифровка:
1. **PRIMARY** (warden_rc4_hook): если внутренний RC4 хук активен → ConsumePlaintext()
2. **FALLBACK** (warden_rc4): если хук не активен → перебор клонированных S-box'ов

В текущей реализации primary метод работает на 100% — все CMSG пакеты расшифрованы через внутренний хук.

## 4. Последовательность событий при выгрузке

### Шаг за шагом: что происходит, когда вы запускаете `injector.exe --eject`

#### 1. Пользователь запускает `injector.exe --eject`

Вы открываете консоль и пишете:
```
injector.exe --eject
```

#### 2. Injector сигнализирует named event `wotlk_unload_event`

Injector открывает именованное событие (через `OpenEventW`) и сигнализирует его (через `SetEvent`).

#### 3. `MainThread` просыпается

Помните, `MainThread` в DLL спит на `WaitForSingleObject(unload_event, INFINITE)`. Когда событие сигнализируется, поток просыпается.

#### 4. `MainThread` запускает cleanup (очистку)

Выполняются следующие шаги (в обратном порядке по отношению к инициализации):

##### a) Отключает хуки

```cpp
hooks::Shutdown();
```

Вызываем `MH_DisableHook` и `MH_RemoveHook` для всех четырех хуков. Это восстанавливает оригинальный код функций.

##### b) Закрывает shadow copy

```cpp
shadow_copy::Shutdown();
```

Освобождаем память, выделенную для чистой копии `.text` секции.

##### c) Закрывает логгер

```cpp
google::ShutdownGoogleLogging();
```

Завершаем работу glog, сбрасываем буферы логов на диск.

##### d) Закрывает консоль

```cpp
fclose(stdin);
fclose(stdout);
fclose(stderr);
FreeConsole();
```

**Важно**: нужно сначала закрыть file handles (`fclose`), иначе консольное окно не закроется (handles держат консоль открытой).

##### e) Самовыгрузка: `FreeLibraryAndExitThread`

```cpp
FreeLibraryAndExitThread(hModule, 0);
```

Эта функция делает две вещи:
1. Выгружает DLL из процесса (аналог `FreeLibrary`)
2. Завершает текущий поток (аналог `ExitThread`)

**Почему нельзя просто `FreeLibrary`?** Потому что мы вызываем это из потока, который сам является частью DLL. Если мы выгрузим DLL, код потока исчезнет из памяти, и мы получим crash. `FreeLibraryAndExitThread` делает это атомарно и безопасно.

**Почему нельзя `CloseHandle` на поток из `DllMain`?** Из-за loader lock — это вызовет deadlock. Поэтому мы НЕ ждем (`WaitForSingleObject`) завершения потока, а позволяем ему завершиться самостоятельно через `FreeLibraryAndExitThread`.

## 5. Компоненты системы

Теперь давайте разберем, за что отвечает каждый файл/модуль в проекте.

### **dllmain.cpp** — точка входа

**Что делает:**
- Определяет `DllMain` — функцию, которую Windows вызывает при загрузке/выгрузке DLL
- Создает `MainThread` при `DLL_PROCESS_ATTACH`
- `MainThread` выполняет всю инициализацию и ожидает выгрузки

**Аналогия**: это "main()" для DLL.

---

### **hooks/hooks.cpp** — центральный "мозг"

**Что делает:**
- Инициализирует MinHook (`MH_Initialize`)
- Устанавливает 4 хука:
  1. `FrameScript_Execute` — для будущих экспериментов с Lua
  2. `WardenPreHandler` / `WardenPostHandler` — перехват `SMSG_WARDEN_DATA`
  3. `SendPacketHook` — перехват `CMSG_WARDEN_DATA`
  4. `ARC4ProcessHook` — диагностика шифрования заголовков
- Анализирует пакеты Warden (парсит opcodes, строки, проверки)
- Вызывает другие модули для дампа, сканирования, расшифровки

**Особенности:**

#### `SMSG_WARDEN_DATA` — НЕ стандартный `__thiscall`

Это не обычная функция с соглашением `__thiscall` (где `this` передается в `ECX`). Стек выглядит так:
```
[ret addr]
[0]
[opcode = 0x2E6]
[ECX duplicate]
[CDataStore*]  <- 4-й аргумент на стеке
```

Поэтому мы используем `__declspec(naked)` — "голую" функцию без пролога/эпилога. Сами сохраняем все регистры (`pushad`, `pushfd`), извлекаем `CDataStore*` из стека, вызываем наш C++ код, восстанавливаем регистры (`popfd`, `popad`) и прыгаем на оригинальную функцию.

#### Return-address hijack (подмена обратного адреса)

Данные в `CDataStore` на момент вызова хука **еще зашифрованы RC4**. Расшифровка происходит ВНУТРИ оригинального обработчика.

Мы хотим прочитать расшифрованные данные. Решение:
1. **WardenPreHandler** (до вызова оригинала):
   - Сохраняем указатель на `CDataStore`
   - Сохраняем текущую позицию чтения (`readPos`)
   - Подменяем return address на стеке на адрес `WardenPostHandler`
   - Вызываем оригинальный обработчик
2. Оригинальный обработчик расшифровывает данные и выполняет `ret`
3. `ret` возвращает НЕ в исходную функцию, а в **WardenPostHandler**
4. **WardenPostHandler**:
   - Читает расшифрованные данные из сохраненного `CDataStore`
   - Логирует, парсит, анализирует
   - Восстанавливает оригинальный return address
   - Делает `ret` — возвращаемся туда, откуда изначально была вызвана функция

#### `__declspec(naked)` нельзя forward-declare в MSVC

Проблема: мы не можем объявить `void WardenPostHandler();` в заголовочном файле, если функция помечена `__declspec(naked)`.

Решение: используем глобальную переменную `void* g_wardenPostHandlerAddr`, которую устанавливаем в `Initialize()`.

---

### **warden/module_dump.cpp** — захват Warden-модулей

**Что делает:**
- Слушает пакеты `MODULE_USE`, `MODULE_CACHE`, `MODULE_INITIALIZE`
- Собирает чанки модуля в буфер
- Расшифровывает RC4 (ключ = MD5 хеш модуля)
- Распаковывает zlib
- Сохраняет три файла на диск (`<hash>.bin`, `<hash>.rc4`, `<hash>.decomp`)
- При следующем подключении пробует загрузить модуль из кеша (`TryLoadFromCache`)

**Зачем кеш?** Некоторые сервера не отправляют `MODULE_CACHE` повторно, если модуль уже был отправлен (клиент кеширует модули). Без кеша мы не сможем извлечь типы проверок при переподключении.

---

### **warden/warden_scan.cpp** — извлечение типов проверок

**Что делает:**
- Сканирует распакованный Warden-модуль в поисках **dispatch chain** или **remap cross-reference**
- Извлекает соответствие "тип проверки → реальный ID в этом модуле"
- Реализует **DFS solver** для обучения размеров данных каждого типа
- Умеет искать hook-адреса в сырых байтах проверок (функция `ScanForHookAddresses`)

**Три стратегии сканирования:**

1. **XOR-anchored scan** (основная): ищет паттерн `xor r8, [reg+4]` → `movzx eax, al` → цепочку `sub/cmp/je`. Это request parser (dispatch chain).
2. **Cmp-cluster fallback**: ищет кластеры инструкций `cmp al, N`.
3. **Sub-chain fallback**: ищет цепочки инструкций `sub al, N`.

Тестировано на 10 модулях: 8/10 имеют dispatch chains, все 10 имеют remap tables.

---

### **warden/warden_rc4.cpp** — поиск RC4 S-box'ов и расшифровка CMSG

**ПРИМЕЧАНИЕ:** Это fallback-метод. Основной метод расшифровки — внутренний RC4 хук (warden_rc4_hook.cpp).

**Что делает:**
- Сканирует память процесса (регионы `MEM_PRIVATE` и `MEM_IMAGE`) в поисках RC4 S-box'ов
- Проверяет, что массив — это перестановка чисел 0..255
- Поддерживает два формата: `uint8_t S[256]` (256 байт) и `uint32_t S[256]` (1024 байта)
- Поддерживает два layout: `[i][j][S]` и `[S][i][j]`
- **Клонирует** все S-box'ы в `WardenPreHandler` (до того, как CMSG зашифруется)
- В `SendPacketHook` пробует расшифровать CMSG каждым клонированным S-box'ом
- Использует **структурную валидацию** расшифрованных данных (не только opcode byte):
  - `MODULE_MISSING` / `MODULE_OK` = 1 байт
  - `HASH_RESULT` = 21 байт (1 opcode + 20 байт SHA1)
  - `CHEAT_CHECKS_RESULT` = 7+ байт (1 opcode + 2 len + 4 checksum + data)

**Потокобезопасность**: используется `CRITICAL_SECTION`, потому что клонирование происходит в главном потоке (где приходит SMSG), а расшифровка CMSG — в потоке Warden-модуля.

**Почему 64 MB max region size?** Изначально был лимит 4 MB, но некоторые S-box'ы находились в больших регионах памяти и пропускались.

---

### **warden/warden_rc4_hook.cpp** — внутренний хук RC4 (PRIMARY)

**Что делает:**
- Сканирует runtime-память Warden модуля для поиска **ВСЕХ** функций RC4 PRGA
- Использует кластерный анализ: ищет инструкции с displacement 0x100/0x101 (позиции i/j в RC4 контексте)
- Группирует совпадения в кластеры, отбирает кластеры с обеими ссылками (i + j)
- Устанавливает до **4 одновременных** MinHook хуков на найденные функции
- Захватывает plaintext CMSG ДО шифрования RC4

**Multi-hook архитектура:**
- 4 отдельных naked stub'а (`HookedRC4Naked_0`—`_3`), каждый с собственным trampoline
- Общий `RC4DetourHandler` для всех слотов (convention detection shared)
- Решает проблему модулей, где main thread и module thread используют разные RC4 функции (напр. модуль 0BE6B21C)

**Жизненный цикл:**
- Install: после MODULE_INITIALIZE — сканирует и хукает все найденные RC4 функции
- Remove: перед MODULE_USE (когда загружается новый модуль) и при Shutdown — снимает все хуки
- ConsumePlaintext: one-shot получение данных (очищает буфер после чтения)

**Calling convention (6 вариантов, auto-detection):**
- ECX=ctx / EDX=ctx / EAX=ctx (register-based, проверяются первыми)
- stk1=ctx (stack-based __cdecl, проверяется последним)
- Для каждого: normal (stk1=data, stk2=len) или swapped (stk1=len, stk2=data)
- Авто-определение через `LooksLikeRC4Context` + S-box permutation check

**Fallback:** Если ни одна RC4 функция не найдена → `Install()` возвращает false → SendPacket использует `warden_rc4::DecryptCmsg()` (S-box клонирование)

**Потокобезопасность:** CRITICAL_SECTION + InterlockedIncrement (RC4 вызывается из потока Warden модуля)

---

### **warden/shadow_copy.cpp** — чистая копия .text секции

**Что делает:**
- Открывает файл `Wow.exe` на диске
- Парсит PE-заголовки, находит секцию `.text`
- Читает секцию в выделенный буфер памяти
- Предоставляет функцию `CompareMemory` для сравнения адреса в памяти с чистой копией

**Зачем это нужно?** Warden проверяет, не изменен ли код игры (например, не установлены ли хуки, патчи и т.д.). Имея чистую копию, мы можем понять:
- Какие адреса проверяются
- Какие байты сервер ожидает увидеть
- Какие наши хуки могут быть обнаружены

---

### **injector/main.cpp** — инжекция/выгрузка DLL

**Что делает:**
- Парсит аргументы командной строки (`--eject`)
- Если `--eject`:
  - Сигнализирует событие `wotlk_unload_event`
  - Завершается
- Если обычный запуск:
  - Ищет процесс `Wow.exe` (ждет, если не найден)
  - Инжектирует `wotlk.dll` через shellcode + `CreateRemoteThread`
  - Shellcode вызывает `LoadLibraryExA` с флагом `LOAD_WITH_ALTERED_SEARCH_PATH`
  - Проверяет результат (если 0 — ошибка, читает `GetLastError` из удаленного процесса)

**Почему shellcode?** Мы не можем напрямую вызвать `LoadLibraryExA` в чужом процессе. Мы можем только создать удаленный поток (`CreateRemoteThread`), который выполнит наш код. Shellcode — это небольшой фрагмент машинного кода (x86 assembly), который мы записываем в память чужого процесса.

### Входящий пакет от сервера (SMSG_WARDEN_DATA)

```

│                            СЕРВЕР                                │
└───────────────────────────┬─────────────────────────────────────┘
                            │
                            │ Отправляет SMSG_WARDEN_DATA
                            │ (opcode 0x02E6, payload зашифрован RC4)

│  - Расшифровывает ЗАГОЛОВОК через ARC4::Process                  │
│    (4 байта: размер пакета)                                      │
└───────────────────────────┬─────────────────────────────────────┘
                            │
                            │ Payload все еще зашифрован RC4
                            v
┌─────────────────────────────────────────────────────────────────┐
│                    WardenPreHandler (наш хук)                    │
│  - Перехватываем ПЕРЕД оригинальным обработчиком                 │

                            │ Вызываем оригинальный обработчик

│            Оригинальный обработчик WoW (0x007DA850)              │

                            │ RET прыгает на подмененный адрес
```

## Глоссарий терминов

Для тех, кто не знаком с терминами:

- **DLL (Dynamic Link Library)** — динамическая библиотека, файл .dll, который может быть загружен в процесс и содержит код/данные.
- **Инжекция DLL** — техника загрузки DLL в чужой процесс (не через обычный `LoadLibrary`, а через Windows API).
- **Хук (hook)** — перехват функции: подмена начала функции прыжком на свою функцию.
- **Loader lock** — глобальная блокировка Windows, которая удерживается во время загрузки/выгрузки DLL. Нельзя долго работать под этой блокировкой.
- **Named event** — именованное событие Windows, механизм синхронизации между процессами.
- **RC4** — алгоритм потокового шифрования. Состояние = S-box (массив 256 байт) + два индекса i, j.
- **S-box** — substitution box, массив перестановки в алгоритмах шифрования.
- **CDataStore** — внутренний класс WoW для сериализации/десериализации данных (аналог buffer + read/write position).
- **Opcode** — код операции, первый байт пакета, определяющий тип пакета.
- **Shadow copy** — копия данных, сделанная для сравнения или резервирования.
- **DFS (Depth-First Search)** — алгоритм поиска в глубину, используется для перебора вариантов.
- **Dispatch chain** — цепочка инструкций вида if-else (через sub/cmp/je), которая диспетчеризует разные типы запросов.
- **Shellcode** — небольшой фрагмент машинного кода, используемый для выполнения в чужом процессе.

## Заключение

Эта система — сложный, но хорошо структурированный инструмент для анализа протокола Warden в World of Warcraft 3.3.5a.

Ключевые идеи:
1. **Разделение ответственности**: injector только инжектирует, DLL только анализирует.
2. **Многопоточность**: DllMain не блокируется, вся работа в отдельных потоках.
3. **Hooking**: четыре хука перехватывают ключевые функции до/после их выполнения.
4. **Обучение**: система DFS "учится" размерам данных из реальных пакетов.
5. **Кеширование**: модули сохраняются на диск, чтобы избежать повторной загрузки.
6. **RC4 cloning**: клонирование S-box'ов позволяет расшифровать CMSG без реверс-инжиниринга всего модуля.

Надеюсь, это помогло вам понять архитектуру проекта от начала и до конца.
