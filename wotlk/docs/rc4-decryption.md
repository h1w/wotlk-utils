# RC4 Расшифровка CMSG_WARDEN_DATA

Этот документ объясняет, как мы пытаемся расшифровать исходящие ответы клиента на запросы Warden.

## 1. Зачем нужна расшифровка CMSG

### Что мы уже можем видеть
- **SMSG_WARDEN_DATA** (сервер → клиент): мы перехватываем через return-address hijack **ПОСЛЕ** того, как Warden handler расшифровал пакет
- Мы видим расшифрованные данные: MODULE_USE, HASH_REQUEST, CHEAT_CHECKS_REQUEST и т.д.
- Это работает отлично

### Проблема с CMSG
- **CMSG_WARDEN_DATA** (клиент → сервер): ответы клиента на запросы Warden
- Мы перехватываем эти пакеты в хуке SendPacket (адрес 0x00632B50)
- Но к этому моменту данные **уже зашифрованы** RC4 cipher'ом Warden модуля
- Мы видим только зашифрованный мусор

### Почему это важно
Чтобы понять, что происходит в диалоге Warden ↔ клиент, нам нужно видеть **обе стороны**:
- Что сервер **спрашивает** (SMSG) — это мы видим ✓
- Что клиент **отвечает** (CMSG) — это мы НЕ видим ✗

Без расшифровки CMSG мы не знаем:
- Какие хеши клиент отправил на HASH_REQUEST
- Какие результаты MEM_CHECK клиент вернул
- Что клиент ответил на LUA_EVAL проверку

## 2. Два разных RC4 cipher'а

В WoW 3.3.5a используются **два отдельных RC4 шифра**. Начинающие часто их путают.

### Session cipher (ARC4::Process @ 0x00774EA0)
**Назначение**: шифрует заголовки ВСЕХ сетевых пакетов (не только Warden!)

**Что шифрует**:
- CMSG header: 2 байта (размер пакета) + 4 байта (opcode) = 6 байт
- SMSG header: 4 байта

**Что НЕ шифрует**:
- Payload (содержимое) пакетов

**Расположение**: код в исполняемом файле Wow.exe (адрес 0x00774EA0)

**Ключ**: генерируется при логине из сессионного ключа (session key)

**Это НЕ то, что нам нужно для Warden payload!**

### Warden cipher
**Назначение**: шифрует payload ТОЛЬКО Warden пакетов (0x2E6 SMSG, 0x2E7 CMSG)

**Что шифрует**:
- Весь payload после opcode (MODULE_USE, HASH_REQUEST, CHEAT_CHECKS_REQUEST и т.д.)

**Расположение**: внутри blob'а Warden модуля (загружается в VirtualAlloc, MEM_PRIVATE память)

**S-box'ы**: **ДВА отдельных** S-box'а в памяти модуля:
- Один для **decrypt** (расшифровка входящих SMSG от сервера)
- Один для **encrypt** (зашифровка исходящих CMSG к серверу)

**Формат S-box**: uint8_t S[256] — массив из 256 байт (подтверждено сканированием)

**Ключ**: отправляется сервером в пакете MODULE_INITIALIZE (16 байт RC4 ключа)

**Это то, что нам нужно!**

## 3. Как работает RC4

RC4 (Rivest Cipher 4) — потоковый шифр. Очень простой алгоритм, объясню по шагам.

### Key Scheduling Algorithm (KSA) — инициализация
На входе: ключ произвольной длины (в Warden — 16 байт)

```cpp
// Инициализируем S-box значениями 0..255
for (int i = 0; i < 256; i++) {
    S[i] = i;
}

// Перемешиваем S-box на основе ключа
int j = 0;
for (int i = 0; i < 256; i++) {
    j = (j + S[i] + key[i % key_length]) % 256;
    swap(S[i], S[j]);
}
```

После KSA:
- **S-box** содержит перестановку чисел 0-255 (все уникальные)
- Два счётчика **i** и **j** обнуляются

### Pseudo-Random Generation Algorithm (PRGA) — шифрование/расшифровка
Для каждого байта данных:

```cpp
i = (i + 1) % 256;           // Увеличиваем i
j = (j + S[i]) % 256;        // Обновляем j на основе S[i]
swap(S[i], S[j]);            // Перемешиваем S-box

uint8_t K = S[(S[i] + S[j]) % 256];  // Генерируем keystream байт
output = input ^ K;          // XOR с данными
```

**Ключевое свойство RC4**: encrypt и decrypt — это **одна и та же операция**!
- plaintext XOR keystream = ciphertext
- ciphertext XOR keystream = plaintext

Потому что XOR обратим: `(A ^ B) ^ B = A`

### Почему два S-box'а в Warden
Warden общается по схеме request-response:
- Сервер → клиент (SMSG): клиент **decrypt** с помощью decrypt S-box
- Клиент → сервер (CMSG): клиент **encrypt** с помощью encrypt S-box

Оба S-box'а инициализируются **одним и тем же ключом** из MODULE_INITIALIZE, но работают **независимо** (разные i, j, состояние S).

## 4. Стратегия: клонирование S-box'ов

Мы не знаем ключ Warden RC4. Но нам он и не нужен! Мы клонируем **уже инициализированные** S-box'ы из памяти.

### Шаг 1: Сканирование (ScanForRC4States)
**Цель**: найти все RC4 S-box'ы в памяти процесса

**Алгоритм**:
1. Перебираем все readable memory regions (VirtualQuery):
   - MEM_PRIVATE (в т.ч. VirtualAlloc от Warden модуля)
   - MEM_IMAGE (исполняемые файлы и DLL'ки)

2. Для каждого адреса в регионе проверяем:
   - Читаем 256 байт подряд
   - Проверяем: это перестановка 0-255? (каждое значение от 0 до 255 встречается ровно 1 раз)

3. Проверяем два layout'а для uint8_t:
   - **Layout A**: `[i (1 байт)][j (1 байт)][S[256]]` — индексы перед массивом
   - **Layout B**: `[S[256]][i (1 байт)][j (1 байт)]` — индексы после массива

4. Дополнительно проверяем uint32_t варианты (для совместимости):
   - `[i (4 байта)][j (4 байта)][S[256*4]]` — 1024 байта
   - `[S[256*4]][i (4 байта)][j (4 байта)]`

**Результат**: находим ~38 кандидатов (19 уникальных адресов × 2 layout'а)

Среди них:
- Session cipher S-box (ARC4::Process this->S)
- Warden decrypt S-box
- Warden encrypt S-box (это нам нужно!)
- Мусор (случайные перестановки в памяти — редко, но бывает)

### Шаг 2: Клонирование (CloneAllStates в WardenPreHandler)
**Когда**: вызывается в `WardenPreHandler` — **ДО** того, как Warden handler начнёт обработку пакета

**Почему именно здесь**:
- Мы перехватываем SMSG_WARDEN_DATA через return-address hijack
- `WardenPreHandler` срабатывает **перед** оригинальным handler'ом
- В этот момент Warden handler ещё не расшифровал CMSG (который он отправит в ответ)
- Значит, encrypt S-box ещё не использовался → его состояние чистое

**Алгоритм**:
1. Сканируем память заново (ScanForRC4States)
2. Для каждого найденного адреса:
   - Читаем i, j (из layout-специфичных смещений)
   - Копируем S[256] (256 байт)
   - Сохраняем в массив `g_clonedStates[]`
3. Логируем: "Cloned 38/38 RC4 states"

**Thread safety**: используем CRITICAL_SECTION (InitializeCriticalSection + EnterCriticalSection + LeaveCriticalSection), потому что Warden работает в отдельном потоке (не main thread).

### Шаг 3: Попытка расшифровки (DecryptCmsg в SendPacket hook)
**Когда**: вызывается в хуке SendPacket, когда клиент отправляет CMSG_WARDEN_DATA (opcode 0x2E7)

**Алгоритм**:
1. **Fast path** (если уже нашли правильный S-box):
   - Используем запомненный индекс `g_lockedInCloneIndex`
   - Пробуем расшифровать
   - Если success → готово
   - Если fail → переходим к full scan (может быть reconnect, новый модуль)

2. **Full scan** (перебираем все клоны):
   - Для каждого клона (0..37):
     - Копируем состояние (i, j, S[256]) во временную структуру
     - Вызываем RC4_Process (симулируем PRGA)
     - Расшифровываем payload

   - **Быстрый отсев**: первый байт (opcode ответа) должен быть валидным:
     - 0x00 = MODULE_MISSING
     - 0x01 = MODULE_OK
     - 0x02 = CHEAT_CHECKS_RESULT
     - 0x03 = MEM_CHECKS_RESULT (старая версия, не используется)
     - 0x04 = HASH_RESULT
     - 0x05 = MODULE_FAILED
     - Любое другое значение → пропускаем клон

   - **Structural validation** (проверяем соответствие длины):
     - MODULE_MISSING / MODULE_OK / MODULE_FAILED → payload = 1 байт (только opcode)
     - HASH_RESULT → payload = 21 байт (1 opcode + 20 байт SHA1)
     - CHEAT_CHECKS_RESULT → payload ≥ 7 байт (1 opcode + 2 length + 4 checksum + resultData)
     - Если длина не совпадает → пропускаем клон

3. **Lock in** (если нашли единственного кандидата):
   - Ровно 1 клон прошёл валидацию → это encrypt S-box!
   - Запоминаем индекс: `g_lockedInCloneIndex = i`
   - Логируем: "Locked in to clone #23"
   - Следующие пакеты используют fast path

4. **Failure** (если 0 или >1 кандидатов прошли):
   - 0 кандидатов → "No candidate passed structural validation"
   - >1 кандидатов → "Multiple candidates passed, cannot lock in" (редко, но возможно при коротких пакетах)

## 5. Текущий статус

### Что работает
- ✓ **ScanForRC4States**: находит 38 кандидатов (19 адресов × 2 layout'а)
- ✓ **CloneAllStates**: клонирует 38/38 состояний в WardenPreHandler
- ✓ **Structural validation**: корректно проверяет формат CMSG ответов

### Что НЕ работает
- ✗ **DecryptCmsg**: каждый пакет выдаёт "No candidate passed structural validation"
- ✗ Ни один клон не проходит валидацию
- ✗ Lock in не происходит

### Гипотезы о причинах

#### Гипотеза 1: Timing проблема
**Суть**: к моменту клонирования encrypt S-box уже использовался (состояние изменилось)

**Почему возможно**:
- WardenPreHandler срабатывает **перед** handler'ом, но Warden может работать в отдельном потоке
- Возможно, CMSG формируется и шифруется **раньше**, чем мы думаем
- Или мы клонируем **после** того, как handler уже обработал пакет (return-address hijack срабатывает дважды: pre и post)

**Как проверить**:
- Попробовать клонировать в другой момент (например, на входе в SendPacket)
- Логировать TID (thread ID) в WardenPreHandler и DecryptCmsg — они должны быть разными

#### Гипотеза 2: Layout detection неправильный
**Суть**: мы неправильно определяем, где i, j, S в памяти

**Почему возможно**:
- Мы проверяем 2 layout'а для uint8_t, но возможны другие варианты
- Или i/j хранятся в другом месте (не рядом с S)
- Или формат uint32_t (1024 байта), но мы его пропускаем

**Как проверить**:
- Дампить клоны в файл (i, j, S[0..255]) и визуально проверять
- Проверить, что S действительно перестановка (нет дубликатов)
- Попробовать сканировать только uint32_t layout

#### Гипотеза 3: Encrypt S-box не в списке кандидатов
**Суть**: наш scan пропускает реальный encrypt S-box

**Почему возможно**:
- Ограничение на размер региона (64 MB max) — может быть S-box в большем регионе?
- Или S-box находится в недоступной памяти (PAGE_NOACCESS)
- Или формат совсем другой (не uint8_t/uint32_t, а что-то кастомное)

**Как проверить**:
- Увеличить max region size до 128 MB
- Убрать фильтр PAGE_READONLY (добавить PAGE_READWRITE, PAGE_EXECUTE_*)
- Попробовать искать не полный S-box, а частичный паттерн

#### Гипотеза 4: CMSG payload не зашифрован RC4
**Суть**: может быть, CMSG шифруется другим способом (не RC4 Warden модуля)?

**Почему маловероятно**:
- В SMSG расшифровка точно происходит внутри модуля (мы это видели)
- Логично, что CMSG шифруется тем же модулем
- Но может быть другой ключ или алгоритм?

**Как проверить**:
- Хук на ARC4::Process (session cipher) — проверить, что он НЕ шифрует payload
- Дисассемблировать Warden модуль — найти код, который шифрует CMSG

## 6. Что нужно для исправления

### План отладки (по приоритету)

#### 1. Верификация клонов
**Действие**: дампить клоны в файл при каждом CloneAllStates

```cpp
for (size_t i = 0; i < g_clonedStates.size(); i++) {
    std::ofstream f("warden_cache/clone_" + std::to_string(i) + ".bin", std::ios::binary);
    f.write(&g_clonedStates[i].i, 1);
    f.write(&g_clonedStates[i].j, 1);
    f.write(g_clonedStates[i].S, 256);
}
```

**Проверить**:
- Все ли клоны уникальные? (или дубликаты?)
- S действительно перестановка 0-255?
- i, j в разумных пределах (0-255)?

#### 2. Thread ID логирование
**Действие**: логировать TID в ключевых точках

```cpp
DWORD tid = GetCurrentThreadId();
LOG(INFO) << "WardenPreHandler TID=" << tid;
LOG(INFO) << "DecryptCmsg TID=" << tid;
```

**Проверить**: разные ли потоки? Если да → timing issue.

#### 3. Альтернативная точка клонирования
**Действие**: попробовать клонировать в SendPacket (на входе в хук)

**Логика**: в момент отправки CMSG — encrypt S-box точно уже использован. Но может быть, мы сможем найти decrypt S-box и инициализировать encrypt из того же ключа?

**Проблема**: у нас нет ключа (он в MODULE_INITIALIZE, но мы его не сохраняем).

#### 4. Хук на RC4 cipher внутри модуля
**Альтернативный подход**: найти функцию RC4_Process внутри Warden модуля (через сигнатуру) и захукать её.

**Преимущества**:
- Видим plaintext ДО шифрования (на входе функции)
- Не зависим от timing

**Недостатки**:
- Нужно найти функцию (сигнатура может отличаться в разных модулях)
- Более сложный хук (внутри динамически загруженного blob'а)

#### 5. Расширенное сканирование
**Действие**: убрать ограничения на scan

```cpp
// Было:
if (mbi.RegionSize > 64 * 1024 * 1024) continue;
if (!(mbi.Protect & PAGE_READONLY)) continue;

// Стало:
if (mbi.RegionSize > 128 * 1024 * 1024) continue;
// Убрать фильтр по Protect (искать во всех readable регионах)
```

**Проверить**: появятся ли новые кандидаты?

2. Реализовать пункт 2 (TID логирование) → выяснить timing
3. На основе результатов решить: пункт 3, 4 или 5

## Заключение

RC4 расшифровка CMSG — ключевая задача для полного понимания диалога Warden. Текущая реализация (клонирование S-box'ов) логически верна, но практически не работает. Скорее всего, проблема в timing или layout detection. Требуется дальнейшая отладка с дампами и логированием.

После решения этой проблемы мы сможем:
- Видеть все ответы клиента
- Анализировать, какие хеши отправляются
- Готовить почву для spoofing (подмены ответов)
