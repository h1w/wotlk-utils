Техническое руководство по разработке внутренней логики DLL для WoW 3.3.5a (12340)

Настоящий документ представляет собой архитектурный обзор для системных инженеров и специалистов по реверс-инжинирингу, занимающихся разработкой внедряемых (Internal) модулей для клиента World of Warcraft 3.3.5a. В центре внимания — низкоуровневая манипуляция структурами движка и обеспечение стабильности при прямом вызове процедур.


--------------------------------------------------------------------------------


1. Фундаментальная архитектура и точка входа в цикл игры

Синхронизация кода DLL с основным потоком игры (Main Thread) является критическим требованием. Клиент WoW не проектировался как потокобезопасное приложение. Вызов внутренних функций или итерация по структурам данных из стороннего потока неизбежно приведет к состоянию гонки (Race Condition) и последующему Access Violation.

Для перехвата управления и обеспечения полной синхронизации стратегическим стандартом является хук Direct3DDevice9::EndScene (42-й индекс в таблице виртуальных методов). Поскольку EndScene вызывается в контексте основного потока отрисовки в конце каждого кадра, это дает нам безопасное «окно» для работы с памятью и вызова функций движка.

Анализ «Internal» подхода:

* Нулевые задержки: Прямое разыменование указателей исключает накладные расходы системных вызовов ReadProcessMemory.
* Контекстная интеграция: Возможность прямого использования thiscall методов и передачи сложных структур (например, векторов C3Vector) без маршалинга.
* Атомарность: Гарантированное состояние объектов в момент выполнения кода внутри кадра.

2. Магистраль данных: Проектирование и итерация Object Manager

ClntObjMgr (Object Manager) — это ядро адресного пространства WoW, координирующее состояние всех активных сущностей. Элегантная работа с менеджером требует понимания цепочки указателей, начинающейся с корня клиентского соединения.

Иерархия доступа и навигация: Доступ к менеджеру осуществляется через статический корень StaticClientConnection (0x00C79CE0).

1. Base: uintptr_t s_connection = *(uintptr_t*)0x00C79CE0;
2. Manager: uintptr_t pObjMgr = *(uintptr_t*)(s_connection + 0x2ED0);
3. Head: Первый объект списка находится по смещению 0xAC.
4. Next: Указатель на следующую сущность по смещению 0x3C.

Реализация итератора (C++): При итерации обязательна проверка не только на NULL, но и на выравнивание. WoW использует младший бит указателя как флаг состояния; если (currentObj & 1) != 0, указатель невалиден или заблокирован для изменений.

void IterateObjects() {
    uintptr_t connection = *(uintptr_t*)0x00C79CE0;
    if (!connection) return;

    uintptr_t objMgr = *(uintptr_t*)(connection + 0x2ED0);
    uintptr_t currentObj = *(uintptr_t*)(objMgr + 0xAC);

    while (currentObj != 0 && (currentObj & 1) == 0) {
        // GUID локального игрока: *(uint64_t*)(objMgr + 0xC0)
        
        // Логика обработки объекта...
        
        // Переход к следующему узлу
        currentObj = *(uintptr_t*)(currentObj + 0x3C);
    }
}

3. Классификация сущностей и дескрипторы объектов

WoW использует строгую иерархию наследования, где базой является CGObject_C. Ключевой идентификатор типа (TypeID) расположен по смещению 0x14.

Стратегия идентификации:

* TypeID 3: CGUnit_C (NPC и другие игроки).
* TypeID 4: CGPlayer_C (Локальный игрок).

Важно понимать: CGPlayer_C является наследником CGUnit_C. В то время как обычные юниты предоставляют доступ к базовым дескрипторам (HP, Mana, Auras), объект игрока содержит расширенный блок данных, доступный только для него: прогресс опыта, навыки (Skills), репутация и состояние книги заклинаний. Доступ к этим данным осуществляется через массив дескрипторов, указатель на который хранится внутри структуры объекта.

4. Взаимодействие с игровым миром: Click-to-Move и заклинания

Автоматизация действий требует вызова функций с соблюдением их соглашений о вызовах (calling conventions), иначе крах стека неизбежен.

Прототипы ключевых функций:

1. Click-to-Move (0x727400): Использует соглашение __thiscall. Первый аргумент (в регистре ECX) — указатель на объект локального игрока.
2. Для мониторинга состояния движения следует обращаться к структуре CTM_Struct по адресу 0x715CF0 (через GetClickToMoveStruct). Она содержит целевые координаты и текущий тип взаимодействия (Attack, Loot, Move).
3. CastSpell (0x53BC40):

Прямой вызов этих функций из EndScene позволяет имитировать ввод пользователя, не вызывая подозрений у серверных фильтров, так как аргументы и состояние стека будут идентичны легитимным вызовам.

5. Интеграция с Lua Engine и обработка событий

Lua-движок WoW — это высокоуровневый фасад над C++ логикой. DLL может расширять его, регистрируя собственные функции.

* Исполнение скриптов: FrameScript_Execute (0x819210) позволяет запускать любой Lua-код. Это незаменимо для работы с UI и защищенными функциями интерфейса.
* Регистрация функций: FrameScript_RegisterFunction (0x4181B0) требует строгого соответствия сигнатуре Lua API.

C++ сигнатура для Lua:

typedef int (__cdecl* lua_CFunction)(uintptr_t lua_State);
// Регистрация: FrameScript_RegisterFunction("MyInternalFunc", MyCppFunctionPtr);


Использование SignalEvent (0x615020) позволяет вашей библиотеке подписываться на внутренние события игры. Это создает реактивную архитектуру: вместо постоянного опроса памяти (polling) на предмет приглашения в группу, DLL реагирует на событие PARTY_INVITE_REQUEST в момент его генерации движком.

6. Безопасность и обход механизмов обнаружения (Warden)

Warden — динамически загружаемый античит-модуль. Сервер отправляет зашифрованный (RC4) бинарный модуль через SMSG_WARDEN_DATA (opcode 0x2E6), клиент загружает его через VirtualAlloc (НЕ PE-формат) и выполняет проверки.

Архитектура Warden:

* Модуль: custom binary format (40-byte header, RLE-packed sections, delta-encoded relocs). Загружается в MEM_PRIVATE + PAGE_EXECUTE_READWRITE. Каждый модуль использует **собственные** type IDs для проверок (не совпадают с TC константами).
* Шифрование: payload RC4 шифруется ВНУТРИ модуля (не session cipher ARC4 @ 0x00774EA0). Модуль содержит 1-4 RC4 PRGA функции (main thread + module thread).
* Проверки: CHEAT_CHECKS_REQUEST содержит массив проверок (типы: TIMING, MEM, PAGE, PROC, MODULE, DRIVER, MPQ, LUA). Последний байт пакета — xorByte для деобфускации type bytes.
* Ответы: CMSG_WARDEN_DATA (opcode 0x2E7) = [02][resultLen:2 LE][checksum:4][results:N]. Checksum = SHA1(results) → 5 x uint32_t LE → XOR-fold.

Типы проверок и наши контрмеры:

1. MEM_CHECK (data: unk+addr+readLen=6 bytes): читает N байт по адресу. Обнаруживает inline hooks (JMP-патчи). Контрмера: Shadow Copy — подменяем данные CMSG чистыми байтами из PE mapping Wow.exe с диска.
2. PAGE_CHECK (data: seed+SHA1+addr+readLen=29 bytes): проверяет VirtualQuery атрибуты страницы. Контрмера: force result 0xE9 (pass) для адресов наших хуков.
3. MODULE_CHECK (data: seed+SHA1=24 bytes): перечисляет загруженные модули через PEB.Ldr lists, вычисляет HMAC_SHA1(seed, moduleName). Контрмера: PEB unlinking (Layer 1) + force 0xE9 (Layer 2).
4. LUA_EVAL (data: 1 byte): выполняет Lua-код (строка из string section). Ищет запрещённые аддоны. Контрмера: селективный spoof addon-detection API (GetAddOnInfo, IsAddOnLoaded, etc.) → empty string.
5. DRIVER_CHECK, MPQ_CHECK, PROC_CHECK: pass-through (не нацелены на нашу DLL).

Ключевые адреса (build 12340):

* FrameScript_Execute:       0x00819210 (__cdecl)
* SMSG_WARDEN_DATA handler:  0x007DA850 (нестандартная, naked detour)
* SendPacket:                0x00632B50 (нестандартная, naked detour)
* ARC4::Process:             0x00774EA0 (__thiscall, session cipher)

Правила безопасности:

1. Main Thread: функции движка (CastSpell, etc.) вызывать ТОЛЬКО из main thread. Warden может проверить call stack.
2. Inline hooks: неизбежно модифицируют .text секцию — Shadow Copy скрывает изменения от MEM_CHECK.
3. PEB Unlinking: скрываем DLL из PEB.Ldr ПОСЛЕ всей инициализации, восстанавливаем ПЕРЕД eject.
4. Sanitization: проверяем указатели из Object Manager на NULL и alignment (младший бит = флаг).
5. SEH: `__try/__except` нельзя использовать в функциях с C++ объектами (std::string и пр.) — выносить в отдельные helper-функции.
