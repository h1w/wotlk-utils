# Протокол Warden — Подробное руководство

## 1. Что такое Warden

**Warden** — это античитинговая система, разработанная компанией Blizzard Entertainment для защиты игры World of Warcraft от читеров, ботов и модификаций клиента.

### Принцип работы

Warden работает как **динамически загружаемый модуль**, который сервер отправляет клиенту во время игры. Представьте это как "инспектора", который приходит к вам домой проверить, всё ли в порядке:

1. **Сервер отправляет модуль** — небольшую программу (обычно ~30-100 КБ в сжатом виде)
2. **Клиент загружает модуль** в память процесса WoW.exe
3. **Модуль выполняет проверки** — сканирует память, ищет подозрительные процессы, проверяет целостность файлов
4. **Клиент отправляет результаты** обратно на сервер
5. **Сервер принимает решение** — всё в порядке или забанить игрока

### Важная особенность: уникальные ID типов проверок

Каждый Warden-модуль имеет **свою собственную систему нумерации** типов проверок. Это критически важно понимать!

**Пример:**
- В модуле `7C4ABC97`: проверка LUA имеет ID `0xDB`
- В модуле `DA3BF29E`: проверка LUA имеет ID `0x70`
- В открытых исходниках TrinityCore: LUA имеет ID `0x8B`

**Все три числа описывают ОДИН И ТОТ ЖЕ тип проверки**, но с разными ID! Это сделано специально, чтобы усложнить жизнь читерам — нельзя просто взять константы из TrinityCore и использовать их.

## 2. Опкоды Warden пакетов

Все коммуникации между сервером и клиентом происходят через два типа пакетов:

- **SMSG_WARDEN_DATA (0x2E6)** — сервер → клиент (после расшифровки заголовка)
- **CMSG_WARDEN_DATA (0x2E7)** — клиент → сервер

Внутри этих пакетов находятся **под-опкоды**, которые определяют конкретную команду.

---

### 2.1. MODULE_USE (0x00) — 37 байт

**Назначение:** Сервер говорит клиенту "используй вот этот модуль".

**Формат:**
```
[1 байт]  Опкод = 0x00
[16 байт] MD5 хеш модуля (уникальный идентификатор)
[16 байт] RC4 ключ для шифрования (используется для payload cipher)
[4 байта] Размер сжатого модуля (Little Endian)
```

**Что происходит в клиенте (наша DLL):**
1. Получает MD5 хеш модуля
2. Сбрасывает текущее состояние (если был загружен другой модуль)
3. Пытается загрузить модуль из кеша на диске (файл `warden_dumps/<MD5>.bin`)
4. Если в кеше нет — ждёт пакетов MODULE_CACHE от сервера

**Пример MD5 модулей:**
- `7C4ABC97C34C2E09DF3691DAD06994A6` — самый распространённый модуль
- `DA3BF29E4CEBD2CAA6E4A532AF0C31E9` — альтернативный модуль
- `9A95D199B9453CF758AC80E9D96D9411` — ещё один вариант

---

### 2.2. MODULE_CACHE (0x01) — до 503 байт

**Назначение:** Сервер отправляет кусок (chunk) бинарного модуля.

**Формат:**
```
[1 байт]  Опкод = 0x01
[2 байта] Размер куска (chunk_size, Little Endian)
[N байт]  Данные куска (N = chunk_size)
```

**Особенности:**
- Один модуль может передаваться **30-40 пакетами** подряд
- Максимальный размер одного куска — 500 байт (503 - 3 байта заголовка)
- Куски идут **последовательно**, склеиваются в один большой буфер

**Что происходит в клиенте:**
1. Накапливает данные в буфере `moduleData`
2. Когда получен последний кусок (общий размер совпал с ожидаемым из MODULE_USE) — начинает декомпрессию

**Пример:**
Если модуль имеет сжатый размер 15000 байт, а chunk_size = 500, то придёт:
- 30 пакетов по 500 байт = 15000 байт
- Клиент склеит их и получит полный сжатый модуль

---

### 2.3. MODULE_INITIALIZE (0x03)

**Назначение:** Сервер говорит "теперь запусти модуль".

**Формат:**
```
[1 байт]  Опкод = 0x03
[N байт]  Параметры инициализации (зависят от модуля)
```

**Что происходит в клиенте:**
1. Декомпрессирует модуль (если ещё не декомпрессирован)
2. Выделяет память через `VirtualAlloc` (обычно ~29-30 КБ для декомпрессированного модуля)
3. Загружает модуль в память (применяет релокации, разрешает импорты)
4. Вызывает entry point модуля с параметрами инициализации
5. Модуль готов к работе

---

### 2.4. CHEAT_CHECKS_REQUEST (0x02) — переменная длина

**Назначение:** Сервер говорит "выполни вот эти проверки и пришли результаты".

**Формат:**
```
[1 байт]      Опкод = 0x02
[Section 1]   String section (строки для LUA_EVAL, DRIVER и т.д.)
[1 байт]      Терминатор 0x00 (конец string section)
[Section 2]   Check section (последовательность проверок)
[1 байт]      xorByte (последний байт пакета)
```

#### String Section

Содержит строки, на которые ссылаются проверки через индекс `string_idx`.

**Формат одной строки:**
```
[1 байт]  Длина строки (N)
[N байт]  Строка (БЕЗ нулевого терминатора)
```

**Пример:**
```
05 "lua.dll"
0A "GetVersion"
```

После последней строки идёт **терминатор 0x00** — это признак конца string section.

#### Check Section

Содержит последовательность проверок. Каждая проверка начинается с **зашифрованного байта типа**.

**Формат одной проверки:**
```
[1 байт]  Зашифрованный тип (encryptedType = realType ^ xorByte)
[N байт]  Данные проверки (зависят от типа)
```

Чтобы получить **реальный тип**, нужно:
```cpp
uint8_t realType = encryptedType ^ xorByte;
```

где `xorByte` — последний байт всего пакета CHEAT_CHECKS_REQUEST.

#### xorByte — важно!

- **XORится ТОЛЬКО с байтами типов** (первый байт каждой проверки)
- **Данные проверок НЕ шифруются** (адреса, SHA1 хеши остаются как есть)
- **String section НЕ шифруется**

**Пример пакета:**
```
02                          // Опкод CHEAT_CHECKS_REQUEST
05 6C 75 61 35 31 00        // String: "lua51" + терминатор
A4 01 00 00 00 ...          // Проверка 1: тип=0xA4^xorByte, данные...
C3 19 00 00 00 ...          // Проверка 2: тип=0xC3^xorByte, данные...
5F                          // xorByte = 0x5F
```

Если `xorByte = 0x5F`, то:
- Реальный тип проверки 1: `0xA4 ^ 0x5F = 0xFB`
- Реальный тип проверки 2: `0xC3 ^ 0x5F = 0x9C`

---

### 2.5. HASH_REQUEST (0x05) — 17 байт

**Назначение:** Сервер просит посчитать SHA1 хеш от каких-то данных (обычно для проверки целостности памяти).

**Формат:**
```
[1 байт]  Опкод = 0x05
[16 байт] SHA1 seed (зерно для хеша)
```

**ВАЖНО:** Это **НЕ** MEM_CHECKS_REQUEST! Это частая ошибка. Опкод 0x05 — это именно HASH_REQUEST.

**Что происходит в клиенте:**
1. Берёт 16-байтовый seed
2. Вычисляет SHA1 на основе этого seed (алгоритм внутри модуля)
3. Отправляет результат обратно через CMSG_WARDEN_DATA опкод 0x04

## 3. Типы проверок (Check Types)

Каждый тип проверки имеет:
- **Уникальный ID** (например, `0xDB` для LUA в модуле 7C4ABC97)
- **Фиксированный размер данных** (например, 25 байт для MEM_CHECK)
- **Специфичное поведение**

Вспомните: **ID типов уникальны для каждого модуля**! Ниже приведены примеры для модуля `7C4ABC97`.

---

### 3.1. TIMING (size = 0)

**Что проверяет:** Время выполнения самих проверок.

**Данные в запросе:** НЕТ (0 байт, только зашифрованный байт типа).

**Данные в ответе:** 4 байта (tick count, обычно результат `GetTickCount()`).

**Назначение:** Обнаружение замедления выполнения (антиотладчик). Если проверки выполняются слишком долго — возможно, клиент работает под отладчиком или эмулятором.

**Пример в модуле 7C4ABC97:**
- ID типа: `0x1F`
- В пакете: `0x1F ^ xorByte`
- Размер данных: 0
- Ответ: 4 байта, например `12 34 56 78` (tick count в Little Endian)

**Количество:** Обычно **только одна** проверка TIMING на таблицу типов.

---

### 3.2. MEM_CHECK (size = 6)

**Что проверяет:** Хеш участка памяти процесса WoW.exe.

**Данные в запросе (6 байт):**
```
[1 байт]  unk (неизвестный байт)
[4 байта] Адрес в памяти (Little Endian)
[1 байт]  readLen (длина считываемого участка)
```

**Данные в ответе:** Включено в общий CHEAT_CHECKS_RESULT (обычно 1 байт результата на проверку).

**Назначение:** Проверка, не был ли изменён код или данные игры. Например:
- Хуки на функции (замена первых байтов на `JMP`)
- Патчи памяти (изменение констант, отключение проверок)
- Инъекции кода

**Пример:**
```
Адрес: 0x00819210 (функция FrameScript_Execute)
SHA1 seed: [20 случайных байт]
```

Модуль читает память по адресу `0x00819210`, вычисляет SHA1 от неё с использованием seed, и сравнивает с ожидаемым значением (которое хранится в модуле).

**Что делает наш байпас (Variant A):**
Если MEM_CHECK целится на адрес нашего хука (например, 0x00819210), модуль прочитает JMP-патч вместо оригинального пролога. Наш спуфер (`warden_spoof::SpoofCmsgIfNeeded`) перехватывает CMSG plaintext **перед RC4 шифрованием** через internal RC4 hook и заменяет байты на оригинальные из shadow copy (маппинг Wow.exe с диска). Пересчитывает checksum. Сервер видит чистые байты.

---

### 3.3. PAGE_A и PAGE_B (size = 29)

**Что проверяет:** Хеш страницы памяти (аналогично MEM_CHECK, но с SHA1 seed).

**Данные в запросе (29 байт, одинаковый формат для обоих):**
```
[4 байта]  seed (SHA1 seed)
[20 байт]  SHA1 хеш (ожидаемое значение)
[4 байта]  Адрес в памяти (Little Endian)
[1 байт]   readLen (длина считываемого участка)
```

**Важно:** PAGE_A и PAGE_B имеют **одинаковый формат и размер** (29 байт). Адреса могут быть очень низкими (0x60EC, 0x32B9, даже 0x000000C6).

**Пример для модуля 7C4ABC97:**
- PAGE_A: ID = `0x22`
- PAGE_B: ID = `0x47`

---

### 3.4. PROC (size = 31)

**Что проверяет:** Хеш экспортированной функции из загруженной DLL.

**Данные в запросе (31 байт):**
```
[4 байта]  seed (SHA1 seed)
[20 байт]  SHA1 хеш (ожидаемое значение)
[1 байт]   modIdx (индекс строки с именем DLL, например "kernel32.dll")
[1 байт]   procIdx (индекс строки с именем функции, например "CreateFileA")
[4 байта]  Адрес функции (Little Endian)
[1 байт]   readLen (длина считываемого участка)
```

**Назначение:** Проверка, не были ли захучены системные функции. Например:
- `CreateFileA` захучена читом для перехвата чтения MPQ-архивов
- `VirtualProtect` захучена для обхода античита

**Пример:**
```
string_idx = 0 → строка "kernel32.dll"
Адрес = 0x7C801234 (адрес CreateFileA в kernel32.dll)
```

Модуль проверяет, что код функции `CreateFileA` не изменён.

---

### 3.5. MPQ (size = 1)

**Что проверяет:** Целостность игровых архивов (MPQ-файлов).

**Данные в запросе (1 байт):**
```
[1 байт]  strIdx (индекс строки с именем MPQ-файла, например "World\Maps\...\*.adt")
```

**Назначение:** Обнаружение модификаций игровых файлов:
- Изменённые текстуры (wallhack)
- Модифицированные UI (показ cooldowns, автоматизация)
- Взломанные скрипты Lua

---

### 3.6. MODULE (size = 24)

**Что проверяет:** Наличие подозрительного модуля (DLL) в памяти процесса.

**Данные в запросе (24 байта):**
```
[4 байта]  seed (SHA1 seed)
[20 байт]  SHA1 хеш (ожидаемое значение)
```

**Данные в ответе:** 1 байт (0 = не найден, 1 = найден).

**Назначение:** Поиск известных читерских DLL по имени. Например:
- `speedhack.dll`
- `glider.dll` (бот Glider)
- `innerspace.dll` (фреймворк для ботов)

**Наш байпас:** Можно подделать ответ "не найден" даже если DLL загружена, но лучше вообще не грузить DLL с палевным именем.

**Пример для модуля 7C4ABC97:**
- ID типа: `0xB3`

---

### 3.7. DRIVER (size = 25)

**Что проверяет:** Наличие подозрительного драйвера в системе.

**Данные в запросе (25 байт):**
```
[4 байта]  seed (SHA1 seed)
[20 байт]  SHA1 хеш (ожидаемое значение)
[1 байт]   strIdx (индекс строки с именем драйвера, например "vmmemctl")
```

**Данные в ответе:** 1 байт (0 = не найден, 1 = найден).

**Назначение:** Обнаружение:
- Читерских kernel-mode драйверов (для чтения памяти других процессов)
- Драйверов отладчиков (SoftICE, WinDbg kernel driver)
- Драйверов мониторинга (Speedfan, AIDA64 — могут использоваться ботами)

**Пример для модуля 7C4ABC97:**
- ID типа: `0xD8`

---

### 3.8. LUA (size = 1)

**Что проверяет:** Выполняет Lua-код на клиенте и возвращает результат.

**Данные в запросе (1 байт):**
```
[1 байт] string_idx (Lua-код, например "return GetCVar('scriptErrors')")
```

**Данные в ответе:** Зависит от результата Lua-кода (обычно строка).

**Назначение:**
- Проверка переменных окружения (CVar)
- Обнаружение запрещённых аддонов
- Выполнение произвольного кода для сбора информации

**Опасность:** Сервер может выполнить **любой** Lua-код! Например:
- Собрать список всех аддонов
- Проверить наличие переменных, созданных читами
- Даже удалить файлы (если есть уязвимости в Lua API)

**Наш байпас:** Перехватываем выполнение Lua через хук на `FrameScript_Execute` и можем подделать результат.

**Пример для модуля 7C4ABC97:**
- ID типа: `0xDB`

**Пример для модуля DA3BF29E:**
- ID типа: `0x70` (совершенно другой ID!)

## 4. Формат CMSG_WARDEN_DATA (клиент → сервер)

Клиент отправляет результаты проверок через пакет **CMSG_WARDEN_DATA (опкод 0x2E7)**.

Внутри пакета — под-опкод, который определяет тип ответа.

---

### 4.1. MODULE_MISSING (0x00) — 1 байт

**Назначение:** Клиент говорит "у меня нет этого модуля в кеше".

**Формат:**
```
[1 байт] Опкод = 0x00
```

**Когда отправляется:**
Сразу после получения MODULE_USE, если модуль не найден в кеше.

**Что происходит на сервере:**
Сервер начинает отправлять MODULE_CACHE пакеты.

---

### 4.2. MODULE_OK (0x01) — 1 байт

**Назначение:** Клиент говорит "модуль загружен из кеша, всё готово".

**Формат:**
```
[1 байт] Опкод = 0x01
```

**Когда отправляется:**
Сразу после получения MODULE_USE, если модуль успешно загружен из кеша.

**Что происходит на сервере:**
Сервер пропускает отправку MODULE_CACHE и сразу шлёт MODULE_INITIALIZE.

---

### 4.3. HASH_RESULT (0x04) — 21 байт

**Назначение:** Результат проверки HASH_REQUEST.

**Формат:**
```
[1 байт]  Опкод = 0x04
[20 байт] SHA1 хеш (результат)
```

**Когда отправляется:**
В ответ на SMSG_WARDEN_DATA опкод 0x05 (HASH_REQUEST).

---

### 4.4. CHEAT_CHECKS_RESULT (0x02) — переменная длина

**Назначение:** Результаты выполнения всех проверок из CHEAT_CHECKS_REQUEST.

**Формат:**
```
[1 байт]  Опкод = 0x02
[2 байта] Длина результатов (resultLen, Little Endian)
[4 байта] Контрольная сумма (checksum, Little Endian)
[N байт]  Результаты проверок (N = resultLen)
```

**Общий размер:** `7 + resultLen` байт.

**Структура результатов:**
Зависит от типов проверок. Обычно:
- **TIMING:** 4 байта (tick count)
- **MEM_CHECK / PAGE_A / PAGE_B / PROC / MPQ:** 1 байт (0 = OK, другое значение = fail или хеш не совпал)
- **MODULE / DRIVER:** 1 байт (0 = не найден, 1 = найден)
- **LUA:** Переменная длина (строка — результат Lua-кода)

**Пример:**
Если сервер отправил проверки: [TIMING] [MEM_CHECK] [LUA], то ответ:
```
02                    // Опкод CHEAT_CHECKS_RESULT
09 00                 // resultLen = 9 (4 + 1 + 4, например)
AA BB CC DD           // Checksum
12 34 56 78           // TIMING: tick count
00                    // MEM_CHECK: OK
31 32 33 00           // LUA: строка "123" + null terminator
```

### 4.5. Реальные примеры CMSG (из захваченных данных)

Ниже приведены реальные расшифрованные CMSG пакеты, захваченные с помощью внутреннего RC4 хука.

#### Пример 1: Пустой запрос → базовый ответ (7 байт)
**Запрос:** `[02 00 79]` — CHEAT_CHECKS_REQUEST без проверок
**Ответ:**
```
02 00 00 8C BF 48 95
│  │     │
│  │     └── checksum (4 bytes LE: 0x9548BF8C)
│  └──────── resultLen = 0 (нет результатов)
└─────────── opcode CHEAT_CHECKS_RESULT
```

#### Пример 2: Одна проверка (TIMING) → 12 байт
**Ответ:**
```
02 05 00 90 0D D5 28 01 F8 9E BE 00
│  │     │              │
│  │     │              └── results (5 bytes): flag=0x01, ticks=0x00BE9EF8 ≈ 3.5 часа
│  │     └── checksum
│  └──────── resultLen = 5
└─────────── opcode
```

#### Пример 3: LUA-проверка (`zo=""`) → 17 байт
**Ответ:**
```
02 0A 00 60 07 23 7B 00 08 51 4E 4D 50 5A 59 32 52
│  │     │              │  │  └── "QNMPZY2R" (8 символов)
│  │     │              │  └── strlen = 8
│  │     │              └── result byte = 0x00
│  │     └── checksum
│  └──────── resultLen = 10
└─────────── opcode
```

#### Пример 4: Сложный запрос (13 проверок) → 62 байта
**Запрос содержал:** 3×TIMING, 2×MODULE/DRIVER, 2×MEM_CHECK, 5×PAGE/PROC/MPQ, LUA

**Ответ:**
```
02 37 00 C9 32 03 67 [55 bytes of results]
│  │     │
│  │     └── checksum (0x670332C9)
│  └──────── resultLen = 55
└─────────── opcode
```

## 5. Шифрование

Warden использует **два независимых потока шифрования RC4**. Это критически важно понимать!

---

### 5.1. Session Header Cipher (ARC4::Process)

**Адрес в WoW.exe:** `0x00774EA0`

**Назначение:** Шифрует/расшифровывает **заголовки ВСЕХ пакетов** (не только Warden).

**Формат заголовков:**
- **CMSG (клиент → сервер):** 6 байт = [2 байта размер] [4 байта опкод]
- **SMSG (сервер → клиент):** 4 байта = [2 байта опкод] [2 байта размер]

**Пример:**
Когда клиент отправляет `CMSG_WARDEN_DATA` (опкод `0x2E7`), сначала шифруется заголовок:
```
Plaintext:  [15 00] [E7 02 00 00]  (размер=21, опкод=0x2E7)
Encrypted:  [XX XX] [YY YY YY YY]  (после ARC4::Process)
```

Затем к зашифрованному заголовку добавляется **зашифрованный payload**.

**Важно:** Это **НЕ** Warden cipher! Это общее шифрование для всех пакетов (CMSG_PING, SMSG_UPDATE_OBJECT, и т.д.).

**Наш хук на ARC4::Process:**
- Установлен, но используется только для диагностики
- **НЕ помогает** получить plaintext CMSG_WARDEN_DATA payload (только заголовок)

---

### 5.2. Warden Payload Cipher

**Где находится:** Внутри бинарного кода Warden-модуля.

**Назначение:** Шифрует/расшифровывает **содержимое** пакетов SMSG_WARDEN_DATA и CMSG_WARDEN_DATA.

**Алгоритм:** RC4 (ARC4), но реализация находится в модуле, а не в WoW.exe.

**Ключ:** Передаётся в пакете MODULE_USE (16 байт RC4 key).

**Структура RC4 state:**
```cpp
struct RC4_State {
    uint8_t S[256];  // Permutation table (S-box)
    uint8_t i;       // Index i
    uint8_t j;       // Index j
};
```

**Где хранится S-box:**
В памяти модуля (тип `MEM_PRIVATE`). Обычно **два S-box**:
- Один для расшифровки (SMSG_WARDEN_DATA)
- Один для шифрования (CMSG_WARDEN_DATA)

**Наш метод обхода (warden_rc4.cpp):**
1. **Сканируем память** на наличие RC4 S-box (поиск перестановок 0-255)
2. **Клонируем все найденные S-box** в момент получения SMSG_WARDEN_DATA (ДО того, как модуль расшифрует пакет)
3. **Перебираем клоны** в момент отправки CMSG_WARDEN_DATA — пытаемся расшифровать payload каждым клоном
4. **Проверяем структурную валидность** расшифрованных данных (опкод, размер, формат)
5. **Находим правильный клон** (обычно есть только 1-2 подходящих из 40 кандидатов)

**Почему это работает:**
Модуль шифрует CMSG_WARDEN_DATA **во время** обработки SMSG_WARDEN_DATA (в том же thread). Если мы клонируем S-box ДО начала обработки, то у нас будет "чистый" S-box, который можно использовать для расшифровки.

**Два варианта layout:**
- `[i][j][S[256]]` — сначала i, j, потом S-box
- `[S[256]][i][j]` — сначала S-box, потом i, j

Также поддерживаются uint32_t S-box (1024 байта вместо 256).

**Потокобезопасность:**
Используется `CRITICAL_SECTION`, так как клонирование происходит в main thread (хук на SMSG), а расшифровка — в module thread (хук на SendPacket).

---

### 5.3. Почему два отдельных шифра?

**Причина 1: Безопасность.**
Если взломать session cipher, можно читать ВСЕ пакеты (координаты игроков, инвентарь, и т.д.). Но Warden останется защищённым.

**Причина 2: Динамизм.**
Session cipher инициализируется один раз при логине. Warden cipher меняется каждый раз при загрузке нового модуля (новый ключ из MODULE_USE).

**Причина 3: Изоляция.**
Warden-модуль — это отдельный бинарный блоб, он не должен зависеть от внутренностей WoW.exe. У него своя реализация RC4.

## 6. xorByte — как работает

**xorByte** — это последний байт пакета CHEAT_CHECKS_REQUEST. Он используется для **обфускации типов проверок**.

---

### 6.1. Что шифруется xorByte

**Шифруется:**
- Первый байт каждой проверки (тип проверки)

**НЕ шифруется:**
- String section (все строки остаются plaintext)
- Данные проверок (адреса памяти, SHA1 seed остаются plaintext)
- Терминатор 0x00 (между string и check section)

---

### 6.2. Алгоритм

```cpp
uint8_t xorByte = packet[packet.size() - 1];  // Последний байт пакета

for (каждая проверка в check section) {
    uint8_t encryptedType = packet[offset];
    uint8_t realType = encryptedType ^ xorByte;

    // Теперь используем realType для определения, какая это проверка
}
```

---

### 6.3. Пример

**Пакет:**
```
02                          // Опкод CHEAT_CHECKS_REQUEST
05 6C 75 61 35 31 00        // String: length=5, "lua51", терминатор
C6 01 02 03 04 ...          // Проверка 1: encryptedType=0xC6, данные...
8D 11 22 33 44 ...          // Проверка 2: encryptedType=0x8D, данные...
AA                          // xorByte = 0xAA
```

**Расшифровка:**
- Проверка 1: `realType = 0xC6 ^ 0xAA = 0x6C`
- Проверка 2: `realType = 0x8D ^ 0xAA = 0x27`

Затем смотрим в таблицу типов модуля:
- `0x6C` → например, MODULE (размер данных = 1)
- `0x27` → например, PAGE_A (размер данных = 25)

---

### 6.4. Зачем это нужно?

**Усложнение анализа:**
Без знания xorByte невозможно понять, какие проверки в пакете. Это мешает:
- Простому парсингу (нельзя просто искать известные константы типов)
- Эмуляции (нужно знать реальные типы для корректной обработки)

**Динамизм:**
xorByte меняется для каждого пакета, даже если типы проверок одинаковые.

---

### 6.5. Наш обход

В нашем коде (warden_packet_parser.cpp):
```cpp
uint8_t xorByte = data[size - 1];  // Последний байт

// Парсим check section
while (offset < size - 1) {
    uint8_t encryptedType = data[offset++];
    uint8_t realType = encryptedType ^ xorByte;

    // Ищем realType в таблице dispatcher (из warden_scan.cpp)
    CheckTypeInfo info = checkTypeTable[realType];

    // Читаем данные проверки (info.size байт)
    ReadCheckData(data, offset, info.size);
}
```

## 7. Формат Warden-модуля (бинарный)

Warden-модуль — это **НЕ стандартный PE-файл** (DLL/EXE). Это кастомный формат Blizzard.

**Структура:**
```
[40 байт]      Заголовок (header)
[N * 12 байт]  Дескрипторы секций (section descriptors)
[M байт]       Упакованные данные (RLE-compressed)
```

**Заголовок (40 байт):**
```cpp
struct WardenModuleHeader {
    uint32_t moduleSize;          // [0x00] Размер модуля в памяти
    uint32_t unknown1;            // [0x04]
    uint32_t relocOffset;         // [0x08] Смещение таблицы релокаций
    uint32_t relocCount;          // [0x0C] Количество релокаций
    uint32_t exportTableOffset;   // [0x10] Смещение таблицы экспортов
    uint32_t exportCount;         // [0x14] Количество экспортов
    uint32_t baseIndex;           // [0x18] Базовый индекс
    uint32_t importTableOffset;   // [0x1C] Смещение таблицы импортов
    uint32_t importLibCount;      // [0x20] Количество импортируемых библиотек
    uint32_t sectionDescCount;    // [0x24] Количество дескрипторов секций
};
```

**Дескриптор секции (12 байт):**
```cpp
struct SectionDesc {
    uint32_t virtualOffset;   // Смещение в памяти (после загрузки)
    uint32_t virtualSize;     // Размер в памяти
    uint32_t flags;           // Флаги (права доступа)
};
```

**Релокации:**
- Хранятся в дельта-кодировании (каждая релокация = предыдущая + дельта)
- Применяются после загрузки модуля в память

**Импорты:**
- Ссылки на функции WoW.exe и системных DLL
- Разрешаются через таблицу экспортов WoW.exe

**Стабильная сигнатура (memcpy-like функция):**
```
56 57 FC 8B 54 24 14 8B 74 24 10 8B 44 24 0C 8B CA 8B F8 C1 E9 02 74 02 F3 A5
```
Присутствует во всех модулях. Используется для поиска модуля в памяти.

## 8. Dispatcher (таблица типов проверок)

Каждый модуль содержит **dispatcher** — код, который парсит пакет CHEAT_CHECKS_REQUEST и вызывает нужные handler'ы.

**Две формы dispatcher:**

### 8.1. Request Parser (dispatch chain)

**Паттерн:**
```asm
xor r8, [reg+4]     ; r8 = encryptedType ^ xorByte
movzx eax, al       ; eax = realType (младший байт)
sub eax, 0x??       ; Вычитание базового индекса
dec eax             ; Декремент
cmp eax, 0x??       ; Сравнение с максимальным индексом
je/jne handler_??   ; Переход на handler
```

**Якорь (anchor byte):** `32 [40-7F] 04` = `xor r8, [reg+4]`

Эта форма позволяет **извлечь реальные ID типов** из кода модуля.

**Наш метод (warden_scan.cpp):**
1. Ищем anchor byte `32 ?? 04`
2. Проверяем, что следом идёт `0F B6 C0` (movzx eax, al)
3. Парсим цепочку sub/dec/cmp
4. Извлекаем realType ID из инструкций

**Успешность:** 8 из 10 протестированных модулей имеют dispatch chain.

---

### 8.2. Response Builder (remap table)

**Паттерн:**
```asm
xor r8, [reg+4]         ; r8 = encryptedType ^ xorByte
movzx eax, al           ; eax = realType
movzx eax, byte [remap_table + eax]  ; Remapping
jmp [jump_table + eax*4]             ; Переход
```

**Таблица remap:** 256 байт, преобразует realType в индекс handler'а.

**Проблема:** Таблица содержит 200+ записей (много мусора). **БЕСПОЛЕЗНА** для извлечения типов.

**Успешность:** Все 10 модулей имеют remap table, но она не помогает.

---

### 8.3. Fallback методы

Если dispatch chain не найден:

**Cmp-cluster scan:**
Ищем скопления инструкций `cmp al, 0x??` в коде модуля.

**Sub-chain scan:**
Ищем последовательности `sub al, 0x??` + `cmp al, 0x??`.

**Успешность:** Низкая, много ложных срабатываний.

## 9. Временная линия работы Warden

**Фаза 1: Загрузка модуля**
1. Сервер → Клиент: `SMSG_WARDEN_DATA` опкод `0x00` (MODULE_USE)
2. Клиент → Сервер: `CMSG_WARDEN_DATA` опкод `0x00` (MODULE_MISSING) или `0x01` (MODULE_OK)
3. Если MODULE_MISSING:
   - Сервер → Клиент: 30-40 пакетов `SMSG_WARDEN_DATA` опкод `0x01` (MODULE_CACHE)
4. Сервер → Клиент: `SMSG_WARDEN_DATA` опкод `0x03` (MODULE_INITIALIZE)
5. Клиент: Декомпрессирует, загружает, инициализирует модуль

**Фаза 2: Проверки**
6. Сервер → Клиент: `SMSG_WARDEN_DATA` опкод `0x02` (CHEAT_CHECKS_REQUEST)
7. Клиент: Выполняет проверки (MEM, LUA, DRIVER, и т.д.)
8. Клиент → Сервер: `CMSG_WARDEN_DATA` опкод `0x02` (CHEAT_CHECKS_RESULT)

**Фаза 3: Хеш-проверки** (периодически)
9. Сервер → Клиент: `SMSG_WARDEN_DATA` опкод `0x05` (HASH_REQUEST)
10. Клиент → Сервер: `CMSG_WARDEN_DATA` опкод `0x04` (HASH_RESULT)

**Фаза 2 и 3 повторяются** каждые 15-60 секунд (рандомный интервал).

## 10. Наш обход (краткий обзор)

**Хук на SMSG_WARDEN_DATA (0x007DA850):**
- Использует return-address hijack (pre-handler + post-handler)
- Pre-handler: Клонирует RC4 S-box
- Post-handler: Читает расшифрованный пакет, парсит, логирует

**Хук на SendPacket (0x00632B50):**
- Перехватывает CMSG_WARDEN_DATA
- Пытается расшифровать payload с помощью клонированных S-box
- Логирует расшифрованные ответы (MODULE_OK, CHEAT_CHECKS_RESULT, и т.д.)

**Хук на FrameScript_Execute (0x00819210):**
- Перехватывает выполнение Lua-кода
- Можно подделать результаты LUA проверок

**Module dumping:**
- Сохраняет декомпрессированный модуль на диск (`warden_dumps/<MD5>.bin`)
- При повторном подключении загружает из кеша (экономит трафик)

**Dispatcher extraction (warden_scan.cpp):**
- XOR-anchored scan: ищет `xor r8, [reg+4]` паттерн
- Парсит dispatch chain для извлечения realType ID
- Строит таблицу CheckTypeInfo (ID → размер данных)

**RC4 cloning (warden_rc4.cpp):**
- Сканирует MEM_PRIVATE и MEM_IMAGE память
- Ищет перестановки 0-255 (RC4 S-box)
- Клонирует все кандидаты (обычно 40 штук)
- Перебирает клоны для расшифровки CMSG

## 13. Заключение

**Warden** — это мощная, но обратимая система. Основные сложности:

1. **Шифрование:** Два уровня RC4 (session + payload)
2. **Динамизм:** Модули меняются, типы проверок уникальны для каждого модуля
3. **Обфускация:** xorByte, кастомный формат модуля, отсутствие символов отладки

**Наши методы обхода:**

1. **Return-address hijack** для чтения расшифрованных SMSG
2. **Internal RC4 multi-hook** (PRIMARY) для прямого захвата CMSG plaintext (warden_rc4_hook.cpp)
   - До 4 одновременных хуков на RC4 PRGA функции внутри модуля
   - 6 поддерживаемых calling conventions (auto-detection)
3. **RC4 S-box cloning** (FALLBACK) для расшифровки CMSG (warden_rc4.cpp)
4. **XOR-anchored scan** для извлечения таблицы типов
5. **Module dumping** для офлайн-анализа

**Выполнено:**

- Парсинг результатов CHEAT_CHECKS_RESULT (per-check response format) — РЕШЕНО
- Checksum algorithm: SHA1(results) -> XOR-fold -> uint32_t — РЕШЕНО
- MEM_CHECK / PAGE_CHECK spoofing (Variant A): подмена plaintext CMSG перед RC4 encrypt — РЕАЛИЗОВАНО
- Request-response корреляция через FIFO queue — РАБОТАЕТ

**Следующие шаги:**

- Обход LUA проверок (подмена результатов в CMSG)
- Антиопределение DLL (MODULE_CHECK evasion)
- Боевой тест MEM_CHECK spoofing (дождаться проверки на hook-адрес)
