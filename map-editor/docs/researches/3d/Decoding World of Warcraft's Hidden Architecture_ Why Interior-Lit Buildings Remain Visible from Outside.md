# Decoding World of Warcraft's Hidden Architecture: Why Interior-Lit Buildings Remain Visible from Outside

## The Paradox of Interior-Flagged Groups in Exterior Views

The central challenge in developing a visually accurate map editor for World of Warcraft version 3.3.5a stems from a significant discrepancy between the data used to define World of Warcraft Objects (WMOs) and their actual rendering behavior within the game client. Specifically, numerous structures within major cities like Stormwind—such as individual shops and residential houses—are composed of WMO groups that are explicitly flagged with the `MOGP_INTERIOR` (0x2000) designation [[4](ftp://ftp.cs.princeton.edu/pub/cs226/autocomplete/words-333333.txt), [5](https://www.cs.cmu.edu/~roni/11661/2017_fall_assignments/hw3_stats_google_1gram.txt)]. According to conventional interpretation, this flag should signify that the group represents an enclosed, indoor environment intended to be rendered only when the player character is physically inside the structure. However, in-game observations from an external, bird's-eye perspective clearly show these same buildings as fully formed parts of the cityscape, complete with facades and ground-level interiors visible through open doorways. This creates a paradox where the logical implication of the data flag contradicts the final graphical output.

This research report aims to resolve this paradox by conducting a deep analysis of the underlying systems that govern WMO group visibility. The investigation focuses on the interplay between three key components: the static MOGP flags associated with each WMO group, the dynamic portal structures that define spatial connectivity between groups, and the potential runtime logic employed by the client to make visibility decisions. The ultimate goal is not to achieve pixel-perfect replication of the client's rendering engine but to develop a robust and visually acceptable approximation suitable for a custom 3D map editor designed for navmesh and pathfinding visualization. Understanding why these interior-lit groups remain visible from outside is critical for creating an editor that accurately represents the traversable world without the distracting visual artifacts caused by incorrect culling. The scope of this analysis is confined to the provided context and available information regarding the mechanics of WMO rendering in World of Warcraft 3.3.5a.

The problem manifests acutely when attempting to create a simplified bird's-eye view. A naive approach would be to hide all WMO groups that do not possess the `MOGP_EXTERIOR` flag. However, applying this logic directly would lead to the erroneous conclusion that the entire building should be hidden, as its constituent parts are marked as interior. This would result in a map editor output where large sections of the city appear as empty lots, completely obscuring the very structures whose geometry is essential for pathfinding and navigation mesh generation. This outcome is functionally incorrect and visually unacceptable for the intended use case. Therefore, the core of the research must be to understand the true nature of the `MOGP_INTERIOR` flag and uncover the mechanisms that allow these groups to be rendered from an external viewpoint.

The user's current implementation attempts to address this by using a vertex shader-based technique to selectively discard fragments based on surface orientation [[4](ftp://ftp.cs.princeton.edu/pub/cs226/autocomplete/words-333333.txt), [5](https://www.cs.cmu.edu/~roni/11661/2017_fall_assignments/hw3_stats_google_1gram.txt)]. By baking a special value into the vertex normal for non-exterior groups, the pixel shader can identify and discard nearly vertical surfaces, which correspond to walls, while leaving horizontal ones, such as rooftops, intact. While conceptually sound for perfectly vertical geometry, this method fails when applied to the angled walls of many building facades, which pass through the filter and create the very artifacts the system was designed to eliminate. This limitation highlights a fundamental flaw in the approach: it operates at the level of individual faces without first correctly identifying which entire WMO groups should even be considered for rendering from a given camera perspective. The problem is not one of fragment filtering but of group selection.

To solve this, we must look beyond the simple binary classification of a single flag. The evidence strongly suggests that the relationship between a WMO group's flags and its visibility is more complex than a straightforward rule. It is plausible that the `MOGP_INTERIOR` flag does not exclusively denote an "indoor" space but rather describes a specific rendering mode or lighting model. Many modern games utilize different lighting setups for different types of geometry to enhance visual fidelity. An interior lighting model might provide more dramatic shading, cast sharper shadows, or use different ambient light sources compared to the standard outdoor model. A building facade could legitimately use this model to create a sense of depth and realism, making the `INTERIOR` flag a descriptor of its material properties and appearance rather than its geometric enclosure status. This hypothesis provides a direct explanation for the observed phenomenon: the building is part of the exterior world, but its materials are shaded using an interior-lighting algorithm.

Further complicating the issue is the possibility of multiple flags being set on a single group. A WMO group could logically possess both the `MOGP_EXTERIOR` and `MOGP_INTERIOR` flags simultaneously. In this scenario, the group would be considered part of the outdoor world for spatial containment purposes (allowing it to be rendered from outside) while also being assigned a specific rendering pipeline that uses interior lighting calculations. If TrinityCore's vmap data extraction process simplifies this multi-flag state into a single value, it may incorrectly default to `MOGP_INTERIOR` if it is present, thereby losing the crucial `EXTERIOR` context. This would explain why the custom editor, relying on this simplified data, fails to render the buildings correctly. The resolution of this question hinges on verifying the raw data within the original MPQ archives against the extracted vmap data.

Beyond flag interpretation, the portal structures (MOPT/MOPR) play a crucial role in defining how spaces connect and interact. Portals act as virtual doorways, windows, or openings between adjacent WMO groups [[3](https://www.researchgate.net/publication/299677914_Prospective_and_planning_strategy_for_the_northern-most_coral_reef_of_the_Eastern_Pacific_Cabo_Pulmo_Gulf_of_California)]. When a camera is inside a WMO, the client performs a portal culling traversal, starting from the group containing the camera and recursively visiting all connected groups that are reachable through visible portals. This process ensures that only the logically accessible portions of a complex are rendered, providing a significant performance optimization. However, the behavior of this system when the camera is located *outside* the WMO volume is less clear and represents a key area of investigation. The initial assumption is that the client simply renders all exterior groups and hides all others. Yet, the visibility of shop interiors from outside suggests a more sophisticated mechanism. It is possible that the client performs a reverse traversal from the exterior, considering any group connected via a portal as a "facade element" that should be rendered as part of the main landscape. The size, orientation, and visibility of the connecting portal relative to the camera might then determine whether the interior group is fully rendered, partially rendered, or culled entirely. This hybrid approach would elegantly explain why open storefronts are visible while deeper, enclosed rooms within the same building are not.

Ultimately, the solution for the custom map editor lies in understanding that the client's rendering logic is a multi-stage process. First, it determines the camera's location relative to the WMO's overall bounding volume. Second, it consults the portal graph and potentially other baked data to classify the WMO as either "exterior," "interior," or a complex mixture. Third, it applies specialized rendering rules based on this classification and the camera's position. For a navmesh editor, replicating the exact client-side logic is unnecessary and overly complex. A pragmatic and effective solution is to recognize that for city environments viewed from above, the goal is to represent the full silhouette and footprint of all buildings. Therefore, a toggle in the editor to switch to a "city view" mode, which renders all WMO groups regardless of their interior/exterior flags, would be the most direct and reliable way to achieve a functionally correct and visually acceptable representation for pathfinding purposes. This approach prioritizes the utility of the editor over strict adherence to the client's complex rendering hierarchy.

## Deconstructing MOGP Flags and Their Implications for Rendering

The primary suspect in the mystery of why certain WMO groups are visible from an external viewpoint lies within their metadata, specifically the flags defined in the MOGP section of the WMO file format. These flags serve as instructions to the rendering engine, dictating how a particular group of geometry should be treated. The user has correctly identified two of the most relevant flags: `MOGP_EXTERIOR` (0x8) and `MOGP_INTERIOR` (0x2000). However, a deeper deconstruction reveals that their names can be misleading and that their interaction, along with other potential flags, creates a more nuanced picture than a simple binary classification allows. Understanding the precise meaning and intended use of these flags is fundamental to resolving the visibility paradox.

The `MOGP_EXTERIOR` flag (0x8) is the most straightforward. When set on a WMO group, it signals to the client that this collection of geometry is part of the outdoor world. In the context of portal-based rendering, exterior groups typically form the outer boundary of a WMO complex and are the starting point for visibility calculations when the camera is outside. Logically, any camera position falling outside the aggregate bounding box of a WMO would begin its rendering process by including all exterior groups. This forms the baseline for visibility; without this flag, a group would almost certainly be culled from an exterior view. The presence of this flag on some parts of a building, such as the upper floors or the roof, makes perfect sense and aligns with expectations.

The `MOGP_INTERIOR` flag (0x2000), however, is the source of the central conflict. Its name strongly implies an enclosed, indoor space, suggesting it should be hidden from an external camera. The observation of visible shop fronts in Stormwind, which bear this flag, directly challenges this interpretation. A critical insight is that the flag's name may be a historical artifact or a misnomer for its actual purpose. It is highly probable that `MOGP_INTERIOR` stands for "Interior-Lit" rather than "Indoors." In modern game development, visual fidelity is paramount, and developers often employ different lighting models for different types of scenes. An "interior lighting model" might involve lower overall brightness, different ambient occlusion settings, unique directional light sources, or enhanced shadow detail to make surfaces appear more solid and three-dimensional. A building's facade, especially one with intricate details like stone carvings or wooden paneling, can benefit immensely from such a lighting setup to avoid looking flat or washed out under direct sunlight. Therefore, a ground-floor shop front could be designated as `MOGP_INTERIOR` to apply this richer, more detailed lighting model, even though the structure is fully exposed to the outside world. This interpretation neatly resolves the paradox: the group is not "inside" in a spatial sense, but its appearance is governed by an "interior" rendering pipeline.

This leads to the most plausible explanation for the discrepancy: a WMO group can have multiple flags set simultaneously. It is entirely feasible for a single group, particularly one representing a ground-floor commercial building, to be flagged with both `MOGP_EXTERIOR` and `MOGP_INTERIOR`. In this dual-flagged state, the group is recognized by the client as part of the outdoor world (`EXTERIOR`), ensuring it is rendered from an external viewpoint, while also being routed through a specific shader or lighting pass designed for interior scenes (`INTERIOR`). This combination allows for maximum visual flexibility. The problem arises when data extraction tools, like those used by the TrinityCore project to generate vmaps, simplify this complex state. If the extractor script is written to check for the presence of `MOGP_INTERIOR` and, upon finding it, assign a "non-exterior" status to the group without also checking for the presence of `MOGP_EXTERIOR`, it will produce flawed data. The resulting vmap collision data would indicate that the building should be hidden, leading directly to the visual artifacts seen in the custom map editor. To validate this hypothesis, a direct inspection of the raw WMO files from the original game archives is necessary. Using a hex editor or a specialized WMO parser, one can examine the actual flag values for a sample of problematic buildings in Stormwind. If the flags read `EXTERIOR | INTERIOR`, it confirms that the vmap data is incomplete or misinterpreted, and the solution lies in modifying the extraction tool.

Other flags mentioned in the context, such as `MOGP_SHOW_SKYBOX` (0x4), further illustrate the complexity of WMO rendering. A group with this flag set is responsible for rendering the skybox texture, which typically occurs at the very edge of a zone or inside a large, open-air arena. This flag is almost always found on exterior groups. The absence of this flag might suggest that a group is intended to block the sky, reinforcing its status as an enclosed or semi-enclosed space. However, in a dense urban environment, even exterior-facing facades might be coded to not show the sky to maintain a consistent cityscape view. The interplay between these flags creates a rich set of attributes that describe a group's role, not just its spatial containment. Relying on a single flag to make a definitive visibility decision is inherently flawed.

The following table summarizes the likely meanings and implications of these flags based on the analysis:

| Flag Name | Hex Value | Likely Meaning | Implication for External View |
| :--- | :--- | :--- | :--- |
| `MOGP_EXTERIOR` | 0x8 | Part of the outdoor world; forms the boundary of a WMO complex. | Group is eligible for rendering from an external viewpoint. |
| `MOGP_INTERIOR` | 0x2000 | Uses an "interior lighting model" for enhanced visual detail/shading. | Does NOT necessarily mean the group is "inside"; can be used on exterior facades. |
| `MOGP_SHOW_SKYBOX` | 0x4 | Responsible for rendering the skybox texture. | Typically set on exterior groups at the edge of a zone. |

In conclusion, the `MOGP_INTERIOR` flag is not a reliable indicator of spatial containment. Its true function appears to be related to the rendering pipeline, specifically the choice of lighting model. The visibility of these groups from an external view is therefore not a bug or an exception to the rules, but rather a feature enabled by the use of multiple, complementary flags. For the custom map editor, this means that a simple filter based on the `MOGP_INTERIOR` flag is insufficient. The ideal solution involves validating the raw flag data and adjusting the editor's logic to treat groups with `MOGP_INTERIOR` as renderable from an exterior view, unless there is strong evidence of another flag or a structural rule that dictates otherwise. For a navmesh editor, the safest and most practical approach is to assume that any WMO group belonging to a city or town WMO should be considered for rendering in a bird's-eye view, effectively bypassing the unreliable `INTERIOR` flag check altogether.

## The Role of Portal Structures (MOPT/MOPR) in Spatial Connectivity

While MOGP flags provide metadata about a group's properties, the portal structures defined in the root WMO file—specifically the MOPT (portal definition) and MOPR (portal reference) tables—are the fundamental components that dictate spatial connectivity and govern the visibility of interior spaces. Portals are essentially polygons that act as doorways, windows, or other openings between two adjacent WMO groups. They form a graph where nodes are WMO groups and edges are the portals connecting them. The World of Warcraft client leverages this graph to perform efficient visibility culling, a process that determines which parts of a complex can be seen from the camera's current location. Understanding how this portal graph is used, particularly from an external viewpoint, is essential to solving the visibility paradox.

When a player enters a building, the client initiates a portal culling traversal. It begins with the WMO group that contains the camera and checks every portal in that group's MOPR table to see if it is visible from the camera's perspective. This is done by clipping the portal polygon against the view frustum. Any portal that passes this test is considered an opening to another space. The client then recursively repeats this process for the new group that the portal leads to, continuing until no more visible portals can be found. This recursive traversal builds a list of all groups that are "reachable" from the player's current viewpoint through a chain of open doorways and windows. Only the geometry within these reachable groups is sent to the graphics card for rendering. This system is computationally far cheaper than rendering the entire contents of a large, interconnected WMO complex and is a cornerstone of real-time 3D engine performance.

However, the behavior of this system changes dramatically when the camera is located *outside* the bounding volume of the WMO complex. The user's initial assumption—that the client simply renders all exterior groups and hides everything else—is a reasonable first-order approximation. This would be the simplest and fastest way to handle exterior views. Under this model, the client would first check if the camera is inside the aggregate bounding box of the WMO. If the camera is outside, it would skip the complex portal traversal process and render all groups marked with the `MOGP_EXTERIOR` flag. All other groups, including those with the `MOGP_INTERIOR` flag, would be culled entirely. This model explains why, when looking at the side of a building, you see the exterior wall but not the interior rooms behind it. However, this model fails to explain the visibility of open storefronts and other ground-level interiors from an external view.

A more sophisticated and likely scenario involves a modified portal culling algorithm for exterior viewpoints. Instead of performing a full recursive traversal from an interior point, the client might perform a "forward" or "facade-aware" traversal from the exterior. In this model, the client identifies the set of exterior groups as the starting point. It would then examine the portals on these groups that face outward. If a portal is large, unobstructed, and oriented favorably towards the camera (e.g., a wide-open doorway or a large window), the client might decide to "peek" through it. This decision could be based on a simple calculation, such as the portal's projected area on the screen or its angular size. If the portal meets a certain threshold, the client would add the group on the other side of the portal to the list of groups to be rendered. This would explain why the interiors of shops in Stormwind are visible: they are connected to the main exterior city group via a portal (the shop's doorway), and the client's logic determines that this portal is "visible enough" to warrant rendering the connected interior group. This hybrid approach combines the speed of a simple exterior/hide-all model with the visual richness of selective portal peering.

The portal graph also provides valuable information for approximating this behavior in a custom editor. The user has already performed a breadth-first search (BFS) from exterior groups, calculating a distance for each group. This distance represents the minimum number of portals one must traverse to get from an exterior group to that group. A distance of 0 means the group is itself an exterior group. A distance of 1 means the group is directly connected to an exterior group by a single portal. A distance of 2 means it is two portals away, and so on. This BFS distance map is incredibly useful. In the hypothetical "facade-aware" rendering model, the client might have a hard-coded threshold. For example, it might render all groups with a distance <= 1 from the exterior. This would include the immediate exterior shell of the city and any ground-floor shops connected to it. Groups with a distance of 2 or more, representing second-story balconies or rooms deep inside a building, would be culled. This would perfectly match the in-game experience: you see the storefronts but not the back rooms or upper floors of the buildings.

The relationship between the root WMO's MOPT/MOPR structures and the final rendering decision is therefore indirect but profound. The MOPT table contains the raw geometry of the portals—their vertices transformed into world space. The MOPR tables in each sub-group link back to the indices of these portal geometries in the MOPT table and specify which other group the portal connects to. It is this graph structure that enables the culling algorithms. The visibility decision is not made by looking at a single portal but by analyzing the entire graph and the camera's position relative to it. The client likely performs a series of tests: first, a simple bounding box test to determine if the camera is outside. If it is, it doesn't need to traverse the whole graph. Instead, it can use the pre-calculated BFS distances to quickly identify which groups are "near the surface" and thus potentially visible. The presence of a portal is the trigger, but its characteristics (size, orientation) and its position in the graph (its distance from the exterior) are the factors that ultimately determine if the connected group gets rendered.

For the custom map editor, this analysis points toward a more intelligent culling strategy. Instead of the current shader-based fragment discarding, which is imprecise and computationally expensive, the editor could implement a similar distance-based culling. It could calculate the BFS distance from the exterior for every WMO group. Then, when in a bird's-eye view, it could define a "view distance" threshold. Any group whose BFS distance is greater than this threshold could be culled from rendering. By setting this threshold to a low value, such as 1, the editor would render the main exterior facade of buildings and the ground-level interiors connected to them, while hiding the rest. This would mimic the likely behavior of the client and would be a much more robust and accurate solution than the current method. It leverages the structural information inherent in the portal graph to make a principled decision about visibility, rather than trying to infer it from the imperfect `MOGP_INTERIOR` flag alone.

## Runtime Visibility Logic: Camera Position and Special-Case Rendering

Beyond the static flags and the structural connectivity defined by portals, the World of Warcraft client undoubtedly employs a layer of sophisticated runtime logic to make final visibility decisions. This logic acts as a mediator, interpreting the data and applying rules based on the camera's state and the architectural context of the scene. The user's questions touch upon several key aspects of this logic, including how the client determines if the camera is "inside" or "outside," and whether special-case rendering rules exist for certain types of interiors. Understanding this runtime behavior is crucial for developing a realistic approximation for a map editor.

The first step in the client's visibility algorithm is almost certainly a simple spatial test to determine the camera's relationship to the WMO complex. The most efficient method for this is a bounding box test. The client would calculate the aggregate axis-aligned bounding box (AABB) for all the geometry within a single WMO file. When rendering a frame, it takes the camera's position and checks if it falls within this AABB. If the camera is inside the box, the client assumes it is inside the WMO and initiates the standard portal culling traversal described previously. If the camera is outside the box, it assumes it is in the general outdoor world and switches to an exterior rendering mode. This binary "inside/outside" test is fast and sufficient for the vast majority of cases. It does not require a complex ray-casting or polygon intersection test for every frame, which would be prohibitively expensive. This simple test explains why the rendering mode changes so abruptly when entering a building: the moment the camera's position crosses the threshold of the WMO's bounding box, the client flips a switch from exterior rendering to interior portal culling.

However, this simple test does not fully explain the visibility of shop interiors from an external viewpoint. If the camera is definitively outside the WMO's bounding box, the client cannot perform a full portal traversal because it has no "starting group" inside the complex. The visibility of these interiors suggests that the client's logic extends beyond this basic test. There are two primary hypotheses for this behavior. The first is an extension of the portal culling idea: a "reverse" or "exterior peering" algorithm. As discussed, the client could start with the exterior groups and, for each portal on their boundary, perform a quick test to see if the portal is facing the camera and is sufficiently large. If so, it "opens" the portal and adds the connected group to the render list. This would be a lightweight, forward-looking culling step that runs in parallel with the main exterior rendering pass. The second hypothesis is that the client has built-in special-case rendering rules for specific architectural configurations. For instance, the ground-floor shops in Stormwind are not truly "inside" the walled city; they are integrated elements of the city wall's facade. The client's code might contain a list of known exceptions—certain WMOs or certain group types that are treated as part of the landscape even when they have interior flags. This could be a performance optimization, baking in knowledge about common city layouts to avoid complex per-frame calculations.

Another possibility is that the developers included pre-computed visibility data directly within the WMO files. Instead of calculating visibility at runtime for every possible camera angle, they might have generated a set of visibility maps or lists for common viewpoints, such as the minimap or the bird's-eye map view. For example, for Stormwind, the designers might have manually specified that a certain set of ground-floor groups should always be visible from an external perspective. This baked data would override the default flag-based rules, providing perfect results for those specific cases at the cost of increased disk space and manual authoring effort. This is a common practice in AAA game development for optimizing performance-critical paths.

Regardless of the exact implementation, the existence of this runtime logic is confirmed by the user's observation. The client is not merely reading a flag and making a decision; it is performing a sequence of checks and applying contextual rules. For the custom map editor, replicating this exact logic is not feasible or necessary. However, acknowledging its existence allows for a more pragmatic approach. The editor does not need to simulate the client's internal state machine. Instead, it can adopt a simpler, more predictable rule that approximates the desired outcome for its specific use case. Since the goal is a usable navmesh and pathfinding visualization, the priority is to show the full footprint and silhouette of buildings, not to replicate the client's exact visual effects.

Therefore, the most effective strategy is to introduce a dedicated "City View" or "Navigation Mode" in the editor. In this mode, the editor would ignore the `MOGP_INTERIOR` flag and render all WMO groups that belong to the currently loaded zone. This would immediately solve the problem of missing buildings, presenting a clean, accurate outline of the urban environment. This approach is functionally superior for pathfinding, as it ensures that all potential obstacles and walkable surfaces are represented. The visual artifacts of tall, isolated walls are irrelevant in this context, as the focus is on the spatial relationships for navigation, not on photorealistic rendering. This solution is robust, easy to implement, and directly addresses the core requirement of the project. It sidesteps the complexities of flag interpretation and runtime logic by choosing a simpler, more comprehensive rendering strategy that is better suited to the editor's purpose.

## A Practical Solution for Custom Map Editors

Based on the comprehensive analysis of MOGP flags, portal structures, and likely runtime logic, a clear and actionable solution emerges for the user's custom map editor. The primary objective is not to achieve pixel-perfect fidelity with the World of Warcraft 3.3.5a client but to produce a visually acceptable and functionally correct representation of the game world for the purpose of navmesh and pathfinding visualization. The core problem—interior-lit building facades appearing as unwanted artifacts from an external view—is rooted in a misunderstanding of the `MOGP_INTERIOR` flag and the client's sophisticated visibility algorithms. The optimal solution is not to attempt to reverse-engineer the client's complex logic, but to adopt a pragmatic approach tailored to the editor's specific needs.

The most direct and effective solution is to implement a dedicated rendering mode within the editor, tentatively named "City View" or "Navigation Mode." In this mode, the editor would be configured to render all WMO groups within the loaded zone, irrespective of their `MOGP` flags. This approach completely bypasses the ambiguity of the `MOGP_INTERIOR` flag, which is now understood to likely refer to a "lighting model" rather than spatial containment. By rendering all groups, the editor would instantly resolve the visual artifacts, displaying the complete and accurate silhouettes of buildings like those in Stormwind. This is functionally correct for pathfinding, as it ensures that all physical obstacles and traversable volumes are represented in the bird's-eye view. The visual clutter of seeing interior walls from outside becomes a non-issue when the primary goal is spatial accuracy for navigation, not aesthetic perfection. This solution is robust, easy to implement, and directly serves the user's stated goal.

For users who still wish to experiment with a more nuanced, client-like approximation, a secondary solution involving refinement of the existing culling logic is possible. This requires two preparatory steps. First, the user must verify the actual flag data stored in the original WMO files from the game's MPQ archives. By inspecting the raw bytes for a sample of problematic buildings, the user can determine if the groups are indeed flagged only with `MOGP_INTERIOR` or if they possess a combination of flags, such as `MOGP_EXTERIOR | MOGP_INTERIOR`. This validation step is critical, as it will confirm whether the issue originates from the TrinityCore vmap data extraction process. If the flags are misread by the extractor, correcting the parsing script would be the proper fix.

Assuming the flags are correctly `MOGP_INTERIOR`, the second step is to refine the culling algorithm to be smarter than a simple shader hack. Instead of relying on the derivative-based normal check, which is imprecise and inefficient, the editor should leverage the portal graph structure. The user has already calculated the BFS distance from exterior groups, which is a powerful piece of information. A refined algorithm could work as follows: for each WMO group, if its BFS distance is greater than a configurable threshold (e.g., 1), it is culled from the exterior view. This mimics the likely behavior of the client's "facade peering" logic, where only groups directly connected to the exterior are considered for rendering. Groups with a distance of 0 are the exterior walls themselves, and groups with a distance of 1 are the ground-floor interiors like shop fronts. This method is more accurate than the current shader approach and provides a better approximation of the client's behavior, though it is still more complex to implement than the simple "render all" solution.

Finally, it is important to reiterate that for a navmesh and pathfinding editor, absolute fidelity to the game client's rendering is not a requirement. The client's rendering is optimized for visual appeal and performance in a real-time gaming context. The editor's rendering is optimized for clarity and completeness in a development context. The trade-off between visual accuracy and functional correctness favors functionality. Therefore, the recommendation is to prioritize simplicity and reliability. Implementing the "City View" mode that renders all WMOs is the most prudent course of action. It guarantees a complete and correct representation of the world for pathfinding purposes, eliminating the user's current problems and future-proofing the editor against similar issues in other zones. This approach acknowledges the complexity of the client's visibility system while pragmatically working around it to meet the specific, well-defined goals of the project.
