# Beyond Spatial Cutoffs: A Multi-Layered Heuristic for Eliminating WMO Interior Artifacts in a Custom 3D Viewer

## Problem Analysis: The Nature of Indoor Artifacts in VMAP-Based Rendering

The visual artifacts encountered when viewing World of Warcraft cities from an elevated perspective stem directly from the nature of the data provided by TrinityCore's vmap tools and the absence of a sophisticated visibility system in the custom 3D viewer <user>. The core issue is not a flaw in the viewer's rendering pipeline itself, but rather a fundamental mismatch between the raw collision mesh data extracted and the complex spatial relationships required to render a coherent architectural environment. The viewer correctly parses the geometric data—vertices, indices, and per-group headers—from the VMAP048 format, transforming model-space coordinates into world space <user>. However, this process reconstructs the building's physical boundaries without any context regarding their semantic role within the structure. Consequently, every piece of geometry, whether it represents an external facade, an internal wall, a corridor ceiling, or a staircase landing, is treated as an independent object to be rendered if it falls within the view frustum. This leads to the manifestation of massive, untextured vertical slabs, which are the tops of interior rooms and corridors extending above the main roofline of buildings like Stormwind City Hall <user>.

The root cause of this problem lies in the stripping away of critical "glue" data during the VMAP extraction process. The original game engine uses a highly optimized visibility determination system, primarily based on Binary Space Partitioning (BSP) trees combined with portals, to decide which parts of a scene are visible from the player's current viewpoint [[12](https://www.researchgate.net/publication/337590893_Indoor_Navigation_Systems_Using_Annotated_Maps_in_Mobile_Augmented_Reality)]. A BSP tree recursively divides a space into convex subspaces, and portals are defined as rectangular openings (like doors or windows) that connect these subspaces. The game client determines visibility by traversing this hierarchical structure from the player's starting point, only rendering the polygons contained within reachable convex subspaces. The VMAP data, however, contains no such structural information. It provides individual WMO groups, each with its own set of vertices and a bounding box, but offers no insight into how these groups relate to one another in a navigable or occlusive manner [[12](https://www.researchgate.net/publication/337590893_Indoor_Navigation_Systems_Using_Annotated_Maps_in_Mobile_Augmented_Reality)]. This lack of connectivity and spatial hierarchy is precisely why the viewer cannot differentiate between the exterior shell of a building and the voluminous, empty spaces inside it.

Furthermore, the metadata associated with each group in the VMAP file is often ambiguous or semantically misleading. For instance, the user's initial attempt to filter out interior groups using the `MOGP_FLAG_INTERIOR` (0x2000) failed because this flag does not control geometric location; instead, it dictates the lighting mode used for rendering the group, specifically `LIGHTING_MODE_INTERIOR` <user>. Many architectural features on the exterior of a building, such as overhangs, balconies, or shaded facades, may require interior-like lighting calculations to appear correct under certain conditions. Therefore, applying this flag as a geometric classifier removed a significant portion of valid exterior geometry, demonstrating that simple flag checks are unreliable for this task <user>. The mogpFlags header also contains other flags, such as `MOGP_FLAG_OUTDOOR` (0x0008), which appears more promising but is still likely incomplete on its own [[12](https://www.researchgate.net/publication/337590893_Indoor_Navigation_Systems_Using_Annotated_Maps_in_Mobile_Augmented_Reality)]. The fundamental limitation is that the VMAP format, while excellent for collision detection, was not designed to support advanced visibility approximations. It isolates geometric primitives from the rich contextual data that defines their role within the larger architectural whole. Without access to the original WMO structure, including its portal definitions (found in MOPT and MOPR chunks), any attempt to solve this problem must rely on heuristic approximations derived solely from the available vertex positions and basic metadata <user>[[12](https://www.researchgate.net/publication/337590893_Indoor_Navigation_Systems_Using_Annotated_Maps_in_Mobile_Augmented_Reality)].

## Heuristic-Based Approximation Using VMAP048 Data

Given the constraints of the VMAP048 data, which lacks explicit visibility or connectivity information, a robust solution requires developing a multi-stage heuristic approximation. This approach moves beyond simplistic rules like height-based clipping and instead builds a probabilistic model to classify each WMO group based on a combination of its metadata flags, spatial properties derived from its bounding box, and geometric characteristics of its vertex cloud. While this method will not be perfect, a well-designed combination of these heuristics has a high probability of achieving the target reduction of ~90% in visual artifacts.

The first stage of this heuristic process should focus on the `mogpFlags` present in the 36-byte group header. Although single flags can be misleading, combinations provide valuable clues. The most direct indicator of exterior geometry is the `MOGP_FLAG_OUTDOOR` (0x0008) flag. Groups possessing this flag are almost certainly part of the building's exterior shell and should be included in the rendering list without further scrutiny. Conversely, the absence of this flag makes a group a candidate for either interior geometry or potentially overlooked exterior features. The previously problematic `MOGP_FLAG_INTERIOR` (0x2000) flag, related to lighting mode, should generally be disregarded for geometric classification, as its presence does not reliably indicate that a group is inside a building <user>. A more nuanced approach would involve checking for combinations, such as a group having neither the outdoor flag nor the interior lighting flag, which might suggest it is part of a neutral, possibly flat, exterior surface like a courtyard floor or a large plaza tile.

The second stage introduces spatial heuristics derived from the group's bounding box (`bbox`). The bounding box provides a fast, computationally inexpensive way to analyze the coarse-grained shape and position of a group relative to its surroundings. One powerful heuristic is the aspect ratio of the bounding box. Interior architectural elements like walls, partitions, and columns typically form long, thin, prismatic shapes, whereas exterior facades tend to have more varied and often more complex geometries. By calculating the ratios of the box's width, height, and depth, one can identify candidates that match the profile of an interior wall. For example, a bounding box where the height is significantly greater than both the width and depth, and the width and depth are similar and small, is a strong indicator of an interior partition. Another spatial heuristic involves analyzing the group's position relative to the ground plane and known building structures. A naive height cutoff was rejected by the user, but a more intelligent version can be implemented. Before rendering, a preliminary pass could establish an approximate ground level for the city and identify the heights of major building rooftops. Any WMO group whose bounding box extends significantly above the local roofline and whose base is not supported by a solid, enclosing roof structure is a prime candidate for culling. This helps filter out the tops of tall interior rooms and corridors that create the most disruptive visual artifacts <user>.

The third and most computationally intensive stage involves a deeper geometric analysis of the vertex cloud for high-probability candidate groups. After filtering with flags and spatial heuristics, the remaining groups are those most likely to be problematic interiors. A lightweight Principal Component Analysis (PCA) can be performed on their vertices to assess planarity. Interior walls and ceilings are, by definition, largely flat surfaces. PCA decomposes the vertex cloud into three orthogonal axes (principal components) representing the directions of maximum variance. If the variance along one of these axes is very small compared to the other two, it indicates that the points lie predominantly on a plane, consistent with a wall or floor. This confirms the geometric nature of the group before deciding to cull it. Additionally, one could compare the overall shape of the vertex cloud to a canonical representation of an interior wall segment. This could involve fitting a simplified rectangle to the cloud's convex hull and comparing the fit's quality. A high-quality fit would reinforce the classification of the group as an interior wall.

By combining these three stages—a primary filter based on `MOGP_FLAG_OUTDOOR`, a secondary refinement using spatial heuristics on bounding boxes, and a tertiary validation using vertex-based geometric analysis—it is possible to construct a powerful and flexible heuristic system. This multi-layered approach allows for a weighted decision-making process, where multiple lines of evidence must align before a group is culled. This strategy directly addresses the user's need for an approximation that is more sophisticated than simple spatial cutoffs and leverages all available information within the VMAP048 format to achieve a high degree of accuracy.

| Heuristic Stage | Method | Basis of Operation | Computational Cost | Reliability |
| :--- | :--- | :--- | :--- | :--- |
| **Primary Filter** | Flag Check | Checks for `MOGP_FLAG_OUTDOOR` (0x0008) in `mogpFlags`. | Very Low | High (for confirming exterior) / Medium (for identifying candidates) |
| **Secondary Filter** | Bounding Box Analysis | Analyzes box aspect ratios and vertical position relative to rooflines. | Low | Medium |

This structured, tiered approach provides a practical and systematic method for tackling the problem with the available VMAP data.

## Leveraging Original WMO Files for Definitive Visibility Classification

Should the heuristic-based approximation using only VMAP048 data prove insufficient to meet the goal of eliminating ~90% of artifacts, the next logical step is to parse the original WMO files from the game's MPQ archives. This pathway unlocks access to the definitive source of visibility information used by the official World of Warcraft client: the portal-based culling system. While this approach is more complex to implement, it replaces probabilistic heuristics with deterministic data, offering a much higher degree of accuracy and reliability in distinguishing geometrically interior groups from exterior ones <user>. The user has confirmed they are willing to undertake this path, making it a viable and powerful alternative.

The official visibility system relies on a Binary Space Partitioning (BSP) tree structure for each WMO [[12](https://www.researchgate.net/publication/337590893_Indoor_Navigation_Systems_Using_Annotated_Maps_in_Mobile_Augmented_Reality)]. This tree is built from partitions, which correspond to the planes of the WMO's geometry (walls, floors, etc.). These partitions divide the 3D space of the WMO into a series of non-intersecting convex volumes called "leaves." The key to visibility is the concept of portals, which are essentially rectangular holes in these partitions, allowing passage between adjacent leaves. The definitions for these portals are stored in the `MOPT` chunk of the WMO file [[12](https://www.researchgate.net/publication/337590893_Indoor_Navigation_Systems_Using_Annotated_Maps_in_Mobile_Augmented_Reality)]. Each portal is defined by a set of vertices that form its boundary. The `MOPR` chunk then provides the crucial link for each WMO group: it contains a list of indices that point to the portals defined in the `MOPT` chunk that bound that particular group <user>. In essence, the `MOPR` data tells you exactly which portals are attached to a given piece of geometry.

For the custom viewer, this data can be leveraged to perform a simplified but effective culling operation without needing to fully replicate the game's real-time BSP traversal algorithm. Instead of determining visibility on-the-fly for a moving camera, the goal is to pre-classify each WMO group as definitively "exterior" or "interior" based on its connectivity within this static portal graph. The strategy would involve the following steps: First, the WMO file is parsed to extract the `MOPR` and `MOPT` chunks. Second, a graph representation of the portal connections is constructed, where nodes represent the convex leaves of the BSP tree and edges represent the portals connecting them. Third, this graph is analyzed to identify which leaves are connected to the exterior of the building. A leaf can be identified as exterior if one of its portals has a normal vector pointing outwards or if it connects to a large, open area (which can be determined by analyzing the portal's size and the surrounding geometry). Once a seed exterior leaf is found, a flood-fill or graph traversal algorithm can be used to mark all other leaves that are reachable through connected portals as "interior." Finally, the WMO groups are classified: any group whose `MOPR` data lists portals belonging to an exterior leaf is marked for rendering, while all others are culled.

This method provides a definitive answer to the classification problem. Unlike heuristics based on geometry alone, which can be fooled by unusual architectural designs or misinterpreted flags, the portal data represents the actual design intent of the game's artists and engineers. It explicitly defines the navigable and visible spaces within a WMO. While implementing a full BSP tree traversal for dynamic camera movement is a significant undertaking, the task of pre-classifying all groups as interior or exterior is far more manageable. It effectively offloads the complex visibility calculation from runtime to an offline preprocessing step, which is perfectly suited for a map viewer application where the camera can be freely moved but performance is less critical than in a live game client. By integrating a WMO parser and utilizing the `MOPR` data, the viewer gains access to a gold-standard dataset that can resolve ambiguities left by the VMAP-only approach, providing the highest possible accuracy for removing the unwanted indoor rendering artifacts.

## Comparative Analysis of Existing Viewer Implementations

An investigation into the strategies employed by existing third-party viewers, such as Noggit, WoW Model Viewer, and MapViewer, reveals that they universally adopt pragmatic, heuristic-based approaches to manage the complexities of rendering WMOs, rather than attempting to implement the full, resource-intensive portal and BSP culling systems used by the official game client [[12](https://www.researchgate.net/publication/337590893_Indoor_Navigation_Systems_Using_Annotated_Maps_in_Mobile_Augmented_Reality)]. This finding is critical, as it validates the chosen direction of pursuing heuristic approximations. Given that these viewers are designed for tasks like model inspection, texture browsing, and general map exploration, they face many of the same challenges in rendering isolated or improperly contextualized geometry. Their solutions, honed through community development, offer valuable insights into what works in practice.

While the provided sources do not contain direct technical documentation detailing the specific culling logic of each viewer, their functionality strongly implies the use of simplified filtering mechanisms. For example, viewers like Noggit allow users to load entire zones and navigate freely, yet they do not exhibit the extreme levels of rendering chaos one might expect from a naive rendering of all collision meshes. This suggests the presence of some form of automatic or semi-automatic culling. The most common and straightforward method employed by such applications is filtering based on WMO group flags. It is highly probable that many of these viewers use a simple heuristic, perhaps even one as basic as filtering on the `MOGP_FLAG_INTERIOR` (0x2000) flag, despite its known unreliability for geometric classification <user>. Such a filter would remove a significant number of obvious interior artifacts at the cost of excluding some valid exterior geometry, a trade-off acceptable for a viewer focused on general exploration.

Another common strategy seen in various 3D viewers and modeling applications is the manual selection or toggling of objects. Viewers often provide a hierarchical object browser or a list of loaded models and groups that the user can interact with. This allows the user to manually disable the rendering of specific WMO groups or entire WMO files that are known to be problematic. This serves as a powerful fallback for cases where automated heuristics fail. For instance, a user encountering a particularly stubborn interior slab could simply find its entry in the viewer's object list and uncheck the 'Visible' box. This approach acknowledges that no automated system is perfect and empowers the user to achieve the desired clean view. This human-in-the-loop mechanism is a standard feature in professional 3D software and is a practical solution for handling edge cases.

Furthermore, it is reasonable to infer that these viewers employ spatial heuristics to automatically hide geometry that is clearly incorrect. For example, a viewer might ignore any geometry below a certain Z-level (height) or within a bounding box that is known to be underground. While the user explicitly rejected "tupitskie kostylki" (stupid hacks) like simple height clipping, a more intelligent version of this principle is widely used. This could involve analyzing the average height of building rooftops in a given area and culling any WMO group whose bounding box is significantly taller than this average and disconnected from any roof structure. This is a more refined version of the spatial heuristic proposed in the VMAP-only approach and is a technique that would yield immediate improvements in visual clarity. The absence of detailed technical reports in the provided sources means that empirical observation of these viewers in action is necessary to confirm the exact implementation details. However, the general principles of 3D visualization and the stated goals of these projects strongly support the conclusion that they rely on a combination of simple flag filtering, manual user controls, and intelligent spatial heuristics to manage the visibility of complex model hierarchies, mirroring the path recommended for the custom viewer.

## Synthesis and Actionable Implementation Roadmap

The comprehensive analysis confirms that the user's objective of eliminating ~90% of indoor WMO rendering artifacts is achievable through a pragmatic, heuristic-based approach that does not require a full recreation of the game's portal culling system. The optimal solution lies in a multi-stage algorithm that leverages all available data from TrinityCore's VMAP048 format, with the option to escalate to parsing original WMO files for higher precision if needed. This roadmap prioritizes implementation simplicity while maximizing the potential for accuracy, directly addressing the user's requirements for a robust yet non-trivial solution.

The primary and most efficient recommendation is to implement the multi-layered heuristic algorithm using only the VMAP048 data. This approach is advantageous because it requires no modification to the existing project structure, which already handles VMAP parsing and rendering. The implementation should proceed in three distinct stages. First, a primary pass should separate WMO groups into two categories based on the `mogpFlags`. All groups with the `MOGP_FLAG_OUTDOOR` (0x0008) bit set should be designated as `exterior_candidates` and passed to the renderer immediately. All other groups, lacking this flag, should be placed in a temporary `interior_candidate` list for further analysis. This initial split efficiently filters a significant portion of the data based on the most reliable available metadata. Second, the `interior_candidate` list should be processed using spatial heuristics. For each group, its bounding box should be analyzed for characteristic interior shapes, such as a high aspect ratio indicative of a wall, and its vertical position relative to the surrounding terrain and building rooftops should be checked. Groups that are disproportionately tall and not supported by a roof are strong candidates for culling. Third, for the remaining high-probability candidates from the second stage, a lightweight geometric validation can be performed. A Principal Component Analysis (PCA) on the group's vertex cloud can quickly determine if the geometry is a flat plane, a hallmark of interior walls and ceilings. Only if a group passes all three stages of scrutiny should it be considered for culling. This tiered system ensures that decisions are well-supported by multiple forms of evidence, increasing the likelihood of correctly identifying true interior artifacts while preserving valid exterior structures.

If this VMAP-only heuristic proves inadequate and fails to meet the ~90% artifact reduction target, the secondary recommendation is to integrate a parser for the original WMO files. This path provides definitive, data-driven answers about visibility but comes at a higher implementation cost. The process involves adding a component to read `.wmo` files from the game's MPQ archives. The key data to extract is the `MOPR` chunk for each WMO group, which links the group to specific portals defined in the `MOPT` chunk <user>. From this, a portal connectivity graph can be constructed. An offline analysis of this graph can then be used to classify all WMO groups definitively as "interior" or "exterior" by performing a graph traversal from known exterior points. Once this pre-classification is complete, the rendering code can be updated to ignore any group labeled as interior. This method bypasses the ambiguity of heuristics entirely and relies on the architecturally correct data used by the game client itself, offering the highest possible accuracy.

In summary, the recommended course of action is to begin with the VMAP-only heuristic approach due to its low implementation overhead and high potential for success. It systematically applies logical filters based on available data, moving from simple flag checks to more complex spatial and geometric analyses. Should this initial effort fall short of the desired accuracy, the project can then be extended to include WMO file parsing, providing a robust, data-backed solution that guarantees superior results. This phased approach allows for incremental progress and avoids committing to the more complex WMO parsing effort unless absolutely necessary, ensuring an efficient and effective resolution to the rendering artifact problem.
